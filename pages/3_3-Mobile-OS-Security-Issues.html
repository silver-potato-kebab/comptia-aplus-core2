Troubleshoot Common Mobile OS and Application Security Issues

Unauthorized Sources Root / Jailbreak Malicious Apps Compromise Symptoms

Mobile devices carry credentials, email, financial accounts, corporate data, and personal communications — making them high-value targets for attackers. Unlike desktop malware, mobile threats exploit a different attack surface: unofficial app stores, OS-level privilege escalation through rooting and jailbreaking, social-engineered permission grants, and users who trust a familiar-looking app icon without verifying its authenticity.

This objective has two distinct parts. The first covers the security concern categories — the conditions that make a device vulnerable or compromised: where apps came from, whether the OS has been modified, and what kind of malicious software is present. The second covers the observable symptoms — the signs that a compromise has occurred or is in progress. A technician must be able to recognize symptoms, map them to probable causes, and prescribe the correct remediation. Because many symptoms overlap across multiple threat types, systematic diagnosis is essential.

Exam Approach

The exam presents scenarios in both directions: given a threat (e.g., "a user rooted their Android phone"), identify the security risks; or given a symptom (e.g., "data usage suddenly spiked"), identify the most likely cause and appropriate response. Master both mappings. Note that multiple symptoms can point to the same underlying threat, and a single threat can produce multiple symptoms simultaneously.

Section AMobile Security Architecture — Why These Threats Exist

To understand mobile security threats, a technician must first understand the security model that those threats attempt to bypass. Both iOS and Android are built around several interlocking security principles that, when intact, make it very difficult to compromise a device. The threats in this objective are, in most cases, attacks on one or more of these principles.

The Mobile Security Model
App sandboxing, store vetting, OS integrity protection, and permission controls
Foundation
App sandboxing
Every app on both iOS and Android runs in a sandbox — an isolated execution environment where the app can only access its own files and resources unless the user explicitly grants permission. An app cannot read another app's data, access the file system arbitrarily, or escalate its own privileges. This is why mobile malware, even when installed, has limited reach compared to desktop malware — without root/jailbreak privileges, a malicious app is contained in its sandbox. Breaking out of the sandbox requires exploiting a kernel vulnerability (the basis of rooting and jailbreaking).
App store vetting
The Apple App Store and Google Play Store review apps before distribution, scanning for malware signatures and enforcing API usage policies. This gatekeeping is imperfect (malicious apps do occasionally pass review) but dramatically reduces the risk compared to installing apps from arbitrary web sources. The vetting process is why Apple prohibits sideloading entirely on consumer iOS devices (in most regions) — every app must pass App Store review. Google Play Protect adds a runtime layer that continuously scans installed apps for malicious behavior even after installation.
Permission model
Apps must request explicit user permission before accessing sensitive resources: camera, microphone, location, contacts, calendar, health data. Android 10+ and iOS 13+ granularized these controls — location can be granted "only while using the app" rather than always; one-time permissions expire after the session. The permission model limits damage from malicious apps: an app that cannot obtain camera permission cannot silently capture photos or video. Malicious apps circumvent this by social-engineering users into granting broad permissions ("This app requires access to your contacts to function") for permissions they don't actually need.
OS integrity and secure boot
Both platforms implement secure boot — each stage of the boot process is cryptographically verified before it executes, ensuring only Apple/Google-signed OS code runs. iOS adds System Integrity Protection and cryptographic signatures on system files. Android implements Verified Boot (dm-verity) which detects modifications to the OS partition at boot time. Rooting and jailbreaking specifically attack these integrity mechanisms — their goal is to run unsigned code at the kernel level, bypassing all protections above.

Section BSecurity Concerns

Application Source / Unofficial App Stores

Unofficial Application Sources
Apps obtained outside the official App Store or Google Play — sideloading and third-party stores
High Risk
Android format
.apk file (sideloading)
iOS format
.ipa file (restricted)
Primary risk
No vetting → undetected malware
What unofficial sources are
Unofficial application sources are any distribution mechanism for mobile apps other than the platform-official stores. On Android, this includes: direct .apk file downloads from websites, third-party app stores (Amazon Appstore, F-Droid, APKPure, Aptoide), and app stores bundled with non-Google Android devices (Samsung Galaxy Store, Huawei AppGallery). On iOS, this includes: enterprise distribution certificates used to distribute non-App Store apps, AltStore, and — in the European Union following the Digital Markets Act — third-party marketplaces that Apple has been compelled to allow on EU devices. Unofficial sources bypass the gatekeeping review that official stores provide.
Why unofficial sources are dangerous
Without store review, there is no check for malware, no API enforcement, and no mechanism for the platform to remotely remove malicious apps after discovery. Common attacks using unofficial sources: repackaged legitimate apps — an attacker takes a popular app, injects malicious code, and redistributes the modified APK on third-party sites; the app functions normally (making the user trust it) while simultaneously performing malicious actions. Cracked paid apps — users seeking to use paid apps for free download cracked APKs that almost universally contain bundled malware — the "free" version of a paid app is one of the most reliably malware-laden distribution vectors in mobile security. Direct social engineering — a phishing message instructs the user to download an APK from a link "to verify their account" or "update their banking app."
Android — "Unknown Sources" / Install Unknown Apps
Android requires explicit user action to enable installation from unofficial sources, specifically to reduce the attack surface of sideloading. Android 8+: the permission is per-source-app rather than a global toggle — Settings → Apps → [browser or file manager] → Install unknown apps → Allow. After sideloading a trusted app, this permission should be immediately disabled. On enterprise devices managed by MDM, the ability to enable unknown sources is typically blocked by policy. A technician who discovers that "Install unknown apps" is enabled on a corporate device for a browser or messaging app should flag this as a policy violation — it indicates either a policy gap or a potential social engineering attack that convinced the user to enable it.
Legitimate use cases for unofficial sources
Not all unofficial source usage is malicious. Legitimate scenarios: enterprise in-house apps distributed via MDM or enterprise certificates (corporate line-of-business apps that are not in the public store); beta testing (TestFlight on iOS, internal testing tracks on Android); open-source apps on F-Droid (a curated repository of free and open-source Android apps with its own review process); regional apps unavailable in certain country app stores. In these cases, the risk is managed through organizational controls, known publishers, and trusted certificate chains rather than open-internet distribution.
Google Play Protect
Google Play Protect continuously scans all installed apps (including sideloaded ones) for malicious behavior. It is Android's primary runtime defense against malware. Even if a malicious app is installed from an unofficial source, Play Protect may detect and flag it during its background scans. Check Play Protect status: Play Store → profile icon → Play Protect. Play Protect should always be enabled. Its effectiveness against sideloaded malware is lower than against Play Store malware because it must detect behavioral anomalies rather than relying on pre-publication review. iOS has no equivalent because sideloading is generally prohibited — the app review process is the primary defense.

Developer Mode

Developer Mode
An OS state that enables advanced capabilities intended for app development — expanding the attack surface
Elevated Risk
What developer mode enables
Developer mode unlocks advanced capabilities on mobile devices intended for app developers and testers. On Android: tap Build Number seven times in Settings → About → enables Settings → Developer Options, which includes: USB debugging (ADB access), mock location providers, background process limits override, Wi-Fi verbose logging, pointer location overlays, and the ability to install apps via ADB (Android Debug Bridge) over USB or network — effectively enabling sideloading without going through the "Install Unknown Apps" flow. On iOS: enabled via Xcode or Settings → Privacy & Security → Developer Mode (iOS 16+); enables apps to run in development mode, Instruments profiling, and TestFlight beta installs.
Security risks
The primary security risk of developer mode is USB debugging (ADB). When USB debugging is enabled and a device is connected to a computer with an authorized ADB host key, a technician (or attacker) can: install arbitrary APKs without any store review (adb install app.apk), extract the contents of accessible storage, execute shell commands on the device, screen capture or record, and bypass lock screen protection on some Android versions. Practical attack scenario: a device left unattended at a desk with USB debugging enabled can be compromised in seconds by connecting a USB cable to a prepared laptop — no password is required if the host key is already authorized, or if the attacker can briefly authorize their key during the window when the screen is on.
Who should have it enabled
Developer mode should only be enabled on devices actively used for app development or testing. On corporate devices, MDM policy should block developer mode if it is not operationally required. A technician who discovers developer mode enabled on an end-user's device should: inquire about the reason (was it enabled intentionally by the user, or by someone with temporary access?), disable it, and report to the security team if no legitimate reason is identified. Developer mode being enabled on a device that was "slow" or "acting strange" is a significant indicator of potential compromise.
Disabling developer mode
Android: Settings → Developer Options → toggle off the master switch at the top of Developer Options. On some Samsung devices, this is under Settings → Developer Options → disable via the toggle at the top. Disabling developer mode disables USB debugging and all associated capabilities immediately. iOS: Settings → Privacy & Security → Developer Mode → toggle off → the device restarts to apply the change. After disabling, a passcode is required to re-enable, providing some protection against re-enablement by an unauthorized party with brief physical access.

Root Access and Jailbreaking

Root Access (Android) / Jailbreak (iOS)
Exploiting kernel vulnerabilities to gain superuser / administrator access — dismantling the OS security model
Critical Risk
Android term
Rooting — gaining root (superuser) access
iOS term
Jailbreaking — bypassing iOS restrictions
Corporate policy
MDM detects and may wipe rooted/jailbroken devices
What rooting/jailbreaking is
Rooting on Android and jailbreaking on iOS both refer to exploiting kernel-level vulnerabilities in the mobile OS to gain superuser (root) privileges — the equivalent of administrator access on a desktop OS. With root access, code can bypass all sandbox restrictions, read any app's data, modify system files, disable security controls, install system-level modifications, and operate completely outside the OS's normal security model. Rooting/jailbreaking typically requires chaining together multiple OS exploits to escalate privileges from the user level to the kernel level. Tools like Magisk (Android) and checkra1n/unc0ver (iOS) automate this process.
What the security model loses
A rooted or jailbroken device has fundamentally compromised security because every protection that depends on the OS enforcing rules is now circumventable: App sandboxing — any app with root access can read other apps' sandboxes, including authentication tokens, session cookies, and local database files containing credentials; Verified Boot / Secure Boot — the boot chain integrity is broken; modified OS code may run without detection; Permission model — root-capable apps can self-grant any permission without user interaction; Certificate stores — root access allows installing arbitrary CA certificates, enabling man-in-the-middle attacks against all HTTPS traffic on the device; Full disk encryption — keys accessible at root level; device storage readable without the user's PIN.
Attack chain enabled by root
The most dangerous scenario is a rooted device with a malicious app that takes advantage of root access. Without root, a malicious app is confined to its sandbox. With root, it can: extract credentials from all other apps' databases (banking apps, password managers, email); intercept all network traffic (by installing a rogue CA certificate); log all keystrokes across all apps; silently send any file from the device to an external server; establish a persistent backdoor that survives reboots; and prevent its own removal by modifying system files. This is why security researchers describe rooting a device as "handing the attacker the keys to the kingdom."
Detecting root/jailbreak
Signs that a device may be rooted or jailbroken: Android — presence of apps like SuperSU, Magisk Manager, or KingRoot in the app drawer; warnings from banking apps ("This device is not secure"); Google Play Protect showing "Device not Play certified" or SafetyNet/Play Integrity API failing; unusual apps in system app list; device is marked "Rooted" in MDM console. iOS — presence of Cydia, Sileo, or Zebra (jailbreak app stores) on the home screen; apps loading that are not available on the App Store; abnormal battery drain; MDM enrollment failing with "device integrity check failed." Many MDM solutions (Intune, Jamf, VMware) include jailbreak/root detection and can automatically quarantine or wipe detected devices.
Corporate policy response
Most enterprise MDM policies include a compliance rule that triggers an automated response when a rooted or jailbroken device is detected: block access to corporate email, VPN, and apps; selective wipe (remove only corporate data while leaving personal data); or full wipe (factory reset the device). These responses are applied automatically without requiring IT intervention — the MDM continuously checks device integrity. A technician asked to investigate a device flagged by MDM for root/jailbreak detection should: confirm the detection, inform the user that corporate data access is suspended pending investigation, and escalate to the security team. The correct remediation for a rooted/jailbroken device is a factory reset — not attempting to "unroot" the device, as unrooting tools may not fully restore security integrity.

Root vs. Jailbreak — Platform Differences

While conceptually similar, rooting and jailbreaking differ in prevalence and current risk. Android rooting is more common historically because many Android device manufacturers (particularly budget devices) used to ship with unlockable bootloaders, making rooting accessible to non-experts. Modern Android and Google's Play Integrity API have made root harder to hide and actively block rooted devices from running banking apps. iOS jailbreaking has become increasingly difficult as Apple patches exploits rapidly — modern jailbreaks on current iOS versions are rare and often require sophisticated exploit chains. However, a successfully jailbroken iOS device is arguably more dangerous because users expect iOS to be more secure, making them less vigilant about what they install through Cydia.

Unauthorized and Malicious Applications

Unauthorized / Malicious Applications
Apps designed to harm the user or device — spanning adware, spyware, trojans, and credential stealers
CriticalData Loss Risk
Malware categories on mobile
Adware — displays intrusive advertisements, often outside the app that installed it (full-screen ads appearing on the home screen or notification shade); monetizes by generating fraudulent ad impressions. Spyware / Stalkerware — silently monitors user activity (SMS messages, call logs, location, photos) and exfiltrates data to a remote server; often installed by a person with physical access to the device (intimate partner surveillance). Trojans — apps that appear legitimate but contain hidden malicious functionality; a "free version" of a paid game that also subscribes the user to premium SMS services in the background. Banking Trojans — specifically target financial apps by overlaying fake login screens over legitimate banking apps to capture credentials. Cryptominers — run cryptocurrency mining code in the background, consuming CPU, battery, and data.
How malicious apps evade detection
Malicious apps on official stores evade initial review through several techniques: delayed malicious behavior — the app behaves benignly during the review period, then switches to malicious behavior after a time delay or triggered by a server command; dynamic code loading — the initial package is clean, but it downloads and executes additional code from a remote server after installation; legitimate functionality plus hidden payload — the app genuinely does what it claims (flashlight, QR reader, calendar) while also performing malicious background tasks; permission escalation over time — the app gradually requests additional permissions through in-app prompts framed as necessary for new features.
Indicators of a malicious app
Behavioral signs: excessive permission requests (a wallpaper app requesting contact list access, microphone, or location); high data usage from a low-use app; battery drain correlated with the app running in the background; ads appearing when the app is not in the foreground; new apps appearing that the user did not install (malware can install additional payloads); banking apps showing overlay screens with slightly different designs. Structural signs: very few reviews, recently published account, no publisher website, reviews that seem generic or copied.
Removal and remediation
For a confirmed malicious app: (1) Uninstall immediately — Settings → Apps → [app] → Uninstall. (2) Revoke all permissions it was granted and audit whether other apps were installed by it. (3) Change passwords for any accounts accessed while the malicious app was installed — it may have captured credentials. (4) Contact financial institutions if banking app credentials may be compromised. (5) Run a mobile security scanner (Malwarebytes, Bitdefender, Lookout) to check for additional malware. (6) If the full scope of compromise is unclear, perform a factory reset — it is the only way to guarantee the device is clean.

Application Spoofing

Application Spoofing
Fake apps that impersonate legitimate ones to steal credentials or deceive users
Credential Theft
Primary goal
Credential harvesting
Detection method
Check publisher, reviews, rating count
Also called
Fake app, counterfeit app
What application spoofing is
Application spoofing is the creation of a fake app that closely resembles a legitimate, trusted application — copying its icon, name, color scheme, and interface — to trick users into entering credentials or other sensitive information into the fake version. The fake app may appear in the official store (if the attacker managed to get it published before removal) or be distributed via unofficial stores and phishing links. When the user "logs in" to the spoofed app, their credentials are sent to the attacker's server rather than the legitimate service. Examples include: fake banking apps, fake two-factor authentication apps, fake VPN apps, and fake antivirus apps.
How to identify a spoofed app
Check the publisher/developer name — the official Chase bank app is published by "JPMorgan Chase Bank, National Association"; a spoof might be published by "Chase Banking Services" or a generic developer account. Check the number of reviews and install count — a legitimate popular app has millions of installs; a spoof published recently has hundreds or thousands. Check the publish date — a banking app that has been in the store for two months is almost certainly not the real bank's app. Navigate directly to the legitimate website to find the official app store link — never search for banking or financial apps by name in the store; always link from the official website. Verify the URL/developer in the app store listing — scammers often use slightly misspelled names (Citi-Bank instead of Citibank).
Overlay attacks (a related technique)
A variant of app spoofing that does not require a separate fake app is the overlay attack. A malicious app that has been granted the "Draw Over Other Apps" permission on Android can display its own interface on top of a legitimate banking app — the user thinks they are entering their credentials into the real bank app, but they are actually typing into an overlay window controlled by the malicious app. The legitimate bank app is running underneath but never receives the keystrokes. Prevention: revoke "Draw Over Other Apps" permission from any app that does not legitimately need it (accessibility tools, screen recorders). On iOS, the sandboxing model prevents overlay attacks entirely — apps cannot draw over other apps.
Enterprise context — authorized app lists
In corporate environments, MDM systems maintain an authorized app catalog — a list of approved apps that users may install. This directly addresses application spoofing: employees install apps from the MDM-managed catalog rather than searching the public store, and the catalog contains only verified, IT-approved versions of required apps. A new employee who is told to "install the company's expense reporting app" should be directed to the MDM company portal, not the public store, to ensure they install the genuine version rather than a spoofed one that may have been planted in the store with a similar name.

Section CCommon Symptoms of Mobile Security Compromise

The nine symptoms listed in this objective are the observable manifestations of the security concerns covered above. A technician who encounters one or more of these symptoms must be able to construct a differential diagnosis — which of the possible underlying causes best explains what the user is seeing, and what additional evidence would confirm or rule out each possibility.

High network traffic
Most likely: spyware/malware exfiltrating data, cryptominer sending results, botnet activity. Also: legitimate app update, video streaming.
Leaked personal files/data
Most likely: spyware, malicious app with excessive permissions, root-level compromise with data exfiltration. Rarely: legitimate sync misconfiguration.
Data-usage limit notification
Most likely: malware background network activity, cryptominer, adware loading ads. Also: new streaming app, large software update.
High number of ads
Most likely: adware installed (possibly via unofficial source), legitimate free app with aggressive ad SDK. Ads outside the app = adware.
Fake security warnings
Most likely: scareware app or malicious browser notification granted notification permission. Goal is to scare user into installing another malicious app or paying "removal fee."
Degraded response time
Most likely: malware consuming CPU/RAM (cryptominer). Also: battery degradation causing throttling, insufficient storage, too many background processes.
Unexpected application behavior
Most likely: trojan app performing unauthorized actions, malware interfering with legitimate apps. Also: app bug, incompatible OS update.
Limited internet connectivity
Most likely: malware consuming bandwidth, or malicious app redirecting DNS. Also: legitimate network issue, ISP throttling, too many devices on Wi-Fi.
No internet connectivity
Most likely: malware blocking network (anti-forensic), malicious proxy/VPN profile installed. Also: legitimate network outage, misconfigured proxy.

High Network Traffic and Data-Usage Notifications

High Network Traffic / Data-Usage Limit Notification
Unexpected cellular or Wi-Fi data consumption — often indicates covert background exfiltration
Data Exfiltration Indicator
Identifying the cause
The device or carrier sends a data-usage notification because total data consumption has exceeded a threshold — but not all unexplained data usage is malicious. First, rule out legitimate causes: a recent app update (large games can be 1–5 GB), auto-backup initiating on cellular, a video streaming app left running in the background. Then investigate security causes: Android: Settings → Network & Internet → Data Usage → sort by usage — any unfamiliar app appearing near the top, or a known app with disproportionate usage, is the focus of investigation. iOS: Settings → Cellular → scroll down to see per-app cellular data usage. An app that shows high data usage but that the user rarely opens is the primary suspect.
Malware data exfiltration
Spyware and data-exfiltrating malware consume network traffic to send stolen data to command-and-control (C2) servers. The exfiltrated content may include: photos and videos (high volume = high data usage), contacts and calendar, SMS messages, location history, app credential databases, and microphone recordings. Exfiltration is often timed to occur during Wi-Fi connectivity to avoid triggering cellular data alerts — a device that suddenly uses large amounts of data when connected to Wi-Fi but the user wasn't actively streaming should be investigated. Spyware may also be triggered when the device charges overnight, exfiltrating a day's worth of collected data in one transmission.
Cryptominer behavior
Mobile cryptomining malware uses the device's CPU to mine cryptocurrency and submits results to a mining pool server — creating continuous network traffic. The traffic pattern is distinctive: small, frequent outbound connections to the same remote server, occurring even when the device is at idle from the user's perspective. Combined symptom signature: high data usage + degraded performance + high battery drain + device runs warm at idle. This combination strongly suggests a cryptominer. Diagnosis: check data usage by app, check battery usage by app — the same suspicious app should appear elevated in both.
Remediation
Identify the high-traffic app and investigate it: check when it was installed (correlate with when the data spike began), check reviews for reports of malicious behavior, verify the publisher is legitimate, check what permissions it has. If the app is confirmed malicious or suspicious, uninstall it immediately. Monitor data usage for 24–48 hours after removal to confirm the spike resolves. If data usage remains abnormally high after removing the suspect app, there may be additional malware — run a mobile security scanner. If the device was rooted or jailbroken, a factory reset may be required to guarantee removal of all malware components.

Degraded Response Time

Degraded Response Time
Unusual slowness — especially when not correlated with battery age or storage — may indicate a malware process running at high CPU
Investigate Cause
Security vs. hardware cause
Degraded response time can be caused by battery degradation causing CPU throttling (covered in objective 3.2) or by a malicious process consuming CPU. The distinguishing factor is onset pattern: gradual, progressive slowness over months → battery degradation (hardware); sudden onset of slowness that correlates with installing a new app or receiving a suspicious link → malware. Confirm by checking battery health — if battery is healthy (above 80%) and the device is slow, a software cause (malware or rogue legitimate app) is more likely.
Diagnosis steps
Android: Settings → Battery → Battery Usage — identify the app consuming the most CPU in the background. Developer Options → Running Services shows active services and their memory consumption. An unfamiliar service with high memory consumption that was not running before is suspicious. iOS: Settings → Battery → Battery Usage by App — an app with high background activity consumption when the user has not been actively using it is suspicious. Additionally, a device that is warm to the touch when idle indicates high background CPU activity — combined with slowness, this strongly suggests malware (cryptominer or aggressive adware).

Limited / No Internet Connectivity

Limited / No Internet Connectivity
Connectivity that worked before now fails — potentially caused by malicious proxy or VPN profile installation
Check Proxy / VPN Profile
Malicious proxy / VPN profile
A significant and underappreciated mobile attack vector is the installation of a malicious configuration profile (iOS) or a rogue VPN app or proxy setting (Android/iOS) that routes all device traffic through an attacker-controlled server. Once installed, the proxy intercepts all HTTP and HTTPS traffic — enabling man-in-the-middle attacks, credential theft, and traffic monitoring. Malicious configuration profiles are distributed via phishing websites that prompt the user to "install this profile to access the content" or "update your carrier settings." The profile installs a rogue CA certificate alongside the proxy settings, enabling decryption of HTTPS traffic.
Detecting and removing malicious profiles
iOS: Settings → General → VPN & Device Management — review all installed profiles. Any profile not explicitly installed by IT or the user is suspicious; tap it to view the issuer and what it configures (proxy settings, CA certificates). Delete any unauthorized profile. Also check: Settings → General → VPN & Device Management → Certificate Trust Settings — any third-party root certificate installed here enables HTTPS interception; remove any unexpected entries. Android: Settings → Network & Internet → Private DNS or Advanced Wi-Fi → Proxy — check for unexpected proxy settings. Settings → Security → Encryption & Credentials → Trusted Credentials → User tab — any user-added CA certificate that the user did not explicitly install is suspicious and should be removed.
Limited vs. no connectivity
Limited connectivity (can reach some sites but not others) may indicate DNS manipulation — the malware has changed the DNS resolver to redirect specific domains (banking sites, security update servers) to attacker-controlled servers or to block them. No connectivity may indicate the malware is actively blocking outbound connections as an anti-forensic measure (preventing the user from researching the malware) or that a misconfigured proxy/VPN is preventing all traffic. In both cases, check proxy settings, VPN settings, and installed profiles before investigating network hardware.

High Number of Ads

High Number of Ads
Intrusive advertisements — especially those appearing outside any specific app — are the hallmark of adware
Adware
Adware behavior
Adware is malware that generates revenue for the attacker through fraudulent advertising impressions. Mobile adware can manifest as: full-screen ads appearing on the home screen (outside any app), ads in the notification shade, browser redirects to advertisement pages, persistent banner ads that overlay other app interfaces, and "push notification ads" (ads disguised as system notifications). The key diagnostic question is whether ads appear outside a specific app — ads that appear within a free app are expected (the app is ad-supported); ads that appear when no app is open, on the home screen, or in the lock screen indicate adware installed as a separate app or embedded in a recently installed app.
Identifying the adware source
Correlate when the ads started with what was installed around that time. On Android: check recently installed apps in the Play Store → profile → Manage apps & devices → Installed tab → sort by Last Updated or Recently Used. An app installed just before the ads started is the prime candidate. Adware is frequently disguised as utility apps (flashlights, battery savers, file cleaners, QR scanners) that have no reason to display ads at the OS level. Check for notification-based ads: if the ads arrive as notifications, long-press the notification to identify which app sent it — this directly reveals the adware source on Android.
Remediation
Uninstall the identified adware app. If the source is a browser notification rather than an installed app, go to the browser's Settings → Notifications (or Site Settings → Notifications) and revoke notification permission from any unexpected domain. Run a mobile security scanner after removal to confirm no additional adware components remain. Educate the user: free apps from unofficial sources that are "too good to be true" (free versions of paid apps, no-ads claimed versions) are primary adware vectors. Use the official paid version or the official free version from the official store.

Fake Security Warnings

Fake Security Warnings
Scareware pop-ups claiming the device is infected — designed to cause panic and social-engineer a malicious action
Scareware
What fake security warnings look like
Scareware presents fake security alerts claiming the device is infected with a specific number of viruses, has been hacked, or will be damaged unless the user takes immediate action. Common formats: browser pop-up that appears while browsing and cannot be dismissed (JavaScript alert loop); push notification from a site that was granted notification permission ("URGENT: Your phone has 3 viruses!"); within an already-installed adware app showing a fake scan result; or a full-screen overlay (on Android with Draw Over Other Apps permission) that mimics a system security warning. The goal is always to convince the user to either call a phone number, install an "antivirus" app (which is itself malware), or pay a fee.
Key identification markers
Legitimate mobile OS security alerts never: demand a phone call; ask for payment; claim an exact number of viruses; appear as pop-up browser alerts with countdown timers; instruct the user to install a specific app immediately. A warning with any of these characteristics is fake. The operating system itself handles genuine security issues through Settings and system notifications — not through browser pop-ups or push notifications from websites. When a user receives what they believe is a security warning, have them show it to the technician before taking any action — most users who respond to scareware make the situation worse.
Remediation
Browser-based scareware: close the browser tab. If the alert prevents closing (JavaScript loop preventing dismissal): force-close the browser from the app switcher. Clear the browser's history and cache to prevent the page from reloading on restart. Revoke notification permissions from the domain that delivered push notification scareware (browser Settings → Notifications → remove the offending domain). App-based scareware: uninstall the app that displayed the warning. What not to do: never call the number displayed, never install an app the warning recommends, never pay any amount. If the user has already responded to the scareware (installed the recommended app, entered payment information), treat this as a full security incident — investigate for malware, change financial credentials, contact financial institutions.

Unexpected Application Behavior

Unexpected Application Behavior
Apps doing things the user did not initiate — accessing contacts, camera, sending messages, making purchases
Possible Trojan
What to look for
Unexpected behaviors that indicate a malicious or compromised app: contacts being accessed without the user initiating a contact-dependent action; camera activating without the user opening the camera; SMS messages sent from the user's number that the user did not send (premium SMS trojan); unauthorized in-app purchases charged to the account; apps installed without the user's action (requires root, or another app with Install Packages permission on Android); accounts or services the user doesn't recognize appearing in the account list; settings changed without user action (Wi-Fi settings, screen timeout, security settings). Any of these warrant immediate investigation.
Permission audit
When unexpected behavior is observed, audit the permissions of recently installed apps: Android: Settings → Privacy → Permission Manager — view which apps have access to Camera, Microphone, Location, Contacts, SMS, etc. Any app with permissions it does not legitimately need should have those permissions revoked or the app uninstalled. iOS: Settings → Privacy & Security → [each permission type] — review the app list for each sensitive permission. Specifically check Camera, Microphone, Contacts, Location Services, Photos. An app that does not require camera access (a simple utility, a shopping app) having camera permission granted is a red flag.

Leaked Personal Files and Data

Leaked Personal Files / Data
Private data appearing externally — photos, documents, credentials discovered in places the user did not put them
Incident Response Required
Signs of data leakage
Data leakage may be discovered by: the user receiving a ransom demand that includes sample files proving access; unexpected login notifications to accounts from unknown locations (the attacker used stolen credentials from the device); a contact reporting that they received messages from the user's account that the user didn't send; the user's photos appearing on external sites; financial transactions the user didn't initiate; and in enterprise settings, confidential business files being found externally (triggering a DLP alert or audit finding).
Spyware and stalkerware
Stalkerware is a specific category of spyware typically installed by someone with physical access to the device (an abusive partner, an employer monitoring employee devices without disclosure). Stalkerware apps are specifically designed to be hard to detect — they may not appear in the app drawer, disguise themselves as system apps, and suppress their notifications. Signs: device battery drains faster than expected, device is occasionally warm when not in use, data usage is higher than the user's activities explain. Stalkerware detection and removal resources include the Coalition Against Stalkerware (stopstalkerware.org) and tools like Malwarebytes and Lookout which specifically detect stalkerware.
Incident response steps
A confirmed or suspected data leak requires an escalated response: (1) Preserve evidence — document what data was leaked, when it was discovered, and how. Do not factory reset before documenting (a reset destroys forensic evidence). (2) Identify the vector — is there a malicious app, a compromised account, a rooted device? (3) Change all account passwords immediately, from a different device — the compromised device may have a keylogger. (4) Enable MFA on all accounts. (5) Notify affected parties if corporate data was involved — this may trigger HIPAA, GDPR, or other regulatory breach notification obligations. (6) Factory reset the device after evidence collection. (7) File a report with the organization's security team and, if warranted, law enforcement.

Section DMobile Security Investigation and Remediation

When a mobile device displays one or more compromise symptoms, the technician must work through a structured investigation before taking action. Acting too quickly (immediately factory-resetting without investigation) destroys forensic evidence; acting too slowly (leaving a compromised device connected to corporate networks while investigating) allows the compromise to continue or spread.

1
Quarantine the device. Disconnect it from corporate Wi-Fi and revoke its access to corporate email and VPN while investigation proceeds. On MDM-managed devices, the administrator can block corporate resource access remotely without physically handling the device. This prevents ongoing exfiltration or lateral movement to corporate systems.
2
Document the symptoms and timeline. When did symptoms start? What apps were installed around that time? Have any unusual permissions been requested recently? Did the user click any suspicious links, download any files, or install anything from outside the official store? This information guides the investigation and, if the incident is reportable, forms part of the incident record.
3
Check for device modification. Is the device rooted or jailbroken? (Cydia on home screen, Magisk installed, MDM showing integrity check failure, banking apps showing security warnings.) If yes, treat as a full compromise — the entire security model is broken. Proceed to factory reset after evidence documentation.
4
Review installed apps. Check for apps installed from unofficial sources (on Android, apps without Play Store origin). Check for recently installed apps that correlate with symptom onset. Check permission usage — which apps have access to camera, microphone, contacts, location, SMS. Uninstall any confirmed or highly suspicious malicious apps.
5
Check network configuration. Review proxy settings, VPN profiles, and installed certificates. Remove any unauthorized proxy configuration or CA certificates. On iOS, check Settings → General → VPN & Device Management for unauthorized profiles. On Android, check Settings → Network → Private DNS and Advanced Wi-Fi settings for proxy configuration.
6
Run a mobile security scanner. Malwarebytes, Bitdefender, Lookout, or the built-in Google Play Protect scan can detect known malware signatures and behavioral anomalies. A clean scan does not guarantee no compromise — novel malware evades signature detection — but a positive detection confirms and identifies the threat.
7
Change credentials from a clean device. Regardless of whether malware was confirmed, if the device had access to sensitive accounts (corporate email, banking, password manager), change those passwords from a different, known-clean device. The compromised device may have a keylogger that will capture new passwords typed on it.
8
Factory reset if full compromise is confirmed or suspected. Factory reset is the definitive remediation for mobile malware — it returns the device to a known-clean state. For iOS: Settings → General → Transfer or Reset iPhone → Erase All Content. For Android: Settings → General Management → Reset → Factory Reset. After reset, restore from a backup taken before the suspected compromise date (do not restore from a backup that may contain the malware).

Scenario Decision Guide

Mobile Security Troubleshooting — Symptom to Action
User's cellular data spiked to 8 GB this week — normally uses 2 GB
→
Check Settings → Network → Data Usage → sort by consumption. Identify the app with abnormal data usage. If it is a legitimate app the user was actively using (streaming, video calls), explain the cause. If it is an unfamiliar app or one with disproportionate usage, investigate for malware — check install date, permissions, reviews. Uninstall if malicious.
User sees virus warning pop-ups every few minutes on their Android phone
→
Scareware — do not act on the warnings. Determine source: if browser-based, clear browser cache and revoke notification permission from the offending site. If from a notification, long-press to identify the app source and uninstall it. Reassure the user that the warnings are fake and explain how to identify legitimate security alerts.
MDM console flags an employee's Android device as "rooted"
→
Quarantine the device immediately — MDM should auto-block corporate access. Notify the security team. Investigate: was the device rooted intentionally (policy violation) or unknowingly (malware with root exploit)? Either way: full factory reset required. Do not attempt to "unroot" — restore from a clean backup or set up from scratch. Document and report per incident response policy.
A user downloaded a free version of a paid app from a website and now sees ads everywhere — even on the home screen
→
Classic adware via unofficial source. Uninstall the app (Settings → Apps → [app] → Uninstall). If it was installed as an APK, also check that "Install Unknown Apps" is disabled for that source. Run Google Play Protect scan. Educate the user: free versions of paid apps from unofficial sites almost always contain malware.
User reports their phone feels like it was set up fresh — all their apps are gone
→
Device was either remotely wiped by MDM (common if MDM detected root/jailbreak or a compliance violation) or the user inadvertently triggered a factory reset. Check MDM console for any automated compliance wipe actions on that device. If MDM-initiated: inform the user of the compliance issue that triggered it. If no MDM explanation: investigate whether someone with physical access performed a factory reset.
A user's iPhone will not browse the internet even though Wi-Fi shows connected — started after visiting a website that asked them to "update Safari"
→
The "Safari update" was likely a malicious configuration profile that installed a proxy redirecting all traffic. Settings → General → VPN & Device Management — remove any unauthorized profile. Also check Settings → General → VPN & Device Management → Certificate Trust Settings for unauthorized CA certificates. Remove both. Test connectivity after removal.
User installed an app that claimed to be their bank's new app from a link in a text message — now their bank account shows unauthorized transactions
→
Application spoofing / credential theft — treat as a financial fraud incident. (1) Uninstall the fake app immediately. (2) Contact the bank to freeze accounts and dispute transactions. (3) Change banking credentials from a clean device. (4) Enable MFA on banking accounts. (5) Factory reset the device. (6) File a report with the bank's fraud department and consider a police report. Remind: always install banking apps by linking from the official bank website, never from a text message or email link.
User's partner knows details of private conversations they should not know
→
Suspected stalkerware. Check for unfamiliar apps, especially those disguised as utilities or system apps. Run Malwarebytes or Lookout which specifically detect stalkerware. Check battery usage and data usage for unexplained background activity. Factory reset the device. Change all account passwords from a clean device. Refer the user to the Coalition Against Stalkerware (stopstalkerware.org) and, if in a safety concern situation, to local support resources.

Objective 3.3 — Key Facts Summary

Unofficial app storesNo vetting = no malware screening. Common vectors: cracked paid apps, "free" versions, APKs from websites. Repackaged legitimate apps with injected malware are the primary threat.
Google Play ProtectContinuously scans installed apps including sideloaded ones. Should always be enabled. Less effective against novel sideloaded malware than against Play Store malware.
Android unknown sourcesAndroid 8+: per-source-app permission (Settings → Apps → [app] → Install Unknown Apps). Should be disabled after use. MDM can block globally. Enabled on a corporate device = policy violation.
Developer mode riskEnables USB debugging (ADB). Device connected to a computer with ADB authorization = arbitrary APK install, data extraction, shell commands — no password required if host key authorized.
Rooting (Android)Gains superuser/root access via kernel exploit. Breaks sandboxing, Verified Boot, permission model, certificate stores. Malicious app with root = full compromise. Fix: factory reset.
Jailbreaking (iOS)Bypasses iOS security via kernel exploit. Cydia/Sileo appears on home screen. Allows unsigned code at kernel level. MDM detects and can quarantine/wipe. Fix: factory reset.
Root detection signsAndroid: SuperSU/Magisk Manager present, SafetyNet/Play Integrity failing, banking apps showing security warnings. iOS: Cydia on home screen, MDM integrity check failed.
Application spoofingFake app mimicking a legitimate one (bank, authenticator). Identify by checking publisher name, install count, publish date. Always install banking apps from the official website link, not store search.
Overlay attackMalicious app with "Draw Over Other Apps" draws fake UI over a real banking app. Android only — iOS sandboxing prevents this. Prevention: revoke Draw Over Other Apps permission from untrusted apps.
High network trafficSecurity cause: spyware exfiltrating data, cryptominer, botnet. Diagnose: Settings → Network → Data Usage → sort by app. Correlate with recent installs.
Degraded + warm at idleDevice slow AND warm when not in active use = cryptominer strongly suspected. Check battery usage and data usage — same app will be elevated in both.
Ads outside appsAds on home screen, lock screen, or notification shade = adware app. Long-press notification to identify source app. Uninstall. Ads only inside one app = that app is ad-supported (normal).
Fake security warningsNever: demand a phone call, require payment, claim a virus count, instruct to install a specific app. Source is scareware. Do not act. Close it. Revoke notification permission from source.
Malicious iOS profileDistributed via phishing sites ("install to view content"). Installs proxy settings + rogue CA certificate → enables HTTPS MITM. Check: Settings → General → VPN & Device Management → remove unauthorized profiles and certificates.
StalkerwareInstalled by someone with physical access. Hides from app drawer. Signs: unexplained battery drain, warmth at idle, data usage. Use Malwarebytes/Lookout for detection. Factory reset for removal. Refer user to stopstalkerware.org.
Data leak response(1) Document evidence. (2) Change all passwords from a clean device. (3) Enable MFA. (4) Notify affected parties and security team. (5) Factory reset AFTER evidence documented. (6) Regulatory notification if corporate data involved.
MDM compliance wipeMDM automatically quarantines/wipes on root/jailbreak detection. Technician cannot override MDM policy. Escalate to MDM admin. Correct remediation is factory reset, not attempting to unroot.
Factory reset — when requiredConfirmed root/jailbreak; confirmed malware that cannot be fully removed; data leakage with unknown scope; device in boot loop. Always after evidence documentation. Restore from pre-compromise backup only.
iOS profile checkSettings → General → VPN & Device Management. Also check Certificate Trust Settings tab for unauthorized user-installed CA certificates (enables HTTPS interception). Both should have only IT-authorized or carrier entries.
Change passwords — clean deviceAlways change passwords from a DIFFERENT, known-clean device after any suspected compromise. A compromised device may have a keylogger — new passwords typed on it are immediately captured.

High-Probability Exam Scenarios

Scenario 1: An Android user downloaded a free cracked version of a popular paid game from a third-party website. Their phone now shows full-screen ads at random intervals on the home screen. What is the most likely cause, and what is the first step? → Adware installed via the unofficial APK. First step: uninstall the cracked game app. Also check Settings → Apps for any other recently installed apps from the same period. Run Google Play Protect. Educate the user that unofficial APKs commonly contain malware.

Scenario 2: A technician receives a notification from the MDM console that an employee's iPhone has failed the jailbreak detection check. What is the appropriate response? → Quarantine the device (MDM blocks corporate access automatically per policy). Notify the security team. The device must be factory reset — do not attempt to "unjailbreak." Investigate whether the jailbreak was intentional (policy violation) or caused by a drive-by exploit. Document in the incident management system.

Scenario 3: A user's Android phone is very slow and warm even when idle. Data usage is three times the normal amount this month. What is the most likely security cause? → Cryptomining malware. The combination of CPU-intensive background processing (causing warmth and slowness) with abnormal network activity (submitting mining results) is the classic cryptominer signature. Check Settings → Battery → Battery Usage and Settings → Network → Data Usage — the same suspicious app should appear elevated in both. Uninstall it; factory reset if it cannot be removed or if root access was used.

Scenario 4: A user visited a website on their iPhone that asked them to install a "carrier update" to improve performance. They installed it. Now all websites load a strange search engine and HTTPS sites show certificate warnings. What happened and how is it fixed? → The "carrier update" was a malicious configuration profile that installed a rogue CA certificate and proxy settings. Fix: Settings → General → VPN & Device Management → remove the malicious profile. Also check Certificate Trust Settings and remove any unauthorized user-installed CA certificate. Test connectivity after removal.

Scenario 5: A user reports they received a text message with a link to download their bank's "new security app." They installed it, and their bank account now shows unauthorized transactions. What type of attack is this, and what must be done? → Application spoofing — a fake banking app harvested their credentials. Immediate actions: (1) uninstall the fake app; (2) contact the bank to freeze accounts and dispute transactions; (3) change banking credentials from a clean device; (4) enable MFA; (5) factory reset the device. Remind: banking apps should always be installed by navigating to the bank's official website directly, never from a link in a text message.

Scenario 6: A technician is examining a user's Android phone and notices that "Install Unknown Apps" is enabled in the browser app's settings, developer mode is on, and USB debugging is enabled. The user says they don't remember enabling any of these. What is the most likely explanation? → The device was likely compromised — either through a social engineering attack that convinced the user to enable these settings, or through brief physical access by someone who enabled them. These settings together represent a significant attack surface: sideloading is enabled, and USB debugging allows arbitrary code execution via ADB. All three should be disabled immediately, the device audited for sideloaded apps, and the incident reported to the security team.
