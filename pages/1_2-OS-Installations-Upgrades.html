OVERVIEWIntroduction to OS Deployment

Installing and upgrading operating systems is one of the most fundamental and frequently performed tasks in a technician's career. Whether provisioning a brand-new workstation, migrating a user to a newer OS version, recovering a corrupted system, or deploying hundreds of machines across an enterprise, OS installation is at the center of it all. The A+ exam tests not just the mechanics of installation, but your ability to select the right method for the right scenario — and to understand the trade-offs, prerequisites, and risks involved in each approach.

This objective spans the entire OS deployment lifecycle: how a computer is told to start the installation process (boot methods), what kind of installation is appropriate (install type), how the storage device is structured to hold the OS (partitioning and formatting), what must be evaluated before upgrading (upgrade considerations), and how the OS continues to evolve and eventually reaches end-of-life (feature updates and product life cycle).

Core Concept — The Four Questions of OS Deployment

Every OS deployment scenario on the A+ exam can be approached with four questions: (1) How does the machine start the installation? — the boot method. (2) What kind of installation is this? — clean install, upgrade, image, repair, etc. (3) How is the storage device organized? — partitioning scheme and format. (4) What needs to be done before and after? — upgrade considerations, driver acquisition, and life cycle planning. Answering these four questions correctly for every scenario will cover the majority of 1.2 exam content.

SECTION 1Boot Methods

A boot method defines the source from which a computer loads the operating system installer — or an alternative OS environment — when it powers on. The system firmware (BIOS or UEFI) reads the boot order, a prioritized list of devices to attempt booting from, and starts with the highest-priority device that contains bootable media. Understanding boot methods is prerequisite knowledge for any OS installation task.

To change the boot order, a technician enters the system firmware setup (typically by pressing a key like F2, Del, F10, or Esc during POST) and modifies the boot sequence. Alternatively, most modern systems offer a one-time boot menu (often F12 or F11 at POST) that allows selecting a boot device for the current startup without permanently changing the boot order.

Multiboot

A multiboot (dual-boot or multi-boot) configuration installs two or more operating systems on the same physical computer, each residing on its own partition or drive. A boot manager — such as GRUB (GNU Grand Unified Bootloader) on Linux, Windows Boot Manager, or rEFInd on macOS — presents a menu at startup that lets the user select which OS to load.

Multiboot Installation Order

When installing Windows alongside Linux in a dual-boot configuration, always install Windows first. Windows' boot manager will overwrite any existing bootloader in the MBR or EFI system partition, destroying the ability to boot Linux. Install Windows → then install Linux → Linux's GRUB installer detects Windows and adds it to the boot menu automatically. Reversing this order requires manually repairing the Linux bootloader, which is a complex recovery procedure.

  • Disk space planning: Each OS requires its own dedicated partition with adequate free space — typically 40–80 GB minimum for a functional Windows installation, 20–30 GB for most Linux distributions; data partitions can be shared between OSes if formatted with a mutually supported filesystem (FAT32 or exFAT for cross-compatibility)
  • Partition requirements: On GPT/UEFI systems, a single shared EFI System Partition (ESP) can host boot entries for all installed operating systems; each OS installs its bootloader files into a subdirectory of the ESP
  • Time zone conflict: Windows stores the hardware clock as local time; Linux stores it as UTC. This causes the displayed clock to be wrong in one OS after using the other — resolved by configuring Linux to use local time (not recommended) or configuring Windows to use UTC (a registry edit)
  • Driver conflicts: Each OS installs its own drivers independently; drivers in one OS do not affect the other. However, fast startup / hibernation in Windows locks the NTFS filesystem — Linux cannot safely read/write a Windows partition that Windows has hibernated to. Always fully shut down Windows before booting Linux if you need to access Windows files from Linux
  • Use case on exam: A scenario asking how to run two operating systems on a single computer without virtualization → multiboot/dual-boot. A scenario asking about running them simultaneously → virtual machine

Exam Focus — Boot Methods

USB = most common for field installs. PXE/Network = enterprise mass deployment; requires DHCP + TFTP server. Internet-based = OS downloads from vendor servers during setup (macOS Recovery, Windows cloud download). Internal partition = manufacturer recovery partition (F11 at boot) or multiboot. Know that PXE uses the NIC's built-in boot ROM to receive an IP from DHCP and then downloads a boot image — no physical media required.

SECTION 2Types of Installations

The type of installation chosen for a given scenario depends on the state of the target system, the business requirements, the available infrastructure, and how much of the user's existing data and applications should be preserved. Selecting the wrong installation type wastes time, causes data loss, or results in a system that doesn't meet requirements. The A+ exam heavily scenarios these distinctions.

Clean Install

A clean install wipes the target partition completely and installs the operating system from scratch with no data, applications, or settings carried over from any previous OS. The target partition is reformatted before the OS files are written, destroying all prior content. The result is the freshest possible OS state — factory-default settings, no accumulated software cruft, no legacy driver conflicts.

When to Choose Clean Install
✅
New hardware with no existing OS or data to preserve
✅
Severely corrupted, malware-infected, or unbootable system where in-place repair isn't viable
✅
Repurposing a machine for a new user or department — starting with a known-good state
✅
Major version upgrade where a clean slate is preferred over accumulated OS state
✅
Moving to an entirely different OS (Windows → Linux; 32-bit → 64-bit OS)
Clean Install Trade-offs
⚠️
All data is destroyed — backup must be completed and verified before proceeding; no exceptions
⚠️
All applications must be reinstalled — requires software media, license keys, and time
⚠️
All settings lost — browser bookmarks, email profiles, application preferences, desktop customizations
⚠️
Driver installation required — especially on hardware without inbox drivers (specialized NICs, storage controllers)

Upgrade

An in-place upgrade installs a newer version of the operating system over the existing installation, preserving the user's files, installed applications, and settings in place. The upgrade installer migrates compatible data and software to the new OS version. This is the primary path for upgrading from Windows 10 to Windows 11, for example — users retain their desktop, documents, and most applications without reinstallation.

The key distinction: an upgrade requires an existing, functioning OS installation on the target partition. The installer runs from within the running OS (or from bootable media that detects the existing installation) and performs a migration rather than a fresh deployment.

  • Compatibility check first: Always run the OS vendor's compatibility checker before committing to an upgrade — Windows 11 requires TPM 2.0, Secure Boot, UEFI firmware, and minimum CPU from a supported list; incompatible hardware cannot be upgraded through standard means
  • Applications may break: Some applications are not compatible with the new OS version — especially 16-bit applications, old drivers, and software with DRM tied to OS-level APIs. Verify critical software compatibility before upgrading
  • Backup before upgrading: Even though the upgrade preserves data, upgrade processes can fail mid-way. A backup is non-negotiable before any upgrade — the rollback window (typically 10 days in Windows) may not be sufficient if significant data was created post-upgrade and pre-failure
  • Upgrade paths are version-specific: Not all upgrade paths are supported — Windows 7 Home cannot directly upgrade to Windows 10 Pro without additional licensing steps; Windows XP cannot directly upgrade to Windows 10 (clean install required)

Image Deployment

Image deployment copies a pre-configured OS image — a complete snapshot of a reference system's disk content — to multiple target machines simultaneously or in rapid succession. Instead of running through the OS installer and configuration process for each machine individually, a single master image contains the configured OS, drivers, applications, and settings and is deployed ("imaged") to each target.

Image Deployment Workflow
01
Build the reference machine. Install the OS cleanly on a reference (golden) machine. Install all required applications, drivers, Windows updates, and company-standard configurations and settings. This machine becomes the template for all deployed systems.
02
Generalize with Sysprep. Run sysprep /generalize /oobe /shutdown on the reference machine. Sysprep removes machine-specific information — the unique SID (Security Identifier), hardware-specific drivers, computer name, and activation state — making the image suitable for deployment on different hardware.
03
Capture the image. Boot the reference machine to WinPE (Windows Preinstallation Environment) and use DISM (Deployment Image Servicing and Management) or MDT (Microsoft Deployment Toolkit) to capture the disk content into a .wim file. Store the image on a deployment server.
04
Deploy to target machines. Boot target machines via PXE, USB, or network to the deployment server. The imaging tool applies the .wim image to each target's disk, replacing its contents. Each machine receives an identical copy of the reference image.
05
Specialize each machine. On first boot after imaging, Windows runs the OOBE (Out-of-Box Experience), assigns a new unique SID, accepts the license, and applies any machine-specific configuration from an answer file (unattend.xml). The machine joins the domain and pulls group policies automatically.

Sysprep and SID — Why It Matters

Every Windows installation has a Security Identifier (SID) — a unique value used to identify the machine and its local accounts in security contexts. If the same SID exists on multiple machines in the same domain (which would happen if you simply copied a disk image without Sysprep), authentication, group policy, and domain join operations break in unpredictable ways. Sysprep's /generalize flag deletes the SID so Windows generates a new unique one on each machine's first boot after imaging. Sysprep is mandatory before deploying an image to multiple machines.

Remote Network Installation

A remote network installation installs the OS on a target machine by booting via PXE and pulling the installation files from a server on the local network — without any physical media touching the target machine. The technician configures the deployment server once; all subsequent installs happen entirely over the network.

WDS (Windows Deployment Services) Microsoft's server role for network-based Windows deployment. WDS hosts boot images (WinPE) and install images (.wim files). Target machines PXE boot, receive a WinPE environment from WDS, then select and install a Windows image from the server. WDS is included with Windows Server.
MDT (Microsoft Deployment Toolkit) A free Microsoft toolkit that extends WDS with a full deployment workflow — task sequences, driver injection, application installation, domain join, and automated configuration. MDT creates a deployment share that WDS serves to PXE-booting clients. The industry standard for medium-to-large Windows deployments.
SCCM / MECM Microsoft Endpoint Configuration Manager (formerly SCCM — System Center Configuration Manager). Enterprise-grade deployment and management platform. Supports OS deployment, software distribution, patch management, compliance, and inventory — all from a central management console. Used in large enterprise environments managing thousands of machines.
TFTP Trivial File Transfer Protocol — the simple, lightweight protocol used to transfer the initial boot image from the PXE/DHCP server to the booting client NIC. TFTP uses UDP port 69 and has no authentication — it is used only within trusted LAN environments for PXE booting. HTTP/HTTPS is increasingly used for larger image transfers after initial PXE handshake.

Zero-Touch Deployment

Zero-touch deployment (ZTD) is a deployment model where new hardware is shipped directly from the vendor to the end user, and the device automatically configures itself to corporate standards without any IT technician handling the machine. The user unboxes the device, connects to the internet, and the device self-provisions — joining the organization's management platform, downloading applications, and applying policies — entirely automatically.

🏢
Windows Autopilot Microsoft's zero-touch deployment platform for Windows 10/11. The device manufacturer registers the hardware ID in Azure AD. When the user signs in with their corporate Azure AD credentials during OOBE, Autopilot automatically enrolls the device in Intune (MDM), downloads the corporate configuration profile, installs assigned apps, and joins the domain — no IT imaging required. The device arrives at the user's desk and the user sets it up themselves.
🍎
Apple DEP / ABM Apple Device Enrollment Program (now Apple Business Manager / ABM). Apple devices purchased through Apple or authorized resellers are registered in ABM. When activated, they automatically enroll in the organization's MDM (e.g., Jamf, Kandji, Mosyle) and receive their configuration profile. iPhones, iPads, and Macs are all supported.
📱
Android Zero-Touch Google's equivalent for Android enterprise devices. Devices are pre-registered with a zero-touch portal and automatically enroll in the organization's Android EMM (Enterprise Mobility Management) solution on first boot. Commonly used for corporate smartphone and tablet fleets.

Zero-Touch vs. Remote Network Installation

These are often confused. Remote network installation still requires IT to configure the machine on the network (PXE boot, select image) — a technician is involved. Zero-touch deployment requires zero IT physical interaction — the device self-configures completely from the internet with no imaging server or technician presence. Zero-touch is the evolution of network deployment enabled by cloud-based MDM platforms.

Recovery Partition

A recovery partition is a special, typically hidden partition on the system's internal storage that contains either a full factory OS image or recovery tools to reinstall the OS without external media. Recovery partitions are created by manufacturers (OEM recovery) or by Windows itself (Windows Recovery Environment — WinRE).

  • OEM Recovery Partition: Contains the complete factory image including all OEM applications, drivers, and branding. Accessed via a key press at boot (e.g., F11 on HP/Dell, or the Novo button on Lenovo). Restores the system to the exact state it was in when shipped. All user data and applications installed afterward are destroyed
  • Windows Recovery Environment (WinRE): Microsoft's built-in recovery environment, stored on a small hidden partition (~500 MB). WinRE provides Startup Repair, System Restore, command prompt access, and other repair tools. Accessed via Advanced Startup Options (Shift + Restart, or F8 during boot on older systems)
  • Critical limitation: A recovery partition on the same drive as the OS is destroyed if the drive fails — it provides no protection against hardware failure. External backup media (USB recovery drive, network backup) is necessary for true disaster recovery
  • Creating a Windows recovery drive: Windows includes a "Create a recovery drive" tool that copies the recovery partition to a USB drive, providing external bootable recovery media. Recommended for all systems before any major change

Repair Installation

A repair installation (also called an in-place repair or startup repair) reinstalls the OS system files over the existing installation without removing user data, applications, or most settings. It targets only the corrupted or missing OS components while leaving the rest of the system intact.

When Repair Installation Is Used

  • Corrupted system files — BSOD caused by corrupted Windows files that sfc /scannow and DISM couldn't repair
  • Failed update — Windows update partially applied and left the OS in a broken state
  • Missing boot files — BCD (Boot Configuration Data) or MBR corruption causing inability to boot
  • Startup Repair failure — automated startup repair ran and could not resolve the issue automatically
  • Preserves data — unlike clean install; user files and most apps remain intact

Repair Methods in Windows

  • sfc /scannow — System File Checker; scans and replaces corrupted protected OS files from cached copies; run first
  • DISM /Online /Cleanup-Image /RestoreHealth — repairs the Windows Component Store using Windows Update as source; run if SFC fails
  • Startup Repair — automated WinRE tool; fixes BCD, MBR, and boot file issues automatically
  • In-place upgrade repair — boot from Windows installation media, choose "Upgrade" on the existing OS; replaces system files without data loss
  • bootrec /fixmbr, /fixboot, /rebuildbcd — manual boot record repair from WinRE command prompt

Third-Party Drivers

The standard Windows installer includes a large library of inbox drivers for common hardware — USB controllers, network adapters, storage controllers, display adapters. However, specialized hardware (RAID controllers, specific NIC models, custom input devices) may require third-party drivers that must be obtained separately and injected into the installation process.

Missing Storage Controller Driver — The Critical Scenario

The most exam-critical third-party driver scenario: the Windows installer cannot detect the target storage drive because the storage controller driver is not included in the inbox driver set. This commonly occurs with enterprise RAID controllers (LSI, Adaptec, HPE SmartArray) and some NVMe controllers. Symptom: the Windows installer shows "No drives were found" on the drive selection screen. Fix: press "Load driver" on that screen and provide the driver from a USB drive. Always download storage controller drivers from the vendor's support site before beginning installation.

  • Driver injection during install: Windows installer's "Load driver" button (on the disk selection screen) allows loading a driver from external media during the installation process — the driver is added to the install environment so the storage device becomes visible
  • Driver injection into an image (offline): DISM can inject drivers into a .wim image before deployment — DISM /Add-Driver — so that deployed machines automatically have the necessary drivers without requiring post-deployment driver installation
  • Post-installation driver installation: For display, audio, NIC, and peripheral drivers that aren't needed for the install itself, drivers are installed after the OS is running — typically by running the vendor's installer package or via Device Manager → Update Driver → Browse for driver files
  • Driver signing: Windows requires drivers to be digitally signed for 64-bit installs. Unsigned drivers will trigger a warning or be blocked. Disable driver signature enforcement only temporarily in controlled environments — unsigned drivers may be malicious or unstable
  • Source of drivers: Always obtain drivers from the hardware manufacturer's official support site, not third-party driver aggregator sites. Third-party driver sites frequently bundle malware or provide incorrect drivers

SECTION 3Partitioning

Before an OS can be installed, the storage device must be divided into partitions — logical sections that the OS treats as separate, isolated storage areas. Each partition can be formatted independently with a specific filesystem. The structure of how partitions are organized and described on disk is defined by the partition table — and there are two competing standards: the legacy MBR and the modern GPT.

The choice of partition table is directly linked to the system firmware: BIOS systems use MBR; UEFI systems use GPT (though UEFI can boot MBR disks in Legacy/CSM mode for backward compatibility). Understanding both schemes, their limitations, and when to use each is essential A+ knowledge.

MBR — Master Boot Record

The Master Boot Record (MBR) is the legacy partitioning scheme that has been in use since 1983. The MBR is located in the very first 512-byte sector of the disk (sector 0) and contains two critical elements: the bootstrap code (a small program that initiates the boot process by locating the active partition's boot sector) and the partition table (a 64-byte structure describing up to 4 partition entries).

Primary Partitions MBR supports a maximum of 4 primary partitions per disk. Each primary partition can be independently bootable and formatted with its own filesystem. The 4-partition limit is a hard constraint of the 64-byte MBR partition table structure — each entry is exactly 16 bytes, and there are exactly 4 slots.
Extended + Logical Partitions To exceed the 4-partition limit, one primary partition slot can be designated as an extended partition — a container that holds multiple logical drives (also called logical partitions). The extended partition itself is not formatted or used directly; only the logical drives within it are. This allows effectively unlimited partitions on an MBR disk (though in practice more than 12–15 becomes unwieldy).
Active Partition One primary partition is marked as active — the flag in the MBR partition table entry that tells the BIOS bootstrap code which partition to read the Volume Boot Record from to continue the boot process. Only one primary partition can be active at a time on an MBR disk. In Windows, the System Reserved partition (containing BCD and boot files) is typically the active partition.
2 TB Disk Size Limit The MBR partition table uses 32-bit Logical Block Address (LBA) values to describe partition locations and sizes. With standard 512-byte sectors, 2³² sectors × 512 bytes = 2 TiB maximum disk size. Storage beyond 2 TiB on an MBR disk is inaccessible and invisible to the partition table. This is the primary limitation that drove adoption of GPT.
Single Point of Failure The entire MBR is stored in one 512-byte sector. If sector 0 becomes corrupted (physical damage, malware, failed write), the disk is unbootable and the partition table is lost. There is no backup copy of the MBR on the disk (unlike GPT, which maintains a backup). MBR corruption is repaired with bootrec /fixmbr from WinRE.

GPT — GUID Partition Table

The GUID Partition Table (GPT) is the modern partitioning scheme defined as part of the UEFI specification. GPT overcomes every significant limitation of MBR: it supports disks larger than 2 TiB, allows up to 128 partitions (in Windows; the spec allows far more), uses globally unique identifiers (GUIDs) to identify partitions and their types, and stores redundant copies of the partition table for data safety.

128 Partitions (Windows) GPT supports up to 128 partitions on a single disk in Windows (the partition table is 16,384 bytes with 128-byte entries). Unlike MBR, there is no distinction between primary, extended, and logical partitions — all GPT partitions are equivalent. No extended partition workaround is required.
9.4 ZB Disk Size Limit GPT uses 64-bit LBA addressing, supporting up to 2⁶⁴ sectors. With 512-byte sectors: 2⁶⁴ × 512 bytes = approximately 9.4 zettabytes — a limit that will not be reached with any foreseeable storage technology. GPT is effectively unlimited for practical purposes.
EFI System Partition (ESP) A mandatory GPT partition formatted with FAT32. The ESP stores the bootloader files for every OS installed on the system (Windows Boot Manager in \EFI\Microsoft\Boot\, GRUB in \EFI\ubuntu\, etc.). UEFI firmware reads the ESP at boot to find available bootloaders. The ESP must be present on every GPT disk that will boot a UEFI system — typically 100–550 MB in size.
GUID — Globally Unique Identifier Each GPT partition is assigned a 128-bit GUID that uniquely identifies it globally. Additionally, each partition has a partition type GUID that indicates its purpose (EFI System Partition, Microsoft Basic Data, Linux Data, Linux Swap, etc.). These GUIDs allow the OS and tools to identify partitions by their type and identity rather than just their position on disk.
Redundant Headers GPT stores the partition table header at the beginning of the disk (after the protective MBR) AND at the very end of the disk as a backup. If the primary header is corrupted, the backup at the end of the disk can be used for recovery. This redundancy is a major reliability improvement over MBR's single-point-of-failure design.
Protective MBR The first sector of a GPT disk contains a protective MBR that declares the entire disk as a single "GPT protective" partition. This prevents old MBR-only tools from seeing the GPT disk as blank and "helpfully" initializing it with an MBR partition table — which would destroy the GPT partition data. The protective MBR is not bootable from BIOS (it just contains error text) but allows old partitioning tools to at least recognize the disk is in use.

Exam Focus — MBR vs. GPT

MBR: 4 primary partitions max; 2 TiB max disk size; BIOS boot; no redundancy; sector 0 only. GPT: 128 partitions (Windows); 9.4 ZB max; UEFI boot; backup header at end of disk; requires EFI System Partition. A scenario with a 3 TB drive that Windows can't fully see → convert to GPT. A scenario asking about installing Windows 11 (requires UEFI + Secure Boot) → must use GPT. Converting between MBR and GPT on a disk with data requires third-party tools (MBR2GPT for Windows, gdisk for Linux) or a wipe.

SECTION 4Drive Format

After partitioning, each partition must be formatted with a filesystem before it can store data. Formatting creates the filesystem's data structures — the directory hierarchy, allocation tables, and metadata — that the OS uses to organize and locate files. Choosing the wrong filesystem for a partition's purpose causes compatibility issues, performance problems, or inability to install the OS entirely.

NTFS New Technology File System — the standard filesystem for Windows OS partitions, system drives, and internal data volumes. Supports file and folder permissions (ACLs), encryption (EFS), compression, journaling (crash recovery), file sizes up to 16 TiB, and volumes up to 256 TiB. Required for Windows installations — the Windows installer will not install to a non-NTFS partition. NTFS is not natively writable by macOS (macOS can read NTFS, but write support requires third-party drivers).
FAT32 File Allocation Table 32 — the filesystem required for the EFI System Partition (ESP) on GPT/UEFI systems. FAT32 is understood by UEFI firmware and all major operating systems, making it the universal choice for the ESP. Critical limitation: individual files cannot exceed 4 GiB in size. This makes FAT32 unsuitable for OS partitions (Windows install files can exceed 4 GB) and for general data storage with large media files. FAT32 is also used for USB drives intended for cross-platform compatibility.
exFAT Extended FAT — Microsoft's replacement for FAT32 for external drives and flash storage. Removes FAT32's 4 GiB file size limit (supports files up to 128 PiB theoretically) while maintaining broad cross-platform compatibility (supported natively on Windows, macOS, and modern Linux). The preferred format for large USB drives and SD cards used across different OSes. Not suitable for OS partitions.
ext4 Fourth Extended Filesystem — the standard Linux filesystem. Supports journaling, large files (up to 16 TiB per file), large volumes (up to 1 EiB), and Linux-native permissions and ownership. Linux OS partitions are formatted ext4 by default in most distributions. Not natively readable by Windows (requires third-party software like Ext2Fsd or WSL2).
APFS Apple File System — Apple's modern filesystem for macOS (10.13+), iOS, iPadOS, tvOS, and watchOS. Features copy-on-write semantics, native encryption, space sharing between volumes, fast directory sizing, and snapshots. All Mac internal drives use APFS. Not readable by Windows without third-party software.

Quick Format vs. Full Format

When formatting a partition, Windows offers two options. Quick format creates a new, empty filesystem structure and marks all clusters as available — it does not write zeros to the disk surface. Quick format is fast (seconds to minutes) but the old data remains on disk until overwritten — a forensic tool can recover it. Full format also writes zeros to every sector of the partition, verifying each sector is readable and permanently overwriting old data. Full format is much slower (hours on large drives) but ensures data is unrecoverable and bad sectors are detected. For security-sensitive data, use full format or dedicated disk wiping tools (DBAN, Windows Cipher).

SECTION 5Upgrade Considerations

OS upgrades carry inherent risk. A failed or poorly planned upgrade can result in data loss, broken applications, incompatible hardware, or a non-bootable system. Every upgrade scenario requires pre-upgrade evaluation across three dimensions: the data and settings that must be preserved, the software and driver compatibility with the target OS, and the hardware's ability to run the new OS.

Backup Files and User Preferences

The first and most critical upgrade consideration is data backup. Even in an in-place upgrade that is designed to preserve data, hardware failures, power interruptions, or unexpected compatibility issues can corrupt the filesystem or leave the system unbootable with data inaccessible. A verified backup before any upgrade is non-negotiable.

Pre-Upgrade Backup Checklist
01
User files and documents. Back up the user's Documents, Desktop, Downloads, Pictures, Videos, and Music folders. On corporate systems, verify that Documents and Desktop are redirected to a network share (folder redirection) — if so, files are already on the server and don't require manual backup. If not, copy all user profile folders to an external drive or network location.
02
Application data and settings. Many applications store settings outside the standard profile in AppData (hidden folder), ProgramData, or registry keys. Export browser bookmarks and passwords; export email client data (PST files for Outlook); note license keys for purchased applications (use tools like Belarc Advisor or NirSoft's ProduKey to harvest installed application keys). Export VPN profiles, network drive mappings, and printer configurations.
03
System state and configuration. Document or export: network adapter settings (IP, subnet, gateway, DNS — even if DHCP, note the current DHCP reservation); domain join information; local user accounts and groups; mapped network drives; printer installations; startup programs. These are typically rebuilt post-upgrade but documenting them speeds reconstruction if needed.
04
Verify the backup before upgrading. A backup that was not verified is not a backup. Spot-check critical files on the backup destination — open a few documents, confirm photos are readable, verify the backup destination has the expected amount of data. A backup that failed silently leaves you with no recovery path.
05
Consider a full system image. For complex systems with many applications or unique configurations, use Windows Backup, Macrium Reflect, or Clonezilla to create a full disk image before upgrading. A full image can restore the exact pre-upgrade state if the upgrade fails catastrophically, including all applications and settings — much faster than a full reinstall from the application list.

Application and Driver Support / Backward Compatibility

One of the most common post-upgrade complaints is that software that worked on the old OS no longer works on the new one. This is backward compatibility failure — the new OS does not provide the APIs, system calls, or environment that old software expects. Before upgrading, every critical application must be verified for compatibility with the target OS version.

  • Check the vendor's compatibility matrix: For business software (accounting systems, industry-specific applications, medical software), the vendor publishes a compatibility matrix specifying which OS versions are supported. Running unsupported software on a new OS may produce errors, data corruption, or silent failures — do not assume compatibility
  • 16-bit applications: 64-bit versions of Windows cannot run 16-bit (Win3.x) applications at all — there is no 16-bit subsystem in 64-bit Windows. Organizations with legacy 16-bit software must use virtualization (run a 32-bit Windows VM) or find a replacement application
  • 32-bit applications on 64-bit Windows: Most 32-bit applications run on 64-bit Windows via the WoW64 (Windows 32-bit on Windows 64-bit) compatibility layer with no issues. Some exceptions exist for applications that install kernel-mode components (security software, DRM systems)
  • Drivers: Device drivers are the most common compatibility failure point. A driver written for Windows 10 may or may not work on Windows 11. Drivers written for 32-bit Windows will not work on 64-bit Windows. Always confirm that current driver versions exist for all hardware — especially specialized peripherals, printers, scanners, and USB devices — before upgrading
  • Antivirus and security software: Security software frequently requires updates to support new OS versions. Upgrading the OS with old antivirus installed can break both — uninstall antivirus before the OS upgrade, upgrade the OS, then install the OS-compatible version of the antivirus

Hardware Compatibility

Not all hardware can run all OS versions. Each OS version defines minimum hardware requirements — processor architecture and generation, RAM, storage, and features like TPM and Secure Boot. Before upgrading, verify the hardware meets every requirement.

Windows 11 Hardware Requirements — Key Exam Points
CPU 64-bit processor from a supported CPU list — Intel 8th generation (Coffee Lake) or later, AMD Ryzen 2000 series or later. Older but fully functional processors (e.g., Intel Core i7-7700) are not on the supported list and cannot officially run Windows 11. This is the most controversial requirement — many capable machines were excluded.
TPM 2.0 Trusted Platform Module 2.0 is required. TPM is a cryptographic chip (either discrete hardware chip or firmware-based — fTPM) that stores encryption keys securely. Many enterprise systems have TPM but it may be disabled in UEFI settings. Enable it in UEFI before attempting Windows 11 upgrade. TPM 1.2 is not sufficient — must be 2.0.
Secure Boot UEFI Secure Boot must be enabled. Secure Boot verifies that boot software (bootloader, OS kernel, drivers) is signed by trusted keys, preventing malicious bootloaders (bootkits) from loading before the OS. Legacy BIOS systems cannot meet this requirement — they must use a UEFI-capable motherboard.
RAM and Storage Windows 11 requires a minimum of 4 GB RAM and 64 GB storage. While these are low bars, they represent a formal requirement that can disqualify aging thin clients and budget devices. The practical recommendation for a usable Windows 11 system is 8 GB RAM and 128 GB SSD.
PC Health Check Tool Microsoft provides the PC Health Check application (downloadable from Microsoft) that evaluates a machine's hardware against all Windows 11 requirements and reports specifically which requirements fail. This is the correct first step before any Windows 11 upgrade — run it on every candidate machine.

Exam Focus — Upgrade Considerations

Upgrade consideration scenarios always test three things: (1) Back up data first — always, before anything else, verify the backup. (2) Check application compatibility — especially 16-bit apps (won't run on 64-bit Windows at all) and specialty software with vendor-specific OS support. (3) Check hardware compatibility — Windows 11 specifically requires TPM 2.0, Secure Boot, UEFI, and a supported CPU. A question describing an upgrade failure because "the installer said the PC doesn't meet requirements" → check TPM, Secure Boot, and CPU generation.

SECTION 6Feature Updates and Product Life Cycle

Operating systems do not remain static after their initial release. They receive continuous updates — from security patches to entirely new features. Understanding how Windows (and other OSes) deliver updates, and how Microsoft's product life cycle policy determines how long a version receives support, is essential for planning, compliance, and risk management in any IT environment.

Windows Update Types

Security Updates (Patches) Targeted fixes for specific security vulnerabilities. Released on Patch Tuesday — the second Tuesday of every month. These are the highest-priority updates and must be deployed promptly in any environment. Unpatched security vulnerabilities are the primary attack vector for ransomware and other malware. May also be released as out-of-band emergency patches between Patch Tuesdays for critical zero-day vulnerabilities.
Quality Updates (Cumulative) Bug fixes, reliability improvements, and driver updates bundled as cumulative monthly packages. Windows 10/11 quality updates are cumulative — each monthly update contains all previous quality updates, so you only need to install the latest to be fully current. Released on Patch Tuesday. Installing a cumulative update effectively brings the system to the current quality baseline without needing to install months of individual patches.
Feature Updates Feature updates add significant new functionality and changes to Windows — new UI elements, added capabilities, changed behaviors, and sometimes removed features. In Windows 10, feature updates were released approximately twice yearly (e.g., 21H1, 21H2) and essentially represented a new minor version of Windows. In Windows 11, major feature updates are released annually. Feature updates are larger and take longer to install than quality updates. They also have their own support lifecycle.
Driver Updates Hardware driver updates distributed through Windows Update for common devices. While convenient, enterprise environments often disable automatic driver updates from Windows Update to prevent untested driver versions from being silently deployed — preferring to qualify and distribute drivers through WSUS or SCCM where they can be tested first.

Product Life Cycle

Microsoft defines a formal product life cycle for each Windows version and feature update, specifying exactly how long that version will receive security and quality updates. Running an OS beyond its end-of-support date is a significant security risk — vulnerabilities discovered after the end date will never be patched, leaving the system permanently exploitable by any attacker who knows the vulnerability.

General Availability OS version released to the public; Mainstream Support begins; all updates available
Mainstream Support Security + quality updates; feature requests accepted; typically 5 years from GA date
Extended Support Security updates only; no new features; bug fixes by exception; typically 5 more years
End of Life (EOL) No more updates of any kind; system permanently vulnerable; must migrate to supported OS
Mainstream Support The full-featured support phase. Microsoft provides security updates, quality updates, new feature additions, design change requests, and free warranty support during mainstream support. For most Windows client versions, mainstream support lasts 5 years from the general availability (GA) date. This is when the product is actively developed and improved.
Extended Support After mainstream support ends, the OS enters extended support for typically 5 additional years. During extended support, only security updates and critical reliability fixes are provided — no new features, no warranty support, and no free design change requests. For business-critical systems that cannot easily be migrated, extended support provides continued security patching. Organizations must pay for ESU (Extended Security Updates) in some cases.
End of Life (EOL) When both mainstream and extended support have concluded, the OS reaches End of Life. Microsoft publishes no more security patches, quality updates, or support for that version. Any vulnerability discovered after EOL will never be fixed. Systems running EOL operating systems are permanently exposed to all unpatched vulnerabilities. Windows XP reached EOL in April 2014; Windows 7 in January 2020; Windows 8.1 in January 2023.
Windows 10 Feature Update Lifecycle Each Windows 10 semi-annual feature update (e.g., 22H2) has its own end-of-support date — typically 18 months after release for Home/Pro, 30 months for Enterprise/Education. A machine running Windows 10 version 21H1 (released May 2021) stopped receiving updates in December 2022 even though Windows 10 itself continues to be supported. Keeping the OS on a supported feature update version is a separate maintenance task from keeping the OS itself supported.
Long-Term Servicing Channel (LTSC) Windows 10/11 LTSC (formerly LTSB) is a special enterprise variant that receives only security updates — no feature updates — for 5 or 10 years. LTSC versions are used in environments where stability is critical and frequent feature changes are disruptive: medical equipment, manufacturing systems, ATMs, point-of-sale terminals, and industrial control systems. LTSC is not available for Home or standard Pro licenses.

Running an EOL Operating System — Real Risk

The WannaCry ransomware outbreak in May 2017 exploited a Windows SMB vulnerability (EternalBlue/MS17-010). Microsoft had patched the vulnerability for supported Windows versions in March 2017. Organizations running Windows XP (which was EOL since 2014) received no patch and were devastated — hospitals went offline, manufacturers halted production, and over 230,000 systems in 150 countries were encrypted. The patch existed; the systems running EOL software couldn't receive it. This is not a theoretical risk.

Boot Method Selection Guide

  • Single machine, field repair — USB flash drive (most common)
  • Mass enterprise deployment — PXE / Network (WDS + MDT)
  • No media available, internet present — Internet-based (cloud download / Recovery)
  • Running two OSes on one machine — Multiboot (dual-boot)
  • Factory restore, no external media — Recovery partition (F11)
  • New devices, no IT touch — Zero-touch (Autopilot / ABM)

Installation Type Selection Guide

  • New hardware or malware-infected — Clean install
  • Keep apps + files, newer version — In-place upgrade
  • 100 machines same config — Image deployment (Sysprep + WDS)
  • Remote deploy, no media — Remote network installation (PXE)
  • Device ships to user, self-setups — Zero-touch deployment
  • Corrupted OS, keep data — Repair installation (sfc / DISM / upgrade)

MBR vs. GPT Decision

  • Drive > 2 TB → must use GPT
  • Windows 11 → must use GPT (UEFI required)
  • Legacy BIOS system → MBR only (no UEFI)
  • UEFI system → GPT (preferred) or MBR (via CSM)
  • Max partitions needed > 4 → GPT
  • Convert without data loss → MBR2GPT.exe (Windows in-place)

Filesystem Selection Guide

  • Windows OS partition → NTFS (required)
  • EFI System Partition → FAT32 (required by UEFI spec)
  • Cross-platform USB <4 GB files → FAT32
  • Cross-platform USB, large files → exFAT
  • Linux OS partition → ext4
  • macOS internal drive → APFS

Final Exam Reminders

PXE boot requires the NIC to have a boot ROM, and the network must have a DHCP server configured with PXE options pointing to a TFTP server. No physical media touches the machine. This is the network/remote installation method.

Always install Windows before Linux in a dual-boot setup. Windows overwrites the bootloader — Linux installs GRUB after and adds Windows as a menu entry.

Sysprep /generalize is mandatory before deploying an image to multiple machines. Without it, all machines share the same SID and domain operations break.

"No drives found" during Windows install → press Load Driver and supply the storage controller driver from a USB drive (most commonly a RAID or NVMe controller driver).

MBR limits: 4 primary partitions, 2 TiB max disk size. GPT: 128 partitions, effectively unlimited disk size, requires EFI System Partition (FAT32).

FAT32 maximum individual file size is 4 GiB — this is why it cannot be used for OS partitions (Windows install files exceed 4 GB) and why exFAT was created for large external drives.

Windows 11 requires: TPM 2.0 + Secure Boot + UEFI + supported CPU (8th gen Intel / Ryzen 2000+) + 4 GB RAM + 64 GB storage. A system missing any one of these cannot officially upgrade.

16-bit applications cannot run on 64-bit Windows — period. The WoW64 subsystem handles 32-bit apps but there is no 16-bit subsystem in 64-bit Windows. Answer: virtualize a 32-bit OS.

End of Life = no more security patches ever. Windows 7 EOL: January 2020. Windows 10 EOL: October 2025. Running EOL = permanently vulnerable to all subsequently discovered exploits.

LTSC = enterprise-only Windows variant; security patches only for 5–10 years; no feature updates; used for kiosks, ATMs, medical devices, and industrial systems.
