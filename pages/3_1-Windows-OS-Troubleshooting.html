3.1 CompTIA A+ Core 2 · Software Troubleshooting

Troubleshoot Common Windows OS Issues

BSOD & Stop Errors Boot Failures Performance Degradation Services & Applications System Instability

Windows OS troubleshooting is one of the highest-value skill sets for an A+ technician. Every symptom covered in this objective — from a blue screen to a slow profile load — maps to a finite set of root causes that can be isolated through systematic diagnosis. The technician's job is not to memorize magic fixes; it is to build a mental model of what each symptom means, which components it implicates, and how to gather evidence that distinguishes between the candidates.

This objective covers twelve distinct symptom categories. For each one, you need to know: what the symptom looks like, what causes it, which diagnostic tools reveal the cause, and what the remediation steps are. Scenarios on the exam will describe a symptom and ask you to identify the most appropriate next step, the most likely cause, or the correct tool — all of which require understanding the full diagnostic chain, not just isolated facts.

Troubleshooting Methodology Review

CompTIA's six-step troubleshooting methodology underlies every scenario in Domain 3: (1) Identify the problem; (2) Establish a theory of probable cause; (3) Test the theory; (4) Establish a plan of action; (5) Implement the solution; (6) Verify full functionality and document. Even when the exam doesn't explicitly reference these steps, structuring your thinking around them helps you arrive at the correct answer systematically rather than by guessing.

Section ABlue Screen of Death (BSOD)

The Blue Screen of Death (BSOD) — formally called a stop error or bug check — is Windows's response to a fatal kernel-mode error from which it cannot recover. When the kernel detects an inconsistent or unrecoverable state (a driver writing to protected memory, a hardware error that can't be handled, a deadlock in a critical system thread), it halts all execution, displays the stop screen, writes a memory dump file, and reboots. The BSOD is not a bug in itself — it is Windows's protective mechanism preventing the system from running in a corrupted state that could destroy data or spread the error.

:( Your PC ran into a problem and needs to restart.

STOP CODE: DRIVER_IRQL_NOT_LESS_OR_EQUAL
What failed: NetworkDriver.sys
For more information about this issue and possible fixes, visit https://www.windows.com/stopcode

Reading the stop code
The stop code (also called the bug check code) on a BSOD directly identifies what kernel assertion failed. Common stop codes and what they implicate: DRIVER_IRQL_NOT_LESS_OR_EQUAL — a driver attempted to access memory at an invalid interrupt request level, almost always a faulty or incompatible driver; PAGE_FAULT_IN_NONPAGED_AREA — a component tried to access a page of memory that was not present, caused by bad RAM, a buggy driver, or a corrupt page file; IRQL_NOT_LESS_OR_EQUAL — similar to driver_irql, often faulty drivers or RAM; CRITICAL_PROCESS_DIED — a critical Windows system process terminated unexpectedly, often malware, corrupt system files, or driver issues; MEMORY_MANAGEMENT — Windows memory manager detected an error, almost always RAM failure; WHEA_UNCORRECTABLE_ERROR — Windows Hardware Error Architecture caught a hardware error the CPU or chipset could not correct, often CPU, RAM, or motherboard failure; SYSTEM_SERVICE_EXCEPTION — a system service threw an exception, often driver or system file corruption.
The "What failed" field
Modern Windows BSODs display a "What failed" field identifying the specific driver or module that was executing when the error occurred. A filename ending in .sys is a kernel-mode driver. If it names a third-party driver (e.g., NetworkDriver.sys, nvlddmkm.sys for NVIDIA, atikmpag.sys for AMD), the fix is typically to update, roll back, or reinstall that driver. If it names a Windows system file (e.g., ntoskrnl.exe, hal.dll), the issue may be RAM failure, corrupt system files (run sfc /scannow), or a hardware fault.
Memory dump analysis
When a BSOD occurs, Windows writes a memory dump file to disk. Dump types: Small memory dump (Minidump) — saves only the stop code, loaded drivers, and the call stack of the thread that caused the crash (~256 KB, stored in C:\Windows\Minidump\); Kernel memory dump — saves kernel memory only, excludes user-mode process memory; Complete memory dump — saves all physical RAM, largest but most complete for deep analysis. Configure dump type at: System Properties → Advanced → Startup and Recovery → Write debugging information. Minidumps are the most practical for field diagnosis — analyze them with WinDbg or the lighter-weight WhoCrashed tool, which reads minidumps and reports the responsible driver in plain language.
Hardware causes
Faulty RAM is one of the most common BSOD causes. Run Windows Memory Diagnostic (mdsched.exe) — it tests RAM on next reboot with a pattern test. For more thorough testing, boot from a USB running MemTest86, which runs outside Windows and can test all RAM with multiple pass patterns. A single-pass failure indicates bad RAM. Remove and reseat RAM sticks, test each stick individually in a known-good slot to isolate the failing module. Overheating causes BSODs when CPU or GPU thermal protection triggers shutdown — monitor temperatures in BIOS/UEFI or with HWMonitor/Core Temp. Clean thermal paste and fans if temperatures are excessive.
Driver causes
Driver-caused BSODs are the most common category and also the most fixable. Key diagnostic question: did the BSOD start after a recent driver update? If yes: roll back the driver (Device Manager → right-click device → Properties → Driver tab → Roll Back Driver). If a new device was recently installed: update its driver to the latest version from the manufacturer's website, or remove the device to confirm it is the cause. Use Driver Verifier (verifier.exe) to stress-test all non-Microsoft drivers simultaneously — it forces crash dumps on the first driver misbehavior, making the offending driver easier to identify.
Systematic triage
Step 1 — Boot into Safe Mode (F8 or Shift+Restart → Troubleshoot → Advanced → Startup Settings). Safe Mode loads only minimal Microsoft-signed drivers. If the system is stable in Safe Mode, a third-party driver or startup program is causing the BSOD. Step 2 — Check Event Viewer (System and Application logs) for errors logged just before the crash. Step 3 — Read minidumps with WinDbg or WhoCrashed. Step 4 — If driver-related, update or roll back. Step 5 — Run sfc /scannow and DISM /Online /Cleanup-Image /RestoreHealth to repair corrupt system files. Step 6 — Test RAM with MemTest86 if no driver cause is found. Step 7 — If hardware failure is confirmed, replace the faulty component.

Most Tested BSOD Facts

The exam most commonly asks about: (1) which tool analyzes memory dump files → WinDbg (primary tool); (2) first step when BSOD started after a driver update → roll back the driver; (3) which mode to boot into to isolate driver vs. hardware → Safe Mode; (4) which tool tests RAM → Windows Memory Diagnostic (mdsched.exe) or MemTest86. Know that minidumps are stored in C:\Windows\Minidump\.

Section BBoot Issues and No OS Found

Boot failures are among the most alarming issues a user can encounter — a system that will not start appears completely broken. In reality, most boot failures have specific, diagnosable causes with established recovery paths. The two primary categories are pre-OS boot failures (the system cannot find or start Windows at all) and Windows startup failures (Windows begins to load but fails partway through). Understanding where in the boot sequence the failure occurs is the critical first diagnostic step.

The Windows Boot Sequence

Knowing the stages of the Windows boot process allows a technician to pinpoint where a failure is occurring based on how far the system progresses before failing:

1
POST (Power-On Self-Test) — The BIOS/UEFI firmware tests hardware (CPU, RAM, storage controllers). POST errors indicate hardware failures. The system beeps or displays error codes. If POST fails, Windows never starts. Fix: reseat hardware, check BIOS settings, replace failing component.
2
Boot device selection — BIOS/UEFI reads the boot order and attempts to load from the first bootable device. If no bootable device is found: "No bootable device," "Boot device not found," or "Operating system not found." Causes: wrong boot order, dead drive, disconnected SATA/NVMe cable, drive not detected in BIOS.
3
Bootloader — On UEFI systems: the EFI System Partition (ESP) contains bootmgfw.efi (Windows Boot Manager). On legacy BIOS systems: the Master Boot Record (MBR) contains the first-stage bootloader. Errors here: "Bootmgr is missing," "NTLDR is missing" (Windows XP), corrupt BCD. Fix: bootrec commands from Windows Recovery Environment (WinRE).
4
Windows Boot Manager / BCD — The Boot Configuration Data (BCD) store contains the list of OS boot entries. Boot Manager reads BCD and loads the selected entry. Corrupt BCD: "An error occurred while attempting to read the boot configuration data." Fix: bootrec /rebuildbcd, bcdedit.
5
Windows Loader (winload.exe) — Loads the Windows kernel (ntoskrnl.exe), Hardware Abstraction Layer (hal.dll), and boot-start drivers. Errors here often indicate corrupt system files. Fix: sfc /scannow, DISM /RestoreHealth, Startup Repair.
6
Kernel initialization — The kernel initializes, loads drivers, and starts system services. BSOD at this stage indicates driver or hardware issues. The system may cycle in a boot loop — starting, crashing, attempting to repair, and starting again.
7
User session (Winlogon / Explorer) — The login screen appears and the user logs in. explorer.exe starts the desktop shell. Failures here: slow profile load, black screen after login, desktop not loading. Often caused by corrupt user profiles, shell extensions, or startup programs.

"Bootmgr is missing"
The Windows Boot Manager file (bootmgfw.efi on UEFI, bootmgr on MBR systems) cannot be found or is corrupt. Most commonly caused by: an accidental deletion of the EFI System Partition contents, changing the active partition, or installing another OS that overwrote the bootloader. Fix: boot from Windows installation media → Repair your computer → Troubleshoot → Advanced Options → Command Prompt. Run bootrec /fixmbr (repairs the MBR), bootrec /fixboot (writes a new VBR), bootrec /rebuildbcd (scans for Windows installations and rebuilds BCD). On UEFI systems, also run bcdboot C:\Windows /s Z: /f UEFI (where Z: is the EFI partition).
"Operating system not found" / "No bootable device"
The firmware completed POST but cannot find any bootable storage. Causes: (1) Boot order is wrong — BIOS is looking at the wrong device (e.g., USB drive is first and it's not bootable); check and correct BIOS boot order. (2) Drive not detected — check that the drive appears in the BIOS/UEFI storage list; if absent, the drive may be failed, disconnected (reseat SATA/power cables), or the controller may need a driver. (3) Partition table damage — the drive is present but its MBR or GPT is corrupt; use bootrec /rebuildbcd or TestDisk to repair partition tables. (4) Dead drive — if the drive is absent from BIOS even after reseating, test in another system or with a USB adapter to confirm drive failure.
Startup Repair
Startup Repair is an automated Windows Recovery Environment tool that diagnoses and fixes common boot problems — corrupt BCD, missing boot files, incorrect active partition — without manual command-line intervention. Access: boot from Windows installation media → Repair your computer → Troubleshoot → Advanced Options → Startup Repair. Startup Repair is the correct first-line automated repair tool before resorting to manual bootrec commands. It can repair most MBR/BCD issues and some corrupt system files automatically. If Startup Repair fails to fix the issue, proceed to manual bootrec commands or System Restore.
Boot loop
A boot loop (also called an automatic repair loop) occurs when Windows begins to start, encounters a fatal error, and automatically restarts — repeatedly, never reaching the desktop. Windows may display "Preparing Automatic Repair" and cycle indefinitely. Break the loop: force-power-off during three consecutive boot attempts (Windows detects this pattern and boots into WinRE). Then use Startup Repair, System Restore, or — as a last resort — Reset This PC. A boot loop is commonly caused by a recent bad driver install, a failed Windows Update, or corrupt system files.
Corrupt BCD — manual fix
The Boot Configuration Data (BCD) store is a database that tells Boot Manager which OS entries exist and where to find them. Corruption can occur from power loss during an update, disk errors, or manual misconfiguration. From WinRE Command Prompt:

bootrec /scanos — scans all disks for Windows installations
bootrec /rebuildbcd — adds found installations to BCD
bcdedit /enum all — lists all current BCD entries

If these fail, completely rebuild BCD: delete and recreate the BCD store with bcdedit /export C:\BcdBackup, attrib C:\boot\bcd -h -r -s, ren C:\boot\bcd bcd.old, then bootrec /rebuildbcd.
Last Known Good Configuration
Windows maintains a Last Known Good Configuration — a snapshot of registry settings from the last successful boot. On Windows 10/11, this functionality has been largely superseded by System Restore and WinRE recovery options, but the concept remains exam-relevant. If a system change (driver install, registry edit) causes an unbootable state, System Restore (accessed from WinRE → Advanced Options → System Restore) rolls back to a previous restore point, which serves the same purpose as Last Known Good Configuration in practice.

Key bootrec commands available from the Windows Recovery Environment Command Prompt:

X:\Sources> bootrec /fixmbr The operation completed successfully. ← Writes a new MBR; does not touch partition table or BCD
X:\Sources> bootrec /fixboot The operation completed successfully. ← Writes a new Volume Boot Record to the active partition
X:\Sources> bootrec /scanos Total identified Windows installations: 1 ← Scans for Windows installs not in the current BCD
X:\Sources> bootrec /rebuildbcd Add installation to boot list? Yes/No/All: A ← Rebuilds BCD store; type A to add all found installations

Identify the bottleneck first
Performance degradation always has a bottleneck — one resource that is saturated while others have headroom. Open Task Manager → Performance tab to see real-time CPU, Memory, Disk, and Network utilization. The tab that is near 100% is the bottleneck. Each bottleneck type has different causes and solutions: CPU-bound (runaway processes, malware, insufficient cores), RAM-bound (too many applications open, memory leak, insufficient physical RAM), Disk-bound (fragmented HDD, failing drive, excessive paging, malware scanning), Network-bound (bandwidth saturation, misconfigured adapter). Identifying the bottleneck before attempting fixes prevents wasted effort.
High CPU utilization
Task Manager → Processes tab → sort by CPU descending to find the process consuming CPU. Common high-CPU culprits: antivirus scans (scheduled — reschedule to off-hours); Windows Update (TrustedInstaller, WaaS Medical processes — normal during update, concerning if persistent); malware (cryptomining malware pegs CPU continuously, often disguised as svchost.exe); runaway application (a bug in an application consuming CPU in an infinite loop — kill the process and report to vendor). Use Resource Monitor (resmon.exe) for deeper analysis — it shows per-process CPU usage broken down by thread and shows which processes are waiting on each other.
High memory utilization
Task Manager → Performance → Memory shows total used vs. available. Task Manager → Processes → sort by Memory to find the top consumers. Key indicators: low available RAM (under ~500 MB) — Windows begins paging heavily, causing disk thrash; growing memory use over time on one process — indicates a memory leak; applications that were using 200 MB after launch that now consume 2 GB. Memory leaks are bugs in applications — restart the application as a temporary fix; long-term fix requires an application update. Insufficient physical RAM for workload: upgrade RAM or reduce the number of running applications. Check commit charge in Task Manager's Memory performance page — if commit is near or exceeds the page file size, the system is under severe memory pressure.
High disk utilization
Task Manager → Performance → Disk or Processes → Disk column. A mechanical HDD at 100% disk utilization is a common Windows 10/11 performance problem. Causes: Windows Search indexing on an HDD — disable or reschedule; Superfetch/SysMain service preloading data on HDD — on SSD is fine, on slow HDD can cause thrash; Windows Update background downloads/installation; failing HDD — check SMART status with wmic diskdrive get status or CrystalDiskInfo; malware — scanning, exfiltrating, or encrypting files (ransomware causes extreme disk activity). For HDDs: run defrag /c /u to defragment (never defrag SSDs). For SSDs: run the optimizer which performs TRIM.
Startup programs
Excess startup programs extend boot time and keep consuming RAM and CPU after login. Task Manager → Startup tab shows all programs configured to launch at login with their startup impact (Low/Medium/High). Right-click and Disable any programs that are not needed at startup. Note: disabling a startup program does not uninstall it — it just prevents it from auto-launching. Programs can also be managed via msconfig (System Configuration) on older Windows versions. Keep security software (antivirus) and hardware utilities in startup; disable update managers, communication apps, and vendor bloatware that don't need to be running immediately after boot.
Malware as a cause
Malware is a consistent cause of degraded performance. Cryptomining malware specifically pegs CPU and GPU at maximum utilization, dramatically degrading system performance while mining cryptocurrency for the attacker. Ransomware causes extreme disk activity during the encryption phase. Signs malware is the cause: performance degraded suddenly (not gradually), CPU high but no identifiable legitimate process in Task Manager (malware may inject into svchost.exe or use process hollowing), antivirus was recently disabled or not running. Run a full scan with Windows Defender or an on-demand scanner (Malwarebytes) as part of any unexplained performance investigation.
Performance Monitor (perfmon)
Performance Monitor (perfmon.exe) provides detailed long-term performance data collection and analysis. Use it to: create Data Collector Sets that log resource usage over time (useful when performance degrades intermittently at specific times of day); view Performance counters for specific metrics (page faults/sec, disk queue length, available bytes); and diagnose issues that are hard to catch in the moment with Task Manager. The Reliability Monitor (perfmon /rel) shows a timeline of system events — application crashes, hardware errors, driver installs, Windows Updates — correlated on a calendar, making it easy to identify what changed when performance degraded.

Section DLow Memory Warnings

Low Memory Warnings
"Your computer is low on memory" — Windows cannot allocate sufficient virtual memory
RAM / Virtual Memory
Virtual memory and paging
Windows uses a virtual memory system that combines physical RAM with a page file (pagefile.sys) on disk to provide more addressable memory than physical RAM alone. When physical RAM is full, Windows moves least-recently-used memory pages to the page file on disk (paging out) and retrieves them later when needed (paging in). Excessive paging is called thrashing and severely degrades performance because disk access is orders of magnitude slower than RAM access. Windows generates a low memory warning when the combination of physical RAM and page file cannot satisfy all memory requests — both are nearly full.
Immediate actions
When a low memory warning appears: (1) Close any unnecessary applications immediately — this releases physical RAM and page file space. (2) If a specific process is consuming an abnormal amount of memory (memory leak), terminate it via Task Manager. (3) Restart the system if possible — this clears all in-memory state and resets leaked memory. These are temporary fixes; the root cause must be addressed to prevent recurrence.
Page file configuration
The page file is configured at: System Properties → Advanced → Performance Settings → Advanced → Virtual Memory → Change. Options: Automatically manage paging file size for all drives (default, recommended for most users — Windows dynamically adjusts); Custom size — manually set initial and maximum size; No paging file — only appropriate on systems with very large RAM (≥32 GB) for specific workloads. If low memory warnings occur with "System managed" selected, the drive may be too full to expand the page file — free up disk space. General guidance: page file initial size = 1× RAM, maximum = 3× RAM, though Windows manages this well automatically. Place the page file on the fastest available drive (SSD).
Root cause resolution
Persistent low memory warnings require addressing the root cause: Insufficient physical RAM — check whether the installed RAM meets the workload's requirements; if the system regularly pages under normal use, a RAM upgrade is the correct fix. Memory leak — identify the leaking application via Task Manager (memory usage grows continuously over time for one process); update or replace the application. Too many applications — adjust the user's workflow or upgrade RAM. 32-bit application on 64-bit OS — 32-bit processes are limited to 4 GB virtual address space (2 GB by default without the /LARGEADDRESSAWARE flag); a memory-intensive 32-bit application may hit this limit even on a system with ample RAM; solution is to use the 64-bit version of the application if available.

Section EFrequent Shutdowns

Frequent / Unexpected Shutdowns
System powers off without warning — usually thermal or power-related
Hardware Likely
Thermal shutdown (overheating)
The most common cause of sudden, unexpected shutdown (not a BSOD — the system just powers off) is thermal shutdown. Modern CPUs and GPUs include thermal protection — when temperature exceeds a threshold (typically 90–105°C for modern CPUs), the processor throttles performance and, if temperature continues to rise, the system shuts down immediately to prevent permanent hardware damage. Diagnose: monitor CPU and GPU temperatures using HWMonitor, Core Temp, or BIOS/UEFI hardware monitoring. Shutdowns occurring after the system warms up (15–30 minutes of use) are a strong thermal shutdown indicator. Fix: clean dust from vents and fans (compressed air), verify CPU cooler is properly seated and has good thermal paste contact, replace dried-out thermal paste, ensure case airflow is adequate (cable management, fan direction).
Power supply failure (PSU)
A failing or underpowered power supply unit (PSU) causes unexpected shutdowns when it cannot maintain stable output voltages under load. A PSU that works at idle may fail under the load of a gaming session or intensive computation when power draw peaks. Symptoms: shutdowns correlate with high system load (gaming, video encoding); system restarts immediately or takes a moment to restart. Diagnose: test voltage rails with a multimeter or PSU tester; if voltages sag under load, the PSU is failing. Fix: replace the PSU. Ensure the replacement PSU is rated for the system's actual power draw (CPU TDP + GPU TDP + component headroom). Failing capacitors in a PSU can also cause instability — inspect for bulging capacitors if the PSU is opened (safely).
Event log investigation
After an unexpected shutdown, Event Viewer → Windows Logs → System records the shutdown event. Event ID 41 (Kernel-Power) with reason code "The previous system shutdown at [time] on [date] was unexpected" indicates an unplanned power loss — the system was not properly shut down. This event is created on the next successful boot and is the primary way to confirm unexpected shutdown occurred vs. a user-initiated shutdown. Filter the System log for Critical and Error events before the Event ID 41 to look for preceding warnings (disk errors, driver failures, thermal events). Also check Event ID 6008 (EventLog) — "The previous system shutdown at [time] was unexpected."
Windows Update / software cause
Windows Update can force a restart after installing updates, which may appear as an unexpected shutdown to a user who did not notice the notification. Confirm via Event Viewer — planned restarts due to updates create a different event than thermal or power-loss shutdowns. Malware can also cause forced shutdowns — some malware shuts down the system to prevent forensic analysis or to complete an install that requires a reboot. If shutdowns are irregular and Event Viewer shows no hardware errors, run a malware scan.

Section FServices Not Starting

Services Not Starting
Windows services fail to start automatically or manually — causing feature failures
Services.mscEvent Viewer
Services architecture
Windows services are background processes that run independently of user login — antivirus, print spooler, Windows Update, network stack, audio, Windows Defender, and hundreds more. Services are managed through the Services console (services.msc), Task Manager → Services tab, or from the command line with sc and net start/net stop. Each service has a startup type: Automatic (starts at boot), Automatic (Delayed Start) (starts after boot completes — reduces boot impact), Manual (starts only when requested), Disabled (cannot be started). Services can also have dependencies — if a dependency service fails to start, all services that depend on it will also fail.
Diagnosing a failed service
Step 1: Open services.msc, find the service, note its current status and startup type. Right-click → Start — if it fails, a dialog shows the error code. Step 2: Open Event Viewer → Windows Logs → System and filter for the service name — the error event (usually Source: Service Control Manager) shows a specific error code and description explaining why the service failed to start. Common errors: Error 1068 — dependency service or group failed to start (start the dependency first); Error 1079 — account used to run the service differs from what the service requires; Error 2 — the system cannot find the file specified (service executable is missing or path is wrong — often malware removal deletes files, or an application uninstall leaves a broken service registration).
Service recovery options
Services include built-in failure recovery actions. Right-click a service → Properties → Recovery tab. Options for First, Second, and Subsequent failure: Take No Action, Restart the Service, Run a Program, Restart the Computer. For critical services, configure recovery to "Restart the Service" for the first two failures with a short delay, and "Restart the Computer" or "Run a Program" (to send an alert) for subsequent failures. This provides automatic recovery from transient failures without administrator intervention.
Common problem services
Print Spooler — if it crashes, all printing stops; fix by restarting the service (net stop spooler, net start spooler) and clearing the print queue (C:\Windows\System32\spool\PRINTERS\). Windows Audio — if it stops, no sound; often caused by a corrupt audio driver. DHCP Client — if stopped, the computer cannot obtain an IP address; run ipconfig /release and ipconfig /renew after restarting. Windows Defender Antivirus — if disabled or stopped, system is unprotected; malware often disables security services as a first step. Windows Update (wuauserv) — if stopped, updates cannot download or install.

Section GApplications Crashing

Applications Crashing
Applications terminate unexpectedly — hangs, crashes, or "has stopped working" errors
Event ViewerApp-Level
Application vs. system crash
Application crashes occur in user mode — the application terminates, but the OS and other programs continue running. This is fundamentally different from a BSOD (kernel-mode crash), which takes down the entire system. Windows catches user-mode crashes through Windows Error Reporting (WER), which generates crash dump files and can send diagnostic data to Microsoft (with user permission). Application crash dumps are stored in %LocalAppData%\CrashDumps\ (for applications that opt in) or can be collected manually with Task Manager or ProcDump.
Event Viewer diagnosis
Event Viewer → Windows Logs → Application logs every application crash as an Error event with Source Application Error. The event details include: the faulting application name and version, the faulting module (DLL or EXE that crashed inside), the exception code (e.g., 0xc0000005 = access violation), and the fault offset. The faulting module is often more diagnostic than the application name — if the faulting module is a Windows system DLL (e.g., ntdll.dll), the application has a heap corruption or use-after-free bug. If it is a third-party DLL (e.g., a codec or plugin), updating or removing that component often resolves the crash.
Common crash causes and fixes
Missing or corrupt runtime libraries — many applications require specific versions of Visual C++ Redistributables, .NET Framework, or DirectX. A "side-by-side configuration" error or a missing DLL message indicates a runtime dependency problem; install or repair the required runtime. Incompatibility — a 32-bit application may have compatibility issues on a 64-bit OS; try running in compatibility mode (right-click EXE → Properties → Compatibility). Corrupt application files — repair or reinstall the application. Conflicting software — another application or driver interfering; test by booting in Clean Boot state (msconfig → General → Selective Startup → disable startup items and services) to eliminate third-party software as a variable. Insufficient permissions — try running as administrator.
Hung application (not responding)
An application marked "Not Responding" in Task Manager has not processed a Windows message in more than 5 seconds — it is either deadlocked, waiting on a resource, or in an infinite loop. Actions: (1) Wait — some operations (large file processing, network timeouts) may resume on their own. (2) End Task (Task Manager → right-click → End Task) — sends a WM_CLOSE message; the application can handle this gracefully. (3) End Process Tree — force-terminates immediately without graceful shutdown; use when End Task does not respond. Note: force-terminating an application without saving may lose work.

Section HUSB Controller Resource Warnings

USB Controller Resource Warnings
"Not enough USB controller resources" — USB bandwidth or device count exceeded
USB Architecture
USB controller architecture
A USB host controller manages all USB devices connected to it. Most motherboards have several host controllers, each supporting a limited number of devices and a shared bandwidth pool. USB 2.0 controllers share 480 Mbps across all devices on the controller. USB 3.x controllers share bandwidth in the multi-gigabit range. Each controller also has a limited number of endpoints — data transfer pipes — that all connected devices share. The warning "Not enough USB controller resources" means the connected devices have collectively requested more endpoints than the controller can provide. This is separate from bandwidth — a device may fail to enumerate even on an otherwise idle controller if endpoint limits are exhausted.
Causes
Too many high-endpoint devices on one controller — audio interfaces, video capture cards, and some USB hubs each claim many endpoints. Connecting multiple such devices through one USB hub (which shares one host controller) can exhaust the endpoint pool. USB hub limitations — a powered USB hub expands port count but not host controller endpoints — all devices on the hub share the same endpoint pool as if directly connected to that controller port. Driver issues — outdated or corrupt USB controller drivers can misreport available resources. Power delivery — insufficient USB bus power for attached devices (particularly bus-powered hard drives) causes devices to fail to enumerate, which may generate resource-adjacent errors.
Resolution
(1) Distribute devices across controllers — connect high-endpoint devices to different USB ports on the back of the computer (which may be on different host controllers) rather than all through one hub. Check Device Manager → View → Devices by connection to see which USB controller each port is associated with. (2) Update USB controller drivers — Device Manager → right-click USB host controller → Update driver. (3) Uninstall/reinstall USB controllers — in Device Manager, uninstall all USB controllers (they will be rediscovered on reboot). (4) Add a PCIe USB expansion card — adds a new independent host controller with its own endpoint pool, directly addressing the root cause. (5) Reduce the number of connected USB devices — disconnect devices that are not in use.
Device Manager errors
USB resource problems appear in Device Manager as yellow warning triangles on the affected devices or on the USB controller itself. Common Device Manager error codes for USB: Code 10 — device cannot start (driver, power, or resource issue); Code 12 — not enough resources (IRQ, memory, or endpoint conflict); Code 43 — Windows stopped the device because it reported problems (also common for USB devices with power delivery issues). Right-click the problematic device → Properties → Device Status for the specific error message and code.

Section ISystem Instability

System Instability
Random errors, crashes, freezes, and unpredictable behavior across multiple components
Hardware SuspectSystematic Diagnosis
What "instability" means
System instability refers to a pattern of inconsistent, unpredictable failures — random BSODs with varying stop codes, application crashes that do not consistently reproduce, system freezes, file corruption, and errors that appear unrelated to each other. Unlike a consistent, reproducible error that points to a specific component, instability suggests a fundamental issue that manifests differently each time. The most common underlying causes: faulty RAM (random data corruption at the hardware level produces random symptoms), overheating (thermal throttling and shutdown under varying load), failing storage drive (inconsistent read/write errors produce varying symptoms depending on which file is affected), unstable CPU overclock (instability under varying workloads), and corrupt system files.
RAM testing
When system instability has no obvious software cause, test RAM first — it is the most common hardware cause of intermittent, seemingly random failures. Methods: Windows Memory Diagnostic (mdsched.exe) — schedule a test on next restart (basic test, usually sufficient for detecting bad RAM); MemTest86 — boot from USB, run at least one full pass (7 tests), ideally multiple passes; errors at any test indicate faulty RAM. Isolation: if multiple RAM sticks are installed, test with one stick at a time in the primary slot to identify which stick is bad. Try each stick in different slots to rule out a bad memory slot on the motherboard.
System File Checker and DISM
Corrupt system files cause instability by making Windows execute different code than expected. Two tools repair system files: System File Checker (SFC) — sfc /scannow — scans all protected Windows system files and replaces corrupt or missing ones from the Windows Component Store. Run from an elevated command prompt. Results in %windir%\Logs\CBS\CBS.log. DISM (Deployment Image Servicing and Management) — repairs the Component Store itself (which SFC uses as its source): DISM /Online /Cleanup-Image /ScanHealth (checks for corruption), DISM /Online /Cleanup-Image /RestoreHealth (repairs using Windows Update as the source). Run DISM before SFC if you suspect the Component Store itself is corrupt — SFC cannot fix a file if the Component Store's copy is also bad. After DISM completes, run SFC to repair any files that the now-healthy Component Store can fix.
Reliability Monitor
Reliability Monitor (perfmon /rel or search "reliability history") displays a timeline of system events — application failures, Windows failures, warnings, and informational events — on a visual calendar with a stability score from 1 to 10. This is invaluable for identifying: when instability began (correlating with a software installation or update), which components are most frequently failing, and whether instability is random or systematic. Each event entry can be expanded to show details. Look for patterns: if multiple unrelated applications crash on the same day, and that day coincides with a Windows Update, the update is the suspect. If failures cluster around hardware operations (hibernation, external drive connection), hardware is the suspect.
Driver Verifier
Driver Verifier (verifier.exe) is an advanced diagnostic tool that subjects drivers to additional stress tests during normal operation — monitoring for memory allocation errors, improper memory access, and rule violations. When Driver Verifier catches a misbehaving driver, it immediately causes a BSOD with a specific stop code (DRIVER_VERIFIER_DETECTED_VIOLATION) and the offending driver name. This makes intermittent driver bugs that are difficult to reproduce reliably turn into consistent, attributable crashes. Caution: Driver Verifier adds overhead and can make a system with driver issues unbootable — only use on a machine where you have WinRE access and can disable Verifier from the recovery environment if needed (verifier /reset).

Section JSlow Profile Load

Slow Profile Load
Login completes but the desktop takes an unusually long time to appear — profile loading delay
Profile / Group Policy
What happens during profile load
After the user authenticates at the login screen, Windows loads the user profile — a collection of user-specific settings, preferences, and data stored in C:\Users\[username]\. Profile loading involves: mounting the user's registry hive (NTUSER.DAT), applying Group Policy (user-side policies), mapping network drives (in domain environments), running logon scripts, and launching startup programs. Any of these steps can introduce delay. The system displays "Please wait…" during this process. If the delay is consistently long, one of these steps is the bottleneck.
Corrupt user profile
A corrupt user profile is a common cause of both slow profile load and post-login errors. Symptoms: login takes very long, the user is logged in with a "Temporary Profile" (desktop is empty, no familiar settings — Windows created a generic profile because the real one was inaccessible), or NTUSER.DAT fails to load. Diagnosis: Event Viewer → Application → filter for Source: "User Profile Service" — error events here identify profile load failures. Fix for temporary profile: log out and back in (sometimes transient); if persistent — log in with an administrator account, navigate to C:\Users\, check that the user's profile folder exists and is not locked. Create a new profile and migrate data, or use the Profile List registry key fix (HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows NT\CurrentVersion\ProfileList) to correct a misregistered profile.
Group Policy processing delay
In domain environments, Group Policy is applied during login — Windows must contact a domain controller to download and process user-side policies before the desktop appears. Slow profile load in a domain environment often indicates: slow or unreachable domain controller (the client waits to connect before timing out); large number of Group Policy Objects (GPOs) applying to the user; slow network drive mappings configured via GPO (particularly if a mapped network server is offline — Windows will wait for the connection timeout); logon scripts that run synchronously and take time to complete. Use gpresult /h report.html to generate a Group Policy results report showing which GPOs applied and how long each took.
Roaming profiles
Roaming profiles (a domain feature where the user's profile folder is stored on a network share and synchronized at login) can cause severe profile load delays if: the profile has grown very large (downloads, desktop files, AppData), the network share is slow, or the synchronization is downloading changes made on another workstation. Best practices for roaming profiles: use Folder Redirection (Documents, Desktop, AppData are redirected to network shares and accessed directly rather than synchronized on login), configure exclusions for large folders that don't need to roam (browser cache, temp files), and implement profile size limits via GPO.
Startup programs at login
Even after the desktop appears, the system may remain unresponsive for minutes while startup programs launch and initialize. Audit and reduce startup programs via Task Manager → Startup tab. In domain environments, GPO-assigned startup scripts and run-once actions also contribute. Excessive startup programs are identified in Reliability Monitor and Task Manager's Startup Impact column. Antivirus software scanning the profile on first load also contributes — if the scan impact is high, schedule it for non-login times.

Section KTime Drift

Time Drift
System clock loses accuracy — causing security failures, certificate errors, and auth issues
RTC / NTPAuth Impact
Why accurate time matters
A system clock that drifts from the correct time causes problems that range from annoying to security-critical. TLS/SSL certificates — certificates have validity periods; a clock that is hours or days off will cause all certificates to appear expired or not-yet-valid, breaking every HTTPS connection. Kerberos authentication (the default Windows domain authentication protocol) has a maximum clock skew of 5 minutes — if the client's clock differs from the domain controller by more than 5 minutes, Kerberos tickets are rejected and the user cannot log in to the domain. Timestamps in logs — incorrect timestamps make forensic log correlation impossible. Multi-factor authentication TOTP tokens (like Google Authenticator) are time-based — a drifted clock causes TOTP codes to not match.
Hardware cause: failing CMOS battery
The Real-Time Clock (RTC) on the motherboard is powered by a small coin-cell battery (typically CR2032) on the CMOS chip. This battery maintains the clock and BIOS/UEFI settings when the computer is powered off. When the CMOS battery dies: the system clock resets to a default date (often January 1, 2000 or 2004) every time the system loses power, BIOS/UEFI settings may reset to defaults (including boot order), and the system may display CMOS checksum errors on boot. Replace the CMOS battery (typically a CR2032 — check the motherboard manual). After replacement, set the correct time in BIOS/UEFI and let Windows NTP sync correct any remaining drift.
NTP synchronization
Windows continuously synchronizes the system clock with a Network Time Protocol (NTP) server to correct clock drift. Standalone workstations sync with time.windows.com by default. Domain-joined computers sync with the domain hierarchy: workstations sync to domain controllers → domain controllers sync to the PDC Emulator FSMO role holder → the PDC Emulator syncs with an external NTP source (internet NTP pool or a GPS-based stratum-1 server). Check sync status and manually trigger a sync from an elevated command prompt: w32tm /query /status (shows source and last sync time), w32tm /resync /force (forces immediate sync). If sync fails, check that the Windows Time service (w32tm) is running and that the NTP source is reachable.
Virtual machine time drift
Virtual machines are particularly susceptible to clock drift because the VM's clock is derived from the host and virtual CPU scheduling can cause it to fall behind during CPU contention. Hypervisors (Hyper-V, VMware, VirtualBox) include VM integration tools (Hyper-V Integration Services, VMware Tools, VirtualBox Guest Additions) that synchronize the guest VM's clock with the host. These tools should be installed and the time synchronization component enabled. For Hyper-V: the "Hyper-V Time Synchronization Service" in the guest's services list handles this. Ensure NTP is also configured in the guest for additional correction.

Section LWindows Diagnostic Tools Reference

Each symptom covered in this objective is most efficiently diagnosed with specific tools. The following grid maps key diagnostic tools to their purpose, how to launch them, and which symptoms they address.

Task Manager
Ctrl+Shift+Esc · taskmgr.exe
Real-time CPU, RAM, disk, network usage per process. Startup program management. Service start/stop. First-line tool for performance and hung application diagnosis.
Resource Monitor
resmon.exe · Task Manager → Performance → Open Resource Monitor
Deep per-process resource breakdown: CPU wait chain, disk read/write per file, network connections per process, memory committed vs. working set. Used when Task Manager identifies a symptom but not the exact cause.
Event Viewer
eventvwr.msc · Windows+X → Event Viewer
System, Application, and Security logs. Critical for: diagnosing BSODs (System log after crash), service failures (System log, Source: SCM), application crashes (Application log, Source: Application Error), shutdown events (Event ID 41, 6008).
Reliability Monitor
perfmon /rel · Search "reliability history"
Timeline of crashes, errors, and system changes correlated on a calendar. Invaluable for identifying when instability started and correlating it with software changes. Shows stability score trend.
WinDbg
Install from Microsoft Store or WDK
Analyzes BSOD memory dump files. Run !analyze -v on a minidump to identify the responsible driver and call stack. The definitive tool for BSOD root cause analysis.
Memory Diagnostic
mdsched.exe · Search "Windows Memory Diagnostic"
Schedules RAM test on next reboot. Two test modes: Standard (default) and Extended (more thorough). Results displayed after test completes and system boots. First-line RAM test tool.
SFC (System File Checker)
sfc /scannow (elevated cmd)
Scans and repairs corrupt Windows system files using the Component Store as the source. Run DISM /RestoreHealth first to ensure the Component Store itself is healthy. Results in CBS.log.
DISM
DISM /Online /Cleanup-Image /RestoreHealth (elevated cmd)
Repairs the Windows Component Store used by SFC. Uses Windows Update as a source for healthy files. Run before SFC when system instability or file corruption is suspected. Requires internet connectivity.
Device Manager
devmgmt.msc · Windows+X → Device Manager
Hardware driver management — update, roll back, disable, uninstall drivers. Yellow triangles indicate driver or resource errors. View → Show hidden devices reveals ghost devices. Used for USB resource warnings, BSOD driver identification, hardware conflicts.
Performance Monitor
perfmon.exe
Long-term performance data collection and analysis. Create Data Collector Sets for scheduled logging. Hundreds of performance counters available. Used for intermittent performance issues that are hard to catch in real time.
Services Console
services.msc
Start, stop, restart, and configure Windows services. View startup type, dependencies, recovery options, and service account. Essential for diagnosing services not starting.
System Configuration
msconfig.exe
Boot options (Safe Mode, minimal/network), startup program management, and service management for troubleshooting. Clean Boot = selective startup with all third-party services and startup items disabled — isolates software conflicts.
bootrec (WinRE)
From Windows Recovery Env. Command Prompt
Repairs MBR, Volume Boot Record, and BCD store. Essential for "Bootmgr is missing" and "Operating system not found" errors. Commands: /fixmbr, /fixboot, /scanos, /rebuildbcd.
w32tm (Windows Time)
w32tm /query /status · w32tm /resync
Check NTP sync status and force resync. Diagnose time drift issues. View current NTP source, last sync time, and stratum. Essential for Kerberos authentication failures caused by clock skew.

Section MScenario-Based Triage Decision Guide

Windows OS Troubleshooting — Symptom to First Action
BSOD began after installing a new graphics card driver
→
Roll back the driver. Device Manager → Display adapters → Properties → Driver → Roll Back Driver. Boot Safe Mode first if the system will not start normally. Safe Mode loads generic display driver, making rollback possible.
Random BSODs with varying stop codes, no recent changes
→
Test RAM first — run MemTest86 from bootable USB. Varying stop codes with no consistent driver name strongly suggest RAM failure. Also check temperatures (HWMonitor) for overheating as a secondary suspect.
"Bootmgr is missing" on startup
→
Boot from Windows installation media → Repair → Troubleshoot → Advanced → Startup Repair (first attempt). If that fails → Command Prompt → bootrec /fixmbr, bootrec /fixboot, bootrec /rebuildbcd.
System powers off suddenly after 20–30 minutes of use
→
Thermal shutdown suspected. Monitor CPU temperatures with HWMonitor during operation. Clean cooling system (compressed air, thermal paste replacement). Check Event Viewer for Kernel-Power Event ID 41. If clean and still occurring, test PSU under load.
Computer is very slow; CPU at 80–100% constantly
→
Open Task Manager → Processes tab, sort by CPU descending. Identify the process. If a familiar application: troubleshoot that specific app. If svchost.exe group is high: expand it in Resource Monitor to see which service. If no obvious cause: run a malware scan (cryptominer).
Disk usage at 100% in Task Manager on Windows 10 HDD
→
Identify the process causing disk I/O in Task Manager → Processes → Disk column. Common culprits: Windows Search indexing, SysMain (Superfetch), Windows Update. Check SMART status for drive health with CrystalDiskInfo. Consider SSD upgrade as a long-term fix.
"Your computer is low on memory" appears regularly
→
Check Task Manager → Memory to see if physical RAM is full. If one process grows continuously: memory leak → restart/update that application. If RAM is genuinely insufficient: increase page file size (temporary) or add physical RAM (permanent fix).
Print Spooler service keeps stopping; printing fails
→
Restart the service: net stop spooler, delete all files in C:\Windows\System32\spool\PRINTERS\, net start spooler. Set the service's Recovery properties to automatically restart on failure. Check Application Event log for WER error identifying the corrupt print job file.
USB audio interface stops working after adding a second USB device
→
USB controller resource exhaustion. Disconnect other USB devices and test. Connect high-bandwidth USB devices to different USB ports (potentially different host controllers). Add a PCIe USB expansion card for additional independent controller bandwidth. Check Device Manager for Code 12 on USB controller.
System instability — random crashes, errors, no consistent pattern
→
Systematic approach: (1) Check Reliability Monitor for pattern/correlation. (2) Run MemTest86. (3) Run sfc /scannow and DISM. (4) Check SMART for drive errors. (5) Check temperatures. (6) Run Driver Verifier if driver-caused BSODs are suspected.
Login screen appears but desktop takes 3+ minutes to load
→
Check Event Viewer → Application for User Profile Service errors (corrupt profile). In domain: check network drive mappings and GPO processing with gpresult /h. Reduce startup programs (Task Manager → Startup). Test with a new user account — if new account loads fast, the issue is profile-specific.
User cannot log into domain — "time difference" error
→
Kerberos clock skew. Check system clock — if wrong, correct it manually or run w32tm /resync /force. If clock resets after reboot: replace the CMOS battery (CR2032). In domain: ensure workstation is synchronizing with a domain controller, not an internet NTP source, to keep time aligned with the DC.
All websites show certificate errors on a specific workstation
→
First check system clock — an incorrect date causes all certificates to appear expired. Run w32tm /resync. If clock is correct: check for unauthorized proxy in browser settings. Check certmgr.msc → Trusted Root CAs for unexpected entries (rogue CA installed by malware).

High-Probability Exam Scenarios

Scenario 1: A user's Windows 10 PC displays a BSOD with stop code DRIVER_IRQL_NOT_LESS_OR_EQUAL every time they use the wireless adapter. The issue started after a Windows Update. What is the first step? → Roll back the wireless adapter driver in Device Manager. The stop code and the correlation with the update point directly to a driver issue; rolling back is the least destructive first step.

Scenario 2: A Windows workstation randomly BSODs with different stop codes each time. No recent hardware or software changes were made. What should the technician test first? → RAM. Random BSODs with varying stop codes, no consistent driver name, and no recent changes is the classic presentation of failing RAM. Use MemTest86 (boot from USB) for the most thorough test.

Scenario 3: After a power outage, a computer boots to "Operating system not found." The drive appears in BIOS. What tool and command repairs this? → Boot from Windows installation media → Repair → Command Prompt → run bootrec /fixmbr, bootrec /fixboot, and bootrec /rebuildbcd. The power outage likely corrupted the MBR or BCD.

Scenario 4: A workstation's CPU is consistently at 95% usage. The user has not changed anything. Task Manager shows the load is coming from an unfamiliar process. What should the technician suspect and do? → Suspect malware (particularly a cryptominer). Run a full malware scan with Windows Defender and Malwarebytes. Investigate the process name — look it up and use Resource Monitor to see its network connections.

Scenario 5: A domain-joined computer cannot log in with the error "There is a time difference between the client and the server." What is the fix? → Correct the system clock. Run w32tm /resync /force to force NTP sync with the domain controller. If the clock keeps resetting after reboot, replace the CMOS battery. Kerberos requires clocks within 5 minutes of the domain controller.

Scenario 6: A user's profile takes 5 minutes to load at login. Other users on the same machine load instantly. What should the technician check first? → The specific user's profile. Create a new test account — if it loads fast, the issue is the user's profile. Check Event Viewer Application log for User Profile Service errors. A corrupt NTUSER.DAT or temporary profile assignment is the most likely cause.

Scenario 7: A technician runs sfc /scannow and it reports it cannot fix all errors. What should be done next? → Run DISM /Online /Cleanup-Image /RestoreHealth to repair the Windows Component Store (which SFC uses as its source). After DISM completes, run sfc /scannow again. SFC cannot repair files if the Component Store's own copy is also corrupt — DISM repairs the store first.
