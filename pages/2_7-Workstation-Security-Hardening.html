OVERVIEWIntroduction — What Is Workstation Hardening?

Workstation hardening is the process of reducing a system's attack surface by configuring security settings, removing unnecessary features, enforcing access controls, and establishing protective policies that minimize the risk of successful attack. Hardening transforms a machine from its default, out-of-the-box configuration — which prioritizes compatibility and ease of use — into a configuration that prioritizes security without sacrificing necessary functionality.

A freshly installed Windows machine has many features enabled by default that represent unnecessary risk: AutoRun executes code from removable media, the Guest account provides unauthenticated access, default service accounts use well-known passwords, and services that are never used consume attack surface. Each configuration change in this objective removes one piece of that attack surface.

Scenario Verb — How This Is Tested

Objective 2.7 uses the "scenario" verb. Expect questions like: "A technician needs to prevent data from being accessible if a laptop is stolen — what should they configure?" (Data-at-rest encryption/BitLocker). "Users are leaving workstations logged in and unattended — what policy addresses this?" (Screen lock/timeout). "An attacker connected a USB drive and it auto-executed malware — what should have been configured?" (Disable AutoRun). Match the security problem described to the specific hardening technique.

SECTION 1Data-at-Rest Encryption

Data-at-rest encryption protects stored data by rendering it unreadable without the correct decryption key. Unlike data-in-transit encryption (TLS/HTTPS) that protects data moving over networks, data-at-rest encryption protects data stored on drives, USB devices, and other storage media — specifically against the threat of physical theft or unauthorized physical access to the storage medium itself.

The fundamental scenario: a laptop is stolen from a car. Without encryption, the thief can remove the drive, connect it to another machine as a secondary drive, and read every file on it — bypassing Windows login entirely, because Windows login only controls OS-level access. With full-disk encryption, the raw bytes on the drive are encrypted and unreadable without the key — the drive appears as garbage data to any machine other than the one with the correct key.

BitLocker (Full Volume)
—Scope: Entire volume (system drive or data drive)
—Editions: Pro, Enterprise only
—Cipher: AES 128-bit (default) or 256-bit
—Requires: TPM 1.2+ (default), or USB key
—Best for: Laptops, sensitive workstations; any machine that may be physically stolen
—Recovery: 48-digit recovery key — store in AD or secure location
BitLocker-To-Go (Removable)
—Scope: USB drives, external HDDs, SD cards
—Encrypt requires: Pro, Enterprise
—Read on any: Windows machine (password prompt)
—Auth: Password or smart card (no TPM)
—Best for: Protecting data on portable media; enforced by GP "deny write access to unencrypted removable drives"
EFS (Per-File)
—Scope: Individual files and folders on NTFS
—Editions: Pro, Enterprise only
—Auth: User certificate (auto-created)
—Other users: See "Access Denied" — even admins
—Warning: Lose EFS cert = permanent data loss; backup cert before deleting profile
—Gotcha: Copy to FAT32/exFAT silently decrypts

Exam Focus — Data-at-Rest Encryption Scenarios

"A laptop is stolen — how should the data have been protected?" → BitLocker (full-volume encryption). "A user needs to encrypt individual files so no other user — including admins — can read them?" → EFS. "USB drives must be encrypted before sensitive data can be written to them?" → BitLocker-To-Go + Group Policy enforcement. Remember: BitLocker and EFS are Pro/Enterprise only — Home editions get Device Encryption (a limited subset of BitLocker) instead.

SECTION 2Password Considerations

Passwords remain the most common authentication mechanism, and their strength is critical to preventing unauthorized access. Password policy defines the rules that govern what passwords users are allowed to set and how they must be managed over time. In Windows environments, password policies are configured via Group Policy (for domain environments) or Local Security Policy (secpol.msc) for standalone machines.

gpedit.msc → Computer Configuration → Windows Settings → Security Settings → Account Policies → Password Policy

Password Policy Elements

Password Policy Settings secpol.msc / gpedit.msc
Length
Minimum password length is the single most impactful password policy control. Each additional character exponentially increases the number of possible passwords an attacker must try in a brute-force attack. NIST SP 800-63B recommends a minimum of 8 characters for standard accounts, with 12–16+ recommended for privileged accounts. Modern guidance increasingly favors passphrases — a sequence of random words ("correct-horse-battery-staple") — over shorter complex passwords, because length contributes more to security than complexity alone. Group Policy setting: Minimum password length.
Character Types
Password complexity requirements specify which character categories must be present. Windows complexity requirements enforce that passwords must contain characters from at least three of four categories: uppercase letters (A–Z), lowercase letters (a–z), digits (0–9), and symbols (!@#$%^&*). A larger character set means more possible combinations per character position, increasing resistance to brute-force attacks. Group Policy setting: Password must meet complexity requirements (Enabled/Disabled).
Uniqueness
Enforce password history prevents users from recycling previous passwords. When a user changes their password, Windows stores a hash of the previous passwords and rejects any attempt to reuse them. Setting: remember the last 24 passwords (maximum). Without this control, users immediately change to a new password (satisfying a forced change policy) and then immediately change back to their favorite password. Combined with a Minimum password age setting (typically 1 day), this prevents the "change-and-change-back" workaround.
Complexity
Beyond the character type requirements, true password complexity means the password is not easily guessed by dictionary attack — it does not use real words, names, dates, or predictable patterns (Password1!, Summer2024@, company-name123). Modern guidance has shifted: a longer passphrase of random words is both more secure and more memorable than a shorter complex password. The password Tr0ub4dor&3 is technically complex but guessable and hard to remember. correct-horse-battery-staple is longer, more random, and far stronger.
Expiration
Maximum password age forces passwords to be changed after a defined period. Traditional guidance mandated 90-day expiration; NIST revised this in SP 800-63B to recommend against mandatory periodic expiration unless a compromise is suspected. The rationale: forced expiration leads users to make minor, predictable variations (Password1! → Password2!, Password3!) that attackers can predict, and the security benefit is minimal if the password was not compromised. Current best practice: require change only on suspected compromise; focus on complexity and MFA instead. Windows setting: Maximum password age (0 = never expires).

SECTION 3BIOS / UEFI Passwords

The BIOS or UEFI firmware initializes the machine's hardware and launches the OS bootloader before Windows loads. Without firmware-level protection, an attacker with physical access can boot from external media (bypassing Windows login entirely), change boot order to boot into a different OS, access or modify UEFI settings, or install a bootkit. BIOS/UEFI passwords provide pre-boot access control at the firmware level — the first security layer before any OS controls can apply.

BIOS / UEFI Password Types Firmware Level
Supervisor / Admin Password
Controls access to the BIOS/UEFI setup utility itself. Without this password, an unauthorized person can enter the firmware settings (typically by pressing F2, DEL, or F10 at POST) and change any firmware setting — including disabling Secure Boot, changing the boot order, disabling TPM, or clearing the TPM. Setting a Supervisor password requires this password to be entered before UEFI settings can be viewed or modified. This is the most important BIOS/UEFI password to set on corporate laptops.
User / Power-On Password
Controls whether the machine will boot at all. If a User/Power-On password is set, it must be entered every time the machine powers on — before any operating system begins loading. This prevents an unauthorized person from even starting the machine. More restrictive than a Supervisor password — the Supervisor password gates UEFI settings; the Power-On password gates the entire boot process. Most commonly used on kiosk machines and highly sensitive endpoints.
HDD / Drive Password
Some UEFI implementations support an HDD (ATA Security) password that is stored in the drive's firmware. When set, the drive itself requires a password to unlock — at a hardware level that is independent of the OS. Even if the drive is removed and connected to another machine, the drive firmware enforces the password requirement. Provides an additional layer of protection against drive removal, complementing BitLocker.
Resetting BIOS passwords
BIOS/UEFI passwords are typically stored in CMOS memory powered by a small battery on the motherboard. On desktop systems, removing the CMOS battery for 30 seconds (or shorting the CLEAR CMOS jumper) resets the UEFI settings including the password. On modern laptops, most manufacturers have eliminated this reset vector — the password is stored in EEPROM that is not cleared by battery removal. Resetting a forgotten UEFI password on a modern laptop typically requires manufacturer service. This makes the protection much more robust on laptops than on desktops.
Integration with Secure Boot
UEFI Secure Boot cryptographically verifies bootloader signatures. It should be enabled alongside a Supervisor password. A Supervisor password prevents an attacker from entering UEFI to disable Secure Boot. Secure Boot prevents an attacker from booting unauthorized OS images. Together they protect the pre-OS environment from both configuration tampering and unauthorized boot media.

SECTION 4End-User Best Practices

Technical security controls are only as effective as the behaviors of the people using secured systems. End-user best practices are the habits and procedures that users follow to avoid creating security gaps that technology alone cannot close. A properly hardened workstation can still be compromised if a user leaves it unlocked and unattended, writes passwords on sticky notes, or fails to physically secure a laptop.

End-User Security Best Practices
🔒
Use Screensaver Locks
Configure the screensaver to require a password on resume after a short idle period (5–10 minutes). An unattended, unlocked workstation exposes all data and system access to anyone who walks by. The screensaver lock is the last line of defense against physical access to an active session. Quick lock: Win + L locks immediately without waiting for the screensaver timer.
Settings → Personalization → Lock screen → Screen saver settings → On resume, display logon screen
🚪
Log Off When Not in Use
For longer absences (end of workday, leaving the office), users should fully log off rather than just locking the screen. Logging off ends all active sessions, disconnects network drives, clears session tokens, and ensures no background processes run under the user's credentials. On shared workstations (reception desks, lab computers, training rooms), logging off is critical — a lock screen can be bypassed if someone knows the PIN or has access to the reset process.
Start → User icon → Sign out  |  Ctrl + Alt + Del → Sign out
💼
Secure / Protect Critical Hardware
Laptops are particularly vulnerable to physical theft — they contain sensitive data and are easily carried away. Physical security measures: cable locks (Kensington locks) tether laptops to desks. Never leave laptops in visible locations in vehicles — store in trunks or take them inside. Do not leave equipment unattended in public spaces (coffee shops, airports) even briefly. Privacy screens prevent shoulder surfing in public. Enable full-disk encryption (BitLocker) so that theft of the physical hardware does not mean theft of the data.
🛡️
Secure PII and Passwords
Personally Identifiable Information (PII) — names, Social Security numbers, dates of birth, financial data, health records — must be handled according to security policy. Specific practices: never write passwords on sticky notes attached to monitors or keyboards. Never share passwords via email or instant messages. Lock file cabinets containing sensitive paper documents. Shred documents with PII before disposal. Do not discuss sensitive information in public spaces or on speakerphone in open offices. Clear the screen when leaving a workstation displaying sensitive data.
🔑
Use Password Managers
A password manager is an application that generates, stores, and retrieves strong, unique passwords for every account — secured by a single strong master password or biometric. Without a password manager, most users reuse passwords across multiple sites, meaning a breach of one site exposes all accounts sharing that password. Password manager benefits: unique strong password for every account (100+ characters, fully random); no need to memorize individual passwords; auto-fill prevents phishing on lookalike sites (the manager won't fill on a fake site); secure sharing of credentials in teams. Enterprise options: 1Password Business, Bitwarden Teams, LastPass Enterprise, KeePass (open source). Consumer options: Bitwarden (free tier is excellent), 1Password, Dashlane.
Never store passwords in browser if the browser profile is not secured with a master password

SECTION 5Account Management

Account management policies control how user accounts are created, configured, and maintained. These policies enforce security at the authentication layer — determining not just what users can access, but when they can access it, how many times they can fail to authenticate before being locked out, and when their access should automatically expire.

secpol.msc → Account Policies → Account Lockout Policy   |   gpedit.msc → Computer Configuration → Security Settings → Account Policies
Account Management Controls lusrmgr.msc / secpol.msc / gpedit.msc
Restrict User Permissions
Apply the principle of least privilege — users should have only the permissions required for their job function and nothing more. Standard users (members of the Users group) cannot install software to Program Files, modify system settings, or access other users' files. Restricting permissions limits the damage a compromised account or negligent user can cause. Audit permissions regularly and remove access that is no longer justified (access creep). Implemented via NTFS permissions, group membership, and Group Policy.
Restrict Login Times
Logon Hours restrict when a user account can authenticate to the system. Configured per-user in Active Directory Users and Computers (ADUC) → User properties → Account tab → Logon Hours. Example: a receptionist's account is permitted logon only Monday–Friday 7:00 AM–7:00 PM. Attempts to log in outside these hours are denied. For domain environments, when a user's logon hours expire while they are logged in, Windows can be configured to forcibly disconnect them. Effective for detecting unauthorized access (someone logging in at 3:00 AM with a compromised account).
Disable Guest Account
The Guest account is built into Windows and provides unauthenticated (or minimally authenticated) access to the machine. It is disabled by default in Windows 10 and 11 and should remain disabled. An enabled Guest account allows anyone who can physically reach the login screen to access the machine with a known account name and no password. In Active Directory environments, it should be confirmed disabled on every domain-joined machine via Group Policy. Check via: lusrmgr.msc → Users → Guest (should show down-arrow indicating disabled).
Use Failed Attempts Lockout
Account lockout policy automatically locks an account after a specified number of consecutive failed login attempts, preventing brute-force and automated credential-stuffing attacks. The three Group Policy settings: Account lockout threshold (how many failed attempts before lockout — typically 3–10), Account lockout duration (how long the account remains locked — typically 30–60 minutes, or 0 = admin must manually unlock), Reset account lockout counter after (how long before the failure count resets — typically same as or shorter than lockout duration). Lockout policies must balance security (preventing brute force) against availability (help desk burden from legitimate users being locked out).
Use Timeout / Screen Lock
An automatic screen lock timeout locks the workstation after a defined period of inactivity, even if the user forgot to manually lock it. This is a last-resort protection for unattended workstations. Configured via: Group Policy → Computer Configuration → Administrative Templates → Control Panel → Personalization → Screen saver timeout (set seconds) + Force a specific screen saver + Password protect the screen saver. Or: Settings → System → Power & sleep → Screen timeout. Recommended: 5–15 minutes for high-security environments; 15 minutes is a common baseline for standard office environments.
Apply Account Expiration Dates
Account expiration dates automatically disable an account on a specified date, without requiring manual action from IT. This is especially valuable for: contractors and temporary employees (set expiration to the last day of the contract); interns (set expiration to end of internship); project-based access (disable when project ends). Without expiration dates, temporary accounts frequently remain active long after the individual no longer needs access — a common audit finding and insider threat vector. Set in: ADUC → User → Account tab → Account expires.

SECTION 6Change Default Administrator's User Account / Password

Every Windows installation contains a built-in Administrator account — a well-known local account with a fixed, well-known username ("Administrator") that has full control of the machine. This account is a prime target for attackers: its username is known, making credential attacks require guessing only the password. The built-in Administrator account is disabled by default in Windows 10/11 but may be enabled in some deployment scenarios, requiring deliberate hardening.

Default Administrator Account Hardening High Priority
Built-in Admin account
The built-in Administrator account (SID ends in -500) is disabled by default in Windows 10/11 desktop editions. However, it may be enabled in: custom enterprise deployments, after the first account setup on a standalone machine, or via Group Policy. When enabled, it is the highest-privilege account on the system and is exempt from account lockout policy by default — meaning brute-force attacks against it cannot be stopped by lockout policies alone. This is why it must be specifically protected.
Rename the account
Change the display name of the Administrator account to something non-obvious. This forces attackers to guess both the username and password rather than just the password. Configured via: lusrmgr.msc → Users → right-click Administrator → Rename. Or via Group Policy: Computer Configuration → Windows Settings → Security Settings → Local Policies → Security Options → Accounts: Rename administrator account. The SID (-500) does not change, but the visible name does, complicating most automated attack tools.
Change the default password
If the Administrator account is enabled and in use, it must have a strong, unique password — never the default blank password, the company name, or a simple pattern. For local administrator accounts on domain-joined machines, use Microsoft LAPS (Local Administrator Password Solution) — a free tool that automatically sets a unique, random, rotating password for the local Administrator account on every domain-joined machine and stores it in Active Directory. This prevents lateral movement attacks (Pass-the-Hash) across machines that share a common local admin password.
Disable when not needed
The built-in Administrator account should be disabled if not specifically required. Day-to-day administrative tasks should use named administrator accounts (members of the Administrators group) with individual accountability and password enforcement, not the shared built-in account. To disable: lusrmgr.msc → right-click Administrator → Properties → check "Account is disabled." Or: elevated command prompt → net user Administrator /active:no.
Default device credentials
The principle extends to all devices with default credentials: routers (admin/admin, admin/password), network switches, printers, IP cameras, and IoT devices all ship with well-known default credentials that are published online. Every device with default credentials should have its password changed immediately upon deployment. Default credentials are the most commonly exploited vulnerability in SOHO and small enterprise environments — automated scanners find and exploit them within minutes of internet exposure.

Exam Focus — Default Credentials

The exam frequently presents a scenario where a device (router, printer, camera, or workstation) was compromised. A key question is: were default credentials changed? The answer to "how could this have been prevented" is almost always "change default administrator credentials." This applies to every managed device — not just Windows workstations.

SECTION 7Disable AutoRun

AutoRun (and its related feature AutoPlay) automatically executes or opens files from removable media (USB drives, optical discs, memory cards) when they are inserted into a computer. AutoRun reads an autorun.inf file on the media and executes the specified program without user interaction. This feature was a primary malware delivery mechanism for years — simply inserting an infected USB drive would automatically execute malware.

AutoRun / AutoPlay Configuration Disable in All Environments
AutoRun vs. AutoPlay
AutoRun — automatically executes a program specified in autorun.inf when removable media is inserted. The dangerous feature — it executes code without user confirmation. AutoPlay — displays a dialog asking what the user wants to do when media is inserted (open files, play music, run program, etc.). Safer than AutoRun but still represents an attack surface because the AutoPlay dialog can be manipulated to present malicious options that users click. Best practice: disable both. Minimum: disable AutoRun entirely; configure AutoPlay to take no action or open folder.
Why AutoRun is dangerous
The Conficker worm (2008–2009) — which infected over 9 million Windows machines — spread primarily via AutoRun on infected USB drives. A user simply needed to insert a drive; Conficker's autorun.inf would immediately execute its installer. Baiting attacks (intentionally leaving malware-infected USB drives in parking lots, lobbies, or near target facilities for curious employees to find and plug in) rely entirely on AutoRun or AutoPlay to execute the payload without the user's knowledge. Microsoft began disabling AutoRun by default in Windows 7, but older systems and some configurations still have it enabled.
Disable via Group Policy
gpedit.msc → Computer Configuration → Administrative Templates → Windows Components → AutoPlay Policies:
• Turn off AutoPlay → Enabled → All drives
• Set the default behavior for AutoRun → Enabled → Do not execute any autorun commands
• Disallow AutoPlay for non-volume devices → Enabled (prevents AutoRun on MTP/PTP devices)

Or via Registry (same effect):
C:\> reg add "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\Explorer" /v NoDriveTypeAutoRun /t REG_DWORD /d 0xFF /f — 0xFF disables AutoRun for all drive types
Disable via Settings (GUI)
Settings → Bluetooth & devices → AutoPlay → toggle off "Use AutoPlay for all media and devices." This disables the AutoPlay prompt entirely in Windows 10/11. While this prevents AutoPlay, it is not a Group Policy-enforced setting — a user or malware could re-enable it. For managed environments, Group Policy enforcement (above) is more robust because users cannot override it.

SECTION 8Disable Unused Services

Every service running on a Windows machine represents a potential attack surface — a piece of code executing with system or network privileges that could contain exploitable vulnerabilities. Services that are not needed for a machine's business function should be disabled. This principle is called attack surface reduction: the fewer services running, the fewer potential attack vectors exist.

Service Management services.msc / sc.exe
Services management console
Win + R → services.msc opens the Services console listing all Windows services with their current state (Running/Stopped) and startup type (Automatic, Automatic Delayed Start, Manual, Disabled). To disable a service: double-click the service → change Startup type to Disabled → Stop the service if running → Apply → OK. A "Disabled" service will not start automatically or when triggered by another service — it can only be started manually by an administrator.
Startup types
Automatic — starts during system boot without user action. Automatic (Delayed Start) — starts a few minutes after boot completes, reducing boot time impact. Manual — only starts when explicitly called by a user or another service. Disabled — cannot start by any means until explicitly re-enabled by an admin. For hardening: set unnecessary services to Disabled rather than just Manual — Manual services can still be triggered automatically by other components.
Services to consider disabling
Which services to disable depends on the machine's role. Common candidates in SOHO/workstation environments:

Remote Registry — allows remote modification of the Registry; rarely needed on workstations. Telnet — unencrypted remote access; deprecated; always disable. FTP (IIS-based) — only needed on file servers. SNMP (Simple Network Management Protocol) — network monitoring; not needed on workstations; has known vulnerabilities. Windows Remote Management (WinRM) — PowerShell remoting; disable if not needed. Print Spooler — on machines that never print (exploited by PrintNightmare CVE-2021-34527). SMBv1 (not a service directly but disable via: PowerShell → Set-SmbServerConfiguration -EnableSMB1Protocol $false).
Command-line management
C:\> sc query RemoteRegistry — check service status
C:\> sc stop RemoteRegistry — stop the running service
C:\> sc config RemoteRegistry start= disabled — set startup type to Disabled
C:\> Get-Service | Where-Object {$_.Status -eq "Running"} — PowerShell: list running services
Document before disabling
Before disabling any service, document its purpose and test the effect. Some services have unexpected dependencies — disabling one service may cause another to fail. Windows will warn about service dependencies when you attempt to disable a service that others depend on. Test changes in a non-production environment first. Maintain a change log so any unexpected behavior can be traced back to the service change. Services disabled for hardening should be documented in the machine's security baseline configuration.

CIS Benchmarks — A Hardening Reference

The Center for Internet Security (CIS) Benchmarks are free, consensus-based hardening guides for Windows (and many other platforms) that specify exactly which services to disable, which Group Policy settings to configure, and what values to set. They represent the industry standard for workstation hardening configurations. The CIS Benchmark for Windows 10 and Windows 11 covers hundreds of specific settings with justifications for each. For exam purposes, know the principles; for real-world implementation, reference the CIS Benchmarks.

High-Probability Exam Scenarios

Scenario 1: A laptop is stolen from a user's car — how should the data have been protected? → BitLocker (full-volume encryption).
Scenario 2: A user leaves their workstation unlocked and unattended — what two controls address this? → Screensaver lock (auto) + user training to use Win+L (manual).
Scenario 3: An infected USB drive auto-executed malware when inserted — what hardening was missing? → AutoRun was not disabled via Group Policy.
Scenario 4: An attacker is running a brute-force attack against a Windows login — what stops it? → Account lockout policy (locks after N failed attempts).
Scenario 5: Multiple machines were compromised by an attacker using a known local admin password that was the same on all machines → LAPS not deployed; all local admin accounts shared the same password.
Scenario 6: A contractor left 6 months ago but their account still exists and was used to access the system → Account expiration not configured; IAM deprovisioning failed.
Scenario 7: A user can access UEFI settings and changed the boot order to boot from USB, bypassing Windows login → BIOS/UEFI Supervisor password not set.
Scenario 8: A file is EFS-encrypted; the user's profile was deleted before the certificate was backed up — can the file be recovered? → Not without the EFS certificate or a pre-configured Data Recovery Agent (DRA).
