2.11 CompTIA A+ Core 2 · Domain 2: Security

Configure Relevant Security Settings in a Browser

Trusted Sources & Hashing Certificates & HTTPS Privacy Settings Extensions & Features

The web browser is the most-used application on any endpoint — and because of that, it is one of the most targeted attack surfaces in modern computing. Phishing campaigns, drive-by malware downloads, credential theft, malicious extensions, certificate spoofing, and tracking all exploit the browser as the primary vector. A browser with default settings and no security hardening is an invitation to compromise.

This objective covers the full scope of browser security from an IT support technician's perspective: safely sourcing and installing the browser itself, verifying software integrity with hashing, managing certificates and secure connections, configuring built-in privacy and security settings, and controlling the extension ecosystem. Every topic here corresponds to a real attack vector that a misconfigured browser enables.

Browser Scope on the Exam

The exam is browser-agnostic — it tests concepts that apply across Chrome, Firefox, Edge, and Safari rather than specific menu paths. When a scenario mentions a specific setting, focus on what the setting does and what risk it mitigates, not the exact navigation path in a particular browser. Where browser-specific paths are useful for practical application, they are noted, but the exam tests conceptual understanding.

Section ABrowser Download, Installation, and Patching

The security of a browser begins before it is even installed. Browsers obtained from unofficial sources may be trojanized — modified to include malware while appearing functionally identical to the legitimate browser. Verifying the integrity of downloaded software using cryptographic hashing is the technical control that ensures the file you downloaded is exactly what the publisher released.

Trusted vs. Untrusted Sources

Trusted vs. Untrusted Download Sources
Where you get the installer matters as much as what the installer does
Foundation
Trusted sources
A trusted source is a distribution channel directly controlled by the software publisher — the official vendor website, a platform's official app store, or an enterprise software deployment system. For browsers: google.com/chrome, mozilla.org/firefox, microsoft.com/edge. The publisher controls these channels, can sign the hosted files with their code-signing certificate, and bears accountability for the software distributed through them. Downloads from official vendor sites always arrive over HTTPS, protecting the download from interception and tampering in transit.
Untrusted sources
Untrusted sources include third-party download aggregators (CNET Download, Softonic, MajorGeeks), file-sharing sites, torrents, and any site that is not the official vendor. These sources introduce risk at two levels: (1) Bundled software — the installer wraps the legitimate browser with additional unwanted programs (toolbars, adware, PUPs); (2) Trojanized installers — the installer has been modified to include malware that runs during installation. Even if the resulting browser appears functional, a compromised installer may have silently backdoored the system. Additionally, search engine advertisements frequently impersonate official download pages — always navigate directly to the official URL rather than clicking sponsored search results.
Code signing
Legitimate browser installers from official vendors are code-signed — digitally signed with the publisher's private key using a certificate issued by a trusted Certificate Authority (CA). When Windows executes a code-signed installer, it displays the publisher's verified name in the UAC (User Account Control) prompt: "Verified publisher: Google LLC" vs. an unsigned installer that shows "Unknown publisher". An unknown publisher warning on a browser installer is a strong signal to stop and verify. Code signing does not guarantee software is benign (certificates can be stolen or issued fraudulently) but it establishes verified identity and means tampering is detectable.
Enterprise deployment
In managed enterprise environments, browsers are deployed through software management systems — SCCM/Intune, JAMF, Ansible, or similar tools — using pre-vetted, IT-approved installer packages. This prevents users from installing arbitrary browsers or browser versions from untrusted sources, and ensures all deployed browsers match the organization's security baseline. The IT department controls which browser versions are permitted and which extensions are allowed or blocked via Group Policy.

Hashing — Verifying Download Integrity

Cryptographic Hashing for File Verification
Mathematically confirming that a downloaded file has not been tampered with
Integrity Verification
What it verifies
File has not been modified since publisher released it
What it does NOT verify
That the publisher's copy was safe to begin with
Common algorithms
MD5, SHA-1 (legacy), SHA-256 (preferred)
How hashing works
A cryptographic hash function takes an input file of any size and produces a fixed-length output — the hash value (also called a digest, checksum, or fingerprint). The critical properties: (1) Deterministic — the same input always produces the same hash; (2) Avalanche effect — changing even one byte of the input produces a completely different hash; (3) One-way — you cannot reconstruct the file from its hash; (4) Collision resistant — it is computationally infeasible to produce two different files with the same hash (for strong algorithms). These properties make the hash a reliable fingerprint of the file's exact contents.
The verification workflow
Step 1: Navigate to the official vendor download page. Note the published hash value (SHA-256 is standard) for the specific installer version — this is the expected hash. Step 2: Download the installer file. Step 3: Compute the hash of the downloaded file using a trusted tool. Step 4: Compare the computed hash to the published expected hash. If they match exactly, the file is bit-for-bit identical to what the publisher published — no tampering occurred. If they do not match, the file was modified in transit or the source is not genuine — do not execute it.
Hashing tools
Windows (PowerShell): Get-FileHash filename.exe -Algorithm SHA256. Windows (CertUtil): certutil -hashfile filename.exe SHA256. Linux/macOS: sha256sum filename.tar.gz or shasum -a 256 filename.dmg. These built-in tools require no additional software and compute the SHA-256 hash of any file, ready for comparison against the published value.

The hash verification workflow looks like this in practice. Firefox publishes SHA-256 hashes for all release installers. After downloading the installer, a technician runs the hash tool and compares outputs:

Hash Algorithm Security Status

MD5 — 128-bit output. Cryptographically broken; collision attacks are practical. Still used for non-security purposes (detecting accidental corruption) but not suitable for security verification. SHA-1 — 160-bit output. Deprecated for security use; collision attacks have been demonstrated (SHAttered attack, 2017). SHA-256 (SHA-2 family) — 256-bit output. Current standard for file integrity verification; no practical attacks known. SHA-3 — structurally different from SHA-2; equally strong; less common in practice. The exam tests that SHA-256 is the current appropriate choice; MD5 and SHA-1 are legacy/broken.

Browser Patching

Browser Patching
Keeping the browser updated to eliminate known exploitable vulnerabilities
Ongoing Requirement
Why browsers need rapid patching
Browsers are extraordinarily complex software — Chrome is over 30 million lines of code. This complexity, combined with the browser's role executing untrusted content from arbitrary websites (JavaScript, WebAssembly, HTML/CSS rendering, media decoding), creates a large and continuously evolving attack surface. Browsers receive security updates far more frequently than most applications: Chrome releases major versions every four weeks and issues emergency security patches within days of critical vulnerability disclosure. An unpatched browser may have dozens of publicly known, actively exploited vulnerabilities. Zero-day exploits targeting browsers are among the most valuable assets in the exploit market — the browser is the primary path for drive-by malware delivery.
Auto-update behavior
Modern browsers (Chrome, Firefox, Edge) update automatically in the background and apply updates on next restart. Chrome checks for updates every few hours. Firefox updates silently by default. Edge updates through Windows Update in addition to its own updater. Auto-update should never be disabled. The most common reason browsers are found unpatched is that the user never restarts the browser — a browser that has been running for weeks without restart may be several versions behind even with auto-update enabled. Encourage users to restart the browser periodically, or configure forced restart after update via policy.
Checking the current version
Chrome: chrome://settings/help — shows current version and triggers an update check. Firefox: Menu → Help → About Firefox — checks for updates. Edge: edge://settings/help. These pages display the version number and whether the browser is up to date. In enterprise environments, browser versions can be centrally monitored and enforced through Group Policy or endpoint management tools.
EOL browsers
Browsers that are no longer supported by their vendor receive no security patches — Internet Explorer (retired June 2022) is the canonical example. Using an EOL browser exposes the system to all vulnerabilities discovered after the last patch, with no remediation path except replacement. Internet Explorer has hundreds of unpatched CVEs and should never be used for general browsing. Legacy web applications that require Internet Explorer should be accessed through IE Mode in Edge, which provides the IE rendering engine inside a supported, actively patched browser wrapper.

Section BExtensions and Plug-ins

Browser extensions run with elevated privileges inside the browser — they can read and modify web page content, intercept network requests, access cookies, manage downloads, and communicate with external servers. This power makes malicious extensions one of the most effective browser-based attack techniques. Extension security requires both understanding where extensions come from and actively managing what is installed.

Trusted and Untrusted Extension Sources

Extension Sources — Trusted vs. Untrusted
Where an extension comes from determines the baseline level of trust it deserves
High Risk Area
Official stores (trusted)
Browser vendors operate official extension stores — the Chrome Web Store, Firefox Add-Ons (AMO), and Microsoft Edge Add-ons. Extensions distributed through these stores are reviewed by the vendor before publication (though the depth of review varies) and are scanned for known malware signatures. If a malicious extension is discovered post-publication, the vendor can remotely remove it from all installations. Official store distribution also means extensions receive automatic updates through the browser's extension update mechanism. Prefer official store installations over sideloading.
Untrusted sources and sideloading
Sideloading is the installation of a browser extension from outside the official store — typically by loading an unpacked extension from a local directory, or installing a .crx file directly. Sideloaded extensions bypass store review entirely, receive no automatic security scanning, and are not subject to remote removal by the vendor if malicious. Social engineering attacks commonly direct users to sideload a malicious extension under a pretext ("install this extension to verify your account" or "required for accessing our company portal"). Chrome and Edge restrict sideloading by default — extensions installed outside the official store are disabled at next browser launch with a warning. This restriction can be overridden via enterprise policy.
Malicious extension behaviors
Malicious extensions have been documented performing: credential theft (reading form fields on banking and email sites), session hijacking (stealing authentication cookies), clipboard hijacking (replacing cryptocurrency wallet addresses copied to clipboard), ad injection (inserting advertisements into web pages), data exfiltration (sending browsing history and form data to external servers), and cryptomining (running cryptocurrency mining code in the background). Because extensions run persistently in the browser, they operate continuously — not just when you visit a specific site.
Extension permissions review
Every extension requests specific permissions during installation — "Read and change all your data on all websites," "Manage your downloads," "Read and change your browsing history." Review permissions before installing. A simple theme extension that requests "read all data on all websites" should raise immediate suspicion — that permission is far broader than a theme needs. The principle of least privilege applies: an extension should only have the permissions it legitimately needs for its stated function. Overly broad permission requests are a signal of malicious intent or poor security practice.
Supply chain attacks on extensions
Even a formerly trusted extension can become malicious through a supply chain attack. Extension developers may be targeted by attackers who compromise their Google account, update the extension with malicious code, and push the update to all users — who receive it automatically. Alternatively, popular extensions are sometimes purchased by companies that subsequently add malicious functionality. Regularly audit installed extensions and remove any that are no longer maintained, have changed ownership, or whose permissions have expanded unexpectedly after an update.

Section CPassword Managers

Password Managers
Secure storage and auto-fill for unique, complex credentials on every site
Best PracticeHigh Value
Why password managers matter
The single most common cause of account compromise is password reuse — using the same password across multiple sites. When one site suffers a data breach and credentials are exposed, attackers use automated credential stuffing attacks to try those credentials against hundreds of other sites. A password manager solves this by generating and storing a unique, random, complex password for every site — the user only needs to remember one strong master password. Password managers also resist phishing: they match stored credentials to the exact domain, and will not autofill a saved credential for paypa1.com when it was saved for paypal.com.
Built-in browser password managers
All major browsers include built-in password managers (Chrome Password Manager, Firefox Lockwise, Edge Password Manager, Safari Keychain). These are convenient and secure for basic use — credentials are encrypted and synced across devices via the browser account. Limitations: they are browser-specific (credentials saved in Chrome are not accessible in Firefox), they do not typically provide cross-application password management, and their security is tied to the security of the browser account (Google account, Microsoft account). For most users, the built-in manager is a significant improvement over no manager or reused passwords.
Dedicated password managers
Dedicated password managers (Bitwarden, 1Password, Dashlane, KeePass) operate as browser extensions and standalone applications. They provide: cross-browser access, cross-device sync, secure note storage, breach monitoring (alerting when a saved site appears in known breach databases), password health reports (identifying reused, weak, or old passwords), and in some cases TOTP (two-factor authentication) token generation. KeePass is an offline, open-source option for users with high security requirements or no trust in cloud-based storage.
Security considerations
Password managers introduce a single point of failure — the master password. If an attacker obtains the master password, they obtain all stored credentials. Mitigations: use a long, unique master password (a passphrase works well — never reuse it anywhere); enable multi-factor authentication on the password manager account; use a reputable manager with a published security model (zero-knowledge architecture means even the provider cannot read your passwords). The risk of a single strong master password protecting all credentials is far lower than the risk of weak, reused passwords across all sites.

Section DSecure Connections and Valid Certificates

HTTPS (HTTP over TLS) is the mechanism that encrypts communication between the browser and a web server, protecting credentials, session tokens, and data from interception. The TLS certificate — the digital credential presented by the web server — serves two distinct purposes: it enables the encryption, and it proves the server's identity. Understanding certificates is fundamental to recognizing and responding correctly to browser certificate warnings.

How Certificates Establish Trust

TLS Certificates and the Certificate Authority Chain
How the browser decides whether a certificate is valid and trustworthy
Core Concept
Certificate purpose
A TLS certificate is a digitally signed document that contains: the domain name(s) it is valid for, the public key of the server, the issuing Certificate Authority (CA), the validity period (not before / not after dates), and the CA's digital signature over all of this data. When your browser connects to https://example.com, the server presents its certificate. The browser performs several validations: (1) Is the domain in the certificate the domain I connected to? (2) Is the current date within the validity period? (3) Was the certificate signed by a CA that my browser trusts?
Certificate Authority chain
Certificates form a chain of trust. A Root CA is a CA whose certificate is embedded directly in the browser (or OS) as inherently trusted — browsers ship with ~130–170 trusted root CA certificates. Root CAs typically do not issue end-entity certificates directly; instead, they sign Intermediate CA certificates, which then sign end-entity (leaf) certificates for individual websites. The browser validates the full chain: website cert → intermediate CA cert → root CA cert → trusted root store. If any link in the chain is broken, expired, or untrusted, the browser displays a certificate warning.
Certificate types
Domain Validation (DV) — the CA verified that the applicant controls the domain. Fast to obtain (minutes), free via Let's Encrypt, provides encryption but no organizational identity information. The padlock appears the same as EV. Organization Validation (OV) — the CA also verified the legal existence and identity of the organization. Certificate details show the organization name. Extended Validation (EV) — the most rigorous CA verification process; requires extensive organizational documentation. Historically displayed the company name in the browser address bar in green (most browsers removed this display, but EV certificates still exist in the certificate details). DV is sufficient for encryption; OV/EV provide additional identity assurance.
Self-signed certificates
A self-signed certificate is signed by the same entity that issued it — it has no CA chain and is trusted by no browser's root store by default. Browsers display a certificate error when encountering self-signed certificates: "Your connection is not private" (Chrome), "Warning: Potential Security Risk Ahead" (Firefox). Self-signed certificates are commonly used on internal network devices (routers, NAS devices, development servers) where obtaining a CA-signed certificate is impractical. The browser warning does not mean the connection is being attacked — but it does mean you cannot verify the server's identity through a trusted CA chain. Proceed with explicit awareness.

A valid certificate from a trusted CA displays as follows in the browser's certificate viewer. This is what a technician sees when inspecting a certificate on a secured site:

Certificate Warnings — What They Mean

Certificate Error Types and Responses
Every certificate warning has a specific cause — understanding the cause drives the correct response
Troubleshooting
Name mismatch
The domain in the certificate does not match the domain you are connected to. Causes: connecting to an IP address directly instead of a hostname, a misconfigured server presenting the wrong certificate, a legitimate HTTPS interception proxy (corporate proxy or parental control appliance inserting its own certificate), or a man-in-the-middle (on-path) attack where traffic has been redirected to an attacker's server presenting a certificate for the wrong domain. If this appears unexpectedly on a site you access regularly, investigate before proceeding.
Expired certificate
The current date is outside the certificate's validity period. Most commonly caused by the website operator forgetting to renew the certificate before expiration — a mundane administrative failure. Let's Encrypt certificates expire every 90 days and require automated renewal; manual renewals are commonly missed. An expired certificate indicates the site is poorly maintained; the encryption is still present, but the identity assurance is compromised. Also check the client's system clock — a system clock set to the wrong date will cause all certificates to appear expired or not-yet-valid. Always rule out clock error before assuming a site certificate problem.
Untrusted CA
The certificate was signed by a CA not in the browser's trusted root store. Common causes: self-signed certificates on internal devices, internal enterprise CAs whose root certificate has not been distributed to client machines (common in enterprise environments — IT resolves by deploying the internal root CA certificate via Group Policy), or in rare cases, a certificate from a CA that has been removed from the trusted store due to CA malpractice. In enterprise environments, the internal CA's root certificate must be deployed to all endpoints before users can browse internal HTTPS sites without warnings.
Revoked certificate
The CA has invalidated the certificate before its expiration date — typically because the private key was compromised, the certificate was issued in error, or the organization's relationship with the CA was terminated. Browsers check revocation status via CRL (Certificate Revocation List) downloads or OCSP (Online Certificate Status Protocol) queries. A revoked certificate warning on a site you regularly use should be treated as a potential security incident — either the site's private key was compromised (meaning attackers may be impersonating the site) or there is a CA administration issue.

Never Click Through Certificate Warnings on Sensitive Sites

Browsers make certificate errors difficult to bypass deliberately — they require extra clicks and display prominent warnings for a reason. For internal lab devices, development servers, and known self-signed deployments, accepting a certificate warning after verifying the cause is acceptable. For any site that involves login credentials, financial information, or sensitive data, a certificate warning should stop all interaction until the cause is understood. An attacker executing a man-in-the-middle attack will present a certificate that triggers exactly this type of warning — clicking through is exactly what the attacker needs you to do.

Section EBrowser Security and Privacy Settings

Modern browsers include a comprehensive set of built-in security and privacy settings. Most users never examine these settings, leaving them at defaults that optimize for convenience rather than security. A technician hardening a workstation or troubleshooting a browser-related security issue must know what each setting does, when to change it, and what risk it addresses.

Pop-up Blocker

Pop-up Blocker
Preventing websites from opening new browser windows or tabs without user intent
Enable by Default
What it blocks
The pop-up blocker prevents websites from calling the JavaScript window.open() function to open new browser windows or tabs without the user clicking a link. Pop-ups have been used to: display scareware ("Your computer has a virus! Call 1-800-SCAM-NOW"), open fake login pages, initiate drive-by downloads, flood the browser with windows to make it unusable (pop-up storm), and redirect users to malicious sites. All major browsers enable pop-up blocking by default. Individual sites can be added to an allow list (Settings → Pop-ups and redirects → Allow) for legitimate use cases like online banking confirmation windows or ticketing systems.
Legitimate pop-ups
Some legitimate web applications use pop-up windows — payment processors opening a payment confirmation window, OAuth login flows, online meeting software. When the pop-up blocker prevents a legitimate pop-up, the browser typically displays a notification in the address bar ("Pop-up blocked"). The user or technician can then grant permission for that specific site. Never disable the pop-up blocker globally to fix a single-site issue — always add a site-specific exception.

Clearing Browsing Data and Cache

Clearing Browsing Data / Cache
Removing locally stored records of browsing activity and cached website resources
Privacy & Troubleshooting
Keyboard shortcut
Ctrl+Shift+Delete (Windows/Linux) · Cmd+Shift+Delete (Mac)
Scope options
Last hour / 24 hours / 7 days / All time
Who clears it
User, technician, or policy enforcement
Browsing history
The browser maintains a local record of every URL visited, including the page title, timestamp, and visit count. Clearing browsing history removes these records from the browser's local database. Privacy use cases: on a shared computer, clearing history prevents other users from seeing what sites were visited. Security use cases: browsing history is a target for malware that exfiltrates user activity; on compromised systems, browsing history may be collected for profiling. Note: clearing local browsing history does not remove records from the ISP, network router logs, or websites themselves.
Browser cache
The browser cache stores copies of web page resources — HTML, CSS, JavaScript, images, fonts — locally, so that when you revisit a page, the browser can load cached resources instead of re-downloading them. This improves performance. Clearing the cache forces the browser to re-download all resources on next visit. Troubleshooting use case: a cached version of a web page may cause display problems after the site has been updated — clearing the cache forces a fresh download. Security use case: cached content may include sensitive page content or authentication tokens that persist after logout; clearing cache on a shared computer removes this residual data.
Cookies and site data
Cookies are small text files stored by websites in the browser. Session cookies maintain login state — they are the reason you don't need to log in on every page of a website. Persistent cookies store preferences and track user behavior across visits and sites. Clearing cookies logs you out of all websites and removes stored preferences. Security relevance: session cookies are a high-value target for theft (session hijacking). If a user reports "I was still logged in to my account after logging out on a shared computer," the cause is a session cookie that wasn't cleared — clearing cookies and site data resolves this.
Saved passwords and autofill
The "Clear browsing data" dialog also includes options to clear saved passwords and autofill form data. In security incident response on a compromised machine, clearing saved passwords prevents exfiltration of credentials stored in the browser's password database. In enterprise environments, IT policy may prohibit storing passwords in the browser and require use of a dedicated password manager — clearing saved passwords enforces this posture.

Private Browsing Mode

Private / Incognito Browsing Mode
A session that does not persist browsing data locally after the window closes
Know the Limits
Chrome
Incognito (Ctrl+Shift+N)
Firefox
Private Window (Ctrl+Shift+P)
Edge
InPrivate (Ctrl+Shift+N)
What it DOES do
Private browsing mode opens a temporary session that: does not write to browsing history; does not save cookies or site data after the window closes (cookies exist during the session but are discarded at the end); does not use or save autofill data; does not use cached files from regular sessions (starts fresh); discards any downloads from the download list (though the files themselves remain on disk). This makes private mode useful for: one-time logins on shared computers, testing websites without cached/cookie state interfering, browsing as if logged out of all accounts, and accessing content you don't want in browsing history.
What it does NOT do
Critical exam point: private browsing does not provide anonymity on the network. The following can still see your browsing activity: your ISP (sees DNS queries and IP-level traffic); your employer's network/proxy (if browsing through corporate infrastructure); network administrators (who can see traffic at the router level); websites themselves (they see your IP address and can still track you via fingerprinting); any installed monitoring software on the local machine. Private browsing hides activity from other users of the same browser on the same device. It is a local privacy tool, not an anonymization tool.
Extensions in private mode
By default, browser extensions are not active in private/incognito windows — this is a security feature that prevents extensions from having access to private session data. Extensions must be individually granted permission to run in private mode (in extension settings). A malicious extension that cannot run in private mode cannot exfiltrate activity from private sessions. Conversely, if a user finds that a website works in private mode but not in regular mode, it often means a conflicting extension is the culprit — disabling extensions one by one in the regular window isolates the problem.

Exam Focus — What Private Browsing Does NOT Prevent

The exam will test whether you understand the limitations of private browsing. The correct answer to "what does private/incognito mode prevent?" is: it prevents local storage of browsing data (history, cookies, cache) on the device. It does not prevent the ISP, employer, or network administrator from seeing your traffic. It does not make you anonymous to websites. It does not hide activity from monitoring software on the machine. Common wrong answers: "prevents ISP tracking," "makes browsing anonymous," "protects against malware."

Sign-in and Browser Data Synchronization

Browser Sign-in and Data Sync
Cloud synchronization of bookmarks, history, passwords, and settings across devices
Privacy & Security Tradeoff
What sync does
When a user signs into their browser with a Google, Microsoft, Apple, or Firefox account and enables sync, the browser uploads selected data — bookmarks, browsing history, saved passwords, extensions, open tabs, settings — to the provider's cloud and synchronizes it across all signed-in devices. This is convenient but means sensitive data (particularly saved passwords) is stored in the cloud under the browser account's security posture. If the browser account is compromised (account takeover), the attacker gains access to all synced data including saved credentials.
Security implications
Account security is browser security. A Google account without 2FA that has sync enabled means a stolen password gives an attacker every password stored in Chrome. Best practices: enable multi-factor authentication on the browser account, use a strong unique password for the browser account, and review what is and isn't synced — it may not be necessary or appropriate to sync browsing history or to enable sync at all on shared or public computers. Some organizations disable browser sync entirely via policy to prevent corporate browsing data from being uploaded to personal accounts.
Shared/public computers
A user who signs into their browser account on a shared or public computer and forgets to sign out leaves their synced data — including saved passwords — accessible to the next user. On public computers, browsing in private/incognito mode prevents accidental sign-in persistence, and the computer should be using a fresh, non-persistent session if possible. IT policy for public-access computers should include browser profile isolation (each user gets a fresh, isolated browser profile) and session clearing on logout.

Ad Blockers

Ad Blockers
Filtering advertising content — and the security benefits beyond improved UX
Security Benefit
Beyond convenience
Ad blockers are commonly thought of as quality-of-life tools, but they provide genuine security benefits. Malvertising — malicious advertising — is a significant attack vector where attackers inject malicious code into legitimate advertising networks, causing it to run on high-traffic, reputable websites. Victims visiting a major news site or weather site can be silently served malware through the ad network without the site owner's knowledge or complicity. An ad blocker that prevents the advertising code from loading also prevents the malicious code embedded in it from executing.
Recommended tools
uBlock Origin is the most widely recommended ad blocker for security-conscious users — it is open source, lightweight, highly effective, has no "acceptable ads" program, and blocks tracking scripts in addition to display ads. AdBlock Plus is popular but operates an "acceptable ads" whitelist paid for by advertisers. Built-in ad blocking is available in Brave Browser and increasingly in other browsers. In enterprise environments, DNS-based ad and tracking blocking (Pi-hole, NextDNS, Cloudflare Gateway) can filter ads at the network level without requiring a browser extension on every device.
Tracking protection
Modern browsers include built-in tracking protection features (Firefox Enhanced Tracking Protection, Chrome Privacy Sandbox, Edge Tracking Prevention) that block third-party tracking cookies and fingerprinting scripts without requiring an extension. These provide a baseline of privacy protection. Extensions like uBlock Origin provide additional coverage. The combination of browser-native tracking protection and a reputable ad-blocking extension provides strong protection against ad-based malware and cross-site tracking.

Proxy Settings

Proxy Settings
Routing browser traffic through an intermediary server for inspection, filtering, or privacy
Enterprise & Privacy
How proxies work
A proxy server is an intermediary through which browser traffic is routed. When a proxy is configured, the browser does not connect directly to websites — it sends all requests to the proxy, which forwards them to the destination and returns the responses. The website sees the proxy's IP address, not the user's. Proxies can cache content (improving performance), filter requests (blocking prohibited sites), and inspect traffic (for malware scanning or DLP in enterprise environments).
Enterprise proxy configuration
In enterprise environments, an explicit proxy is commonly configured so that all web traffic passes through a corporate proxy/security appliance (e.g., Zscaler, Blue Coat, Forcepoint, Cisco Web Security). The proxy performs: URL filtering (blocking prohibited sites per policy), malware scanning (inspecting downloaded files), SSL inspection (decrypting HTTPS to inspect content — requires the corporate proxy's CA certificate to be trusted by all endpoints), and DLP scanning (preventing sensitive data from being uploaded externally). Proxy settings in enterprise environments are typically pushed via Group Policy or PAC (Proxy Auto-Configuration) files.
Malicious proxy hijacking
A common malware technique is to modify the browser's or OS's proxy settings to route all traffic through an attacker-controlled proxy — enabling man-in-the-middle interception of all browsing including HTTPS (if combined with a rogue CA certificate installation). Symptoms: sudden certificate warnings across all sites, traffic goes through an unexpected proxy, performance degrades. Check proxy settings as part of any malware investigation: Settings → System → Open your computer's proxy settings (Chrome/Edge), or about:config search for network.proxy (Firefox). Unexpected proxy settings indicate a potentially compromised system.
PAC files
A PAC (Proxy Auto-Configuration) file is a JavaScript file that the browser downloads and executes to determine which proxy (if any) to use for each URL. PAC files are powerful — they can route different domains through different proxies, or bypass the proxy for internal sites. Malware can modify the browser's PAC file URL to point to a malicious PAC file that routes all traffic through an attacker's proxy. Verify the PAC file URL in proxy settings points to a legitimate, expected location.

Secure DNS

Secure DNS (DoH / DoT)
Encrypting DNS queries to prevent interception and manipulation
Privacy Enhancement
The DNS privacy problem
Traditional DNS queries are sent in plaintext over UDP port 53. Every DNS query (every hostname you resolve, every website you visit) is visible to: your ISP, your network administrator, any on-path observer on the network, and any router your traffic passes through. Even with HTTPS, the DNS query for a site reveals the domain name before the encrypted connection is established. This enables ISPs to build browsing profiles and enables network-level censorship by poisoning DNS responses.
DNS over HTTPS (DoH)
DNS over HTTPS (DoH) encrypts DNS queries inside standard HTTPS traffic (port 443). Because it looks like normal HTTPS traffic, it is difficult for network operators to block, inspect, or modify. Browsers implementing DoH send DNS queries directly to a DoH-capable resolver (Cloudflare 1.1.1.1, Google 8.8.8.8, NextDNS) rather than to the OS-configured DNS server. This bypasses the ISP's resolver (and its potential logging and manipulation) but means DNS queries go to the configured DoH provider instead. Enable in Chrome at chrome://settings/security → Use secure DNS; Firefox enables it by default for US users.
Enterprise consideration
DoH can conflict with enterprise environments that rely on the corporate DNS resolver for internal hostname resolution and split-horizon DNS. If DoH is configured to use a public resolver (Cloudflare, Google), the browser will not be able to resolve internal hostnames that only exist in the corporate DNS. Enterprises often disable DoH via policy to ensure all DNS queries go through the corporate resolver, which provides both internal name resolution and security filtering. A network-level DoH resolver that handles both internal and filtered queries is the enterprise-friendly solution.
DNS over TLS (DoT)
DNS over TLS (DoT) encrypts DNS queries using TLS over port 853. Unlike DoH (which blends into HTTPS traffic on port 443), DoT uses a dedicated port — making it easier for network operators to identify, and either allow or block explicitly. DoT is more commonly used at the OS or router level rather than within the browser itself; DoH is the browser-native implementation. Both provide equivalent privacy benefits — encrypted, tamper-resistant DNS.

Section FBrowser Feature Management

Modern browsers include numerous features that can be individually enabled or disabled — both through user-facing settings and through enterprise policy. Feature management is about reducing attack surface: features that are not needed should not be running, and features that present risk should be controlled through policy rather than left to individual user discretion.

Managing Plug-ins, Extensions, and Features

JavaScript Selective Control
Enabled by default and required for most modern websites. Can be disabled globally in Settings → Privacy and security → Site settings → JavaScript for maximum restriction, with site-specific exceptions. NoScript (Firefox) and uBlock Origin's advanced mode allow granular per-site JavaScript control — blocking scripts from all domains except explicitly allowed ones.
WebRTC Privacy Risk
Web Real-Time Communication — used for voice/video calls in browsers. A known privacy leak: WebRTC can expose your real IP address even when using a VPN (WebRTC IP leak). Users relying on VPN for IP privacy should use a browser extension (WebRTC Control) or browser with WebRTC disabled. Firefox allows disabling via about:config: set media.peerconnection.enabled to false.
Cookies — Third-Party Disable
Third-party cookies are the primary mechanism for cross-site tracking. Blocking third-party cookies (Settings → Privacy and security → Cookies) prevents advertising networks from building profiles of your browsing across sites. Firefox blocks third-party cookies by default. Chrome is phasing out third-party cookies. Some legacy web applications require them for SSO — add site-specific exceptions only when needed.
Notifications Block by Default
Browser notifications are a spam and phishing vector — users are social-engineered into granting notification permissions to malicious sites, which then push scareware or phishing messages. Set notifications permission to "Don't allow sites to send notifications" (Settings → Privacy and security → Notifications). Grant notification permissions only to specific, trusted sites that legitimately use them.
Geolocation Prompt Only
Allow only on user prompt (the default). Never globally allow geolocation access — sites should request it only when needed and you decide per-site whether to grant it. Revoke permissions for sites you no longer actively use: Settings → Privacy and security → Site settings → Location → Review existing permissions.
Camera and Microphone Prompt Only
Always prompt (default behavior is correct). Audit which sites have been granted persistent camera or microphone access: Settings → Privacy and security → Site settings. Revoke access for any site that no longer needs it. Legitimate video conferencing sites (Zoom web, Meet) will re-request permission when needed.
Flash (NPAPI plug-ins) Disable/Remove
Adobe Flash reached end-of-life on December 31, 2020. All major browsers have removed Flash support. Flash was one of the most exploited browser plug-ins in history. If somehow still present (extremely legacy system), it should be uninstalled immediately. NPAPI plug-ins generally have been removed from modern Chrome; Firefox has also removed NPAPI support except for a few exceptions.
Download Behavior Prompt Location
Configure the browser to prompt for save location on every download rather than auto-saving to the Downloads folder. This prevents drive-by downloads from silently saving files that a user might later accidentally execute. Some browsers also offer "Ask where to save each file before downloading" (Chrome: Settings → Downloads). Enabling Safe Browsing (or equivalent) adds malware scanning of downloads.

Enterprise Browser Management via Group Policy

Enterprise Policy-Based Browser Management
Centrally enforcing browser settings across all managed endpoints
Enterprise
What can be policy-managed
Chrome, Edge, and Firefox all provide Group Policy Administrative Templates (ADMX files) that allow IT administrators to enforce browser settings via Active Directory Group Policy or Intune/MDM. Policy-enforceable settings include: allowed/blocked extensions (whitelist only approved extensions, prevent installation of others), forced installation of extensions (deploy a security extension to all endpoints without user action), disabled features (prevent users from changing security settings like safe browsing, certificate verification), homepage and search engine, proxy settings, password manager (enable or force disable in favor of enterprise password manager), and browser sync behavior (disable sync with personal accounts).
Extension allowlisting
Extension allowlisting is one of the most effective enterprise browser security controls. Rather than relying on users to exercise judgment about extension safety, the IT department maintains an approved list of extensions that are permitted, and all others are blocked — including both installation and operation of unapproved extensions. This prevents malicious extension installation entirely (even by a compromised user account) and eliminates the extension supply chain attack surface on managed devices. Extensions on the approved list can be force-installed on all endpoints via policy.
Safe Browsing / SmartScreen
Google Safe Browsing (Chrome), Microsoft SmartScreen (Edge), and Firefox's built-in protection maintain databases of known phishing sites, malware-distributing URLs, and malicious downloads. When a user navigates to or downloads from a known-bad URL, the browser displays a warning or blocks the request entirely. These should never be disabled. In enterprise environments, confirm Safe Browsing / SmartScreen is enforced via policy and cannot be disabled by users. Enhanced Safe Browsing (Chrome) provides additional real-time checks at the cost of sending more URL data to Google.

Certificate Warning Triage Guide

Certificate Error Response — Triage Workflow
Certificate: expired
→
First check system clock — an incorrect date causes all certificates to appear expired. If clock is correct: the website's certificate has genuinely expired, contact site owner. For an internal server you manage: renew the certificate immediately. Proceeding on an expired certificate is acceptable for internal, non-sensitive tools after confirming the cause.
Certificate: name mismatch
→
Verify the URL in the address bar matches the site you intended to visit. Check for typosquatting (look-alike domains). If this appears on a site that previously worked normally, investigate for a man-in-the-middle attack or DNS hijacking before proceeding. For internal devices (routers, switches), this is expected if connecting by IP address — acceptable for admin use with awareness.
Certificate: untrusted CA
→
Self-signed certificate on an internal device is expected — confirm it's the device you intended to reach. If on a corporate internal site: deploy the internal CA root certificate via Group Policy so all endpoints trust it automatically. If unexpected on an external site: investigate for certificate substitution attack before proceeding.
Certificate: revoked
→
Do not proceed. Revocation indicates the certificate's private key may be compromised or the certificate was issued in error. The site may be actively impersonated by an attacker using the compromised key. Report the issue to the site owner and use an alternative means of contact to verify.
All HTTPS sites suddenly show certificate warnings
→
Investigate: (1) Check system clock; (2) Check proxy settings for unauthorized proxy; (3) Check trusted root CA store for unexpected root certificates (a rogue CA cert installed by malware enables MITM on all HTTPS); (4) Check for malware — SSL interception is a common malware technique. Run a malware scan. Look for unauthorized certificates in certmgr.msc → Trusted Root Certification Authorities.
Corporate site shows certificate warning on managed endpoints
→
Internal CA root certificate has not been deployed to affected endpoints. Deploy the internal root CA certificate via Group Policy: Computer Configuration → Windows Settings → Security Settings → Public Key Policies → Trusted Root Certification Authorities. After policy refresh (gpupdate /force), the warning resolves on all domain-joined machines.

Objective 2.11 — Key Facts Summary

Trusted sourcesDownload browsers only from official vendor websites or app stores. Third-party download aggregators may bundle adware or distribute trojanized installers.
HashingSHA-256 is the current standard. Compare computed hash of downloaded file against publisher's published hash. Mismatch = do not install. MD5 and SHA-1 are broken/deprecated.
Code signingLegitimate installers display a verified publisher name in the UAC prompt. "Unknown publisher" on a browser installer is a red flag. Code signing verifies identity, not safety.
Browser patchingEnable auto-updates. Browsers release security patches frequently. Unpatched browsers have known CVEs actively exploited in drive-by campaigns. EOL browsers (IE) must be replaced.
Extension sourcesPrefer official store extensions. Sideloaded extensions bypass review. Malicious extensions can steal credentials, hijack sessions, and exfiltrate browsing data.
Extension permissionsReview before installing. An extension with "read all data on all websites" has unnecessary breadth for most functions. Minimize permissions per least-privilege principle.
Supply chain (extensions)Trusted extensions can become malicious if the developer's account is compromised or the extension is sold to a malicious new owner. Audit extensions regularly.
Password managersPrevent credential reuse and credential stuffing. Built-in browser managers are acceptable; dedicated managers add cross-browser access, breach monitoring, and audit features.
Certificates — validBrowser validates: domain matches, date within validity period, signed by trusted CA, not revoked. All four must pass for the padlock to appear without warning.
Self-signed certExpected on internal devices. Triggers browser warning because no CA chain exists. Acceptable for known internal devices; investigate before accepting on external sites.
Expired cert — first stepCheck the system clock first. An incorrect date causes all certificates to appear expired or invalid. Rule out clock error before assuming a site has a certificate problem.
Rogue root CAMalware can install a rogue root CA certificate enabling MITM on all HTTPS connections. Symptom: unexpected warnings across all HTTPS sites. Check certmgr.msc Trusted Roots.
Pop-up blockerEnabled by default. Prevents scareware and drive-by redirect popups. Add per-site exceptions for legitimate uses; never disable globally.
Clearing browsing dataCtrl+Shift+Delete. Clears history, cache, cookies, saved passwords depending on selection. Session cookies hold login state — clearing logs you out of all sites.
Private / IncognitoPrevents local storage of browsing data on the device. Does NOT prevent ISP, employer, or network admin from seeing traffic. Not anonymization — local privacy only.
Browser sync securitySync security = browser account security. Enable MFA on Google/Microsoft/Firefox account. Disable sync on shared computers. Compromised sync account = all passwords stolen.
Ad blockersSecurity benefit beyond convenience: blocks malvertising (malicious code in ad networks). uBlock Origin is open-source, highly effective, blocks tracking scripts.
Proxy hijackingMalware may change proxy settings to route traffic through attacker-controlled proxy for MITM. Check proxy settings as part of any malware investigation.
Secure DNS (DoH)Encrypts DNS queries inside HTTPS traffic. Prevents ISP from monitoring DNS. Bypasses OS resolver — may conflict with enterprise internal DNS. Disable via policy in enterprise environments.
Internal root CAEnterprise HTTPS sites signed by internal CA require deploying the internal root CA certificate via Group Policy to all endpoints. Resolves "untrusted CA" warnings on internal sites.

High-Probability Exam Scenarios

Scenario 1: A user downloaded a browser from a third-party site. The file's SHA-256 hash does not match the hash published on the official vendor site. What should the technician do? → Do not install the file. The hash mismatch indicates the file has been modified — it may contain malware. Download the installer directly from the official vendor site and verify the hash before installing.

Scenario 2: A user complains that every HTTPS website is showing certificate errors. What should the technician check first? → System clock — an incorrect date causes all certificates to appear invalid. If the clock is correct, check for malware that may have installed a rogue root CA certificate or modified proxy settings.

Scenario 3: A user browsing in incognito mode asks whether their employer can see their web activity. What is the correct answer? → Yes. Incognito/private mode prevents local storage of browsing data on the device but does not hide traffic from the network — the employer's network infrastructure, proxy servers, and DNS logging can still record all browsing activity.

Scenario 4: After visiting a website, a user's browser began displaying pop-ups claiming the computer is infected and demanding they call a support number. What most likely happened and what is the fix? → The user likely clicked "Allow" on a browser notification permission request from a malicious site. Fix: Settings → Site settings → Notifications → review and revoke the malicious site's notification permission. Run a malware scan to confirm no actual infection.

Scenario 5: Users on a managed corporate network cannot browse the company's internal HTTPS portal without certificate warnings. What is the solution? → Deploy the company's internal root CA certificate to all endpoints via Group Policy (Computer Configuration → Windows Settings → Security Settings → Public Key Policies → Trusted Root CAs). This allows all domain-joined computers to trust certificates signed by the internal CA.

Scenario 6: A technician discovers a browser extension that was not installed by the user, has permissions to "read and change all your data on all websites," and was sideloaded from outside the official store. What should be done? → Remove the extension immediately and investigate for compromise — check for other signs of malware, review browsing history and saved credentials for unauthorized activity, change passwords for sensitive accounts, and run a full malware scan. The extension characteristics describe a malicious browser extension.

Scenario 7: A small business wants to prevent employees from installing any browser extensions not approved by IT. What is the correct technical control? → Configure browser extension allowlisting via Group Policy using the browser's ADMX Group Policy templates. This blocks all extensions not on the approved list from being installed or running, regardless of what the user attempts.
