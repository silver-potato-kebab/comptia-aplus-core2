OVERVIEWIntroduction to Operating Systems

An operating system (OS) is the foundational software layer that manages a device's hardware and provides the services applications need to run — memory management, process scheduling, file storage, device drivers, security, and the user interface itself. Every device a technician touches, from a desktop tower to a smartphone in someone's pocket, runs some operating system, and picking the right one for the job — and knowing its quirks — is core to the support role the A+ exam certifies.

Objective 1.1 asks you to recognize the major desktop and mobile operating systems in use today, understand what each one is best suited for, know the filesystems each one relies on to organize data on disk, and understand what happens when an OS or a specific version of it reaches the end of its supported life. It also touches on the practical headaches that come from mixing operating systems and filesystems in the same environment — the compatibility concerns a technician is expected to anticipate.

Core Concept — Two Categories, One Exam Objective

The exam splits operating systems into two buckets: workstation systems (Windows, Linux, macOS, Chrome OS — designed to run on desktops and laptops) and mobile OSes (iPadOS, iOS, Android — designed for touch-first, battery-powered, always-connected devices). Each OS pairs with certain filesystems, has its own life-cycle policy, and creates specific compatibility friction when it has to interoperate with the others. Keep those three threads — OS, filesystem, life cycle — separate in your head, because exam questions frequently test one against another (e.g., "which filesystem would you use on this OS," or "why can't this file be read on that OS").

SECTION 1Workstation Operating Systems

A workstation OS is designed to run on desktop and laptop computers where a keyboard, mouse, and full-size display are the primary input and output methods, and where the machine typically stays connected to power. The four workstation OSes on the exam — Windows, Linux, macOS, and Chrome OS — cover the overwhelming majority of desktop and laptop deployments a technician will encounter in the field.

Windows

Microsoft Windows is the dominant desktop operating system in both consumer and enterprise environments. Its market position stems from decades of backward compatibility, the broadest hardware and peripheral driver support of any desktop OS, and deep integration with business tools — Active Directory, Group Policy, Microsoft 365, and enterprise management platforms like Intune and SCCM.

WindowsClosed-source · Microsoft
Primary use case General-purpose business and home desktops/laptops; the default choice for organizations standardized on Active Directory and Microsoft's productivity ecosystem
Native filesystem NTFS for internal drives (required for the OS partition); FAT32/exFAT commonly used for removable/external media
Strengths Widest application library and hardware driver availability; native support for legacy business software; centralized management via Active Directory/Group Policy/Intune; largest installed base means the broadest peer/community support
Considerations Largest attack surface due to market share, making it the most frequently targeted OS by malware; licensing costs per seat; feature updates and end-of-life dates must be tracked per version

Linux

Linux is an open-source, Unix-like operating system built around the Linux kernel, distributed in many different "distributions" (distros) such as Ubuntu, Fedora, Debian, and Red Hat Enterprise Linux (RHEL). Because the kernel and most surrounding software are free and open-source, Linux dominates servers, embedded devices, and increasingly developer workstations, while remaining a minority player on consumer desktops.

LinuxOpen-source · Community/Vendor
Primary use case Servers, developer workstations, embedded/IoT devices, and cost-sensitive or highly customizable desktop deployments; the backbone of most of the internet's server infrastructure
Native filesystem ext4 is the default on most distributions; XFS is common on Red Hat/enterprise systems and for large storage volumes
Strengths No license cost; highly configurable and scriptable; strong security model with granular permissions; long-term stability for servers; large ecosystem of free, open-source software
Considerations Smaller consumer software library (some commercial apps have no native Linux version); steeper learning curve for users accustomed to Windows/macOS; hardware driver support varies by distro and hardware vendor

macOS

Apple's macOS is a Unix-based desktop OS that runs exclusively on Apple's Mac hardware. It is known for tight hardware/software integration, a polished user interface, and deep interoperability with Apple's other device platforms (iPhone, iPad, Apple Watch) through Continuity features.

macOSClosed-source · Apple, hardware-locked
Primary use case Creative and professional workstations (video/audio/photo editing, design, development), and organizations already invested in Apple's device ecosystem
Native filesystem APFS (Apple File System) is the default on all modern Macs; older Macs and some external drives may still use HFS+
Strengths Tight hardware/software optimization since Apple controls both; strong built-in creative and productivity software; seamless integration with iPhone/iPad via Continuity, Handoff, and iCloud; Unix underpinnings give it a capable command-line environment (Terminal)
Considerations Only runs on Apple hardware — no option to build/repair with commodity parts; smaller business software library for certain vertical/legacy applications; generally higher hardware cost than comparable Windows/Linux machines

Chrome OS

Chrome OS is Google's lightweight, Linux-kernel-based operating system built around the Chrome web browser. It is designed for devices — Chromebooks — that rely heavily on cloud storage and web/Android applications rather than large locally installed software.

Chrome OSClosed-source core · Google
Primary use case Education (the dominant OS in K-12 classrooms), low-cost/low-maintenance business fleets, and kiosk-style deployments where centralized cloud management matters more than local software installation
Native filesystem Uses a Linux-derived filesystem internally; user-facing storage is primarily cloud-based (Google Drive), so local filesystem specifics rarely surface as a support concern
Strengths Fast boot times; minimal local attack surface (mostly sandboxed web/Android apps); automatic background updates; centralized fleet management through the Google Admin console; inexpensive hardware
Considerations Cannot run traditional Windows/macOS desktop applications natively; heavily dependent on an internet connection for full functionality; limited local storage on most devices by design

Exam Angle — Matching OS to Scenario

Scenario questions on 1.1 often describe an environment and ask which workstation OS fits. Video editor needs a workstation → macOS (creative software ecosystem). School wants low-maintenance, cheap, cloud-managed laptops → Chrome OS. Developer needs a server-like environment locally for scripting/compiling → Linux. Business needs Active Directory domain join and legacy line-of-business software → Windows. Read for the clue words: "creative," "budget/cloud-managed/education," "open-source/server/scripting," and "domain/legacy line-of-business app" respectively.

SECTION 2Mobile Operating Systems

Mobile operating systems are built for touch input, battery efficiency, constant wireless connectivity, and an app-store distribution model rather than traditional installer packages. The exam covers three: Apple's iPadOS and iOS, and Google's Android.

iPadOS and iOS

iOS runs on the iPhone, and iPadOS is Apple's fork of iOS tailored for the iPad's larger touchscreen, adding features like a more capable multitasking Split View, external pointer/keyboard support, and a Files app with more desktop-like file management. Both are closed-source, run only on Apple hardware, and share the same underlying Darwin/XNU kernel lineage as macOS.

iOS (iPhone)

  • Distribution model — Apps install only through the App Store (absent jailbreaking); Apple reviews every app before publication
  • Hardware — Runs exclusively on iPhone hardware; tightly optimized for a specific, limited set of chipsets Apple designs itself
  • Ecosystem role — Central hub for Apple ID, iCloud, Apple Pay, and Continuity features shared with macOS/iPadOS
  • Support model — Long update support window per device generation; security patches distributed directly by Apple, bypassing carriers

iPadOS (iPad)

  • Distribution model — Same App Store model as iOS; many iPhone apps run on iPad automatically or with an adapted layout
  • Hardware — Runs exclusively on iPad hardware; higher-end iPads use the same chip families as Macs
  • Differentiators from iOS — Multitasking (Split View/Slide Over), Apple Pencil support, external display/keyboard support, more capable Files app
  • Support model — Same Apple-direct patch distribution model as iOS; update support tied to hardware generation

Android

Android is Google's mobile OS, built on an open-source Linux kernel, but distributed and customized by many different hardware manufacturers (Samsung, Google, Motorola, and others). This open licensing model is the single biggest structural difference between Android and Apple's mobile OSes.

AndroidOpen-source core · Google, multi-vendor
Primary use case The most widely used mobile OS worldwide across a huge range of price points and hardware form factors, from budget phones to foldables to tablets
Distribution model Google Play Store is the default, but Android's open licensing allows sideloading APK files and alternative app stores — something iOS does not permit without jailbreaking
Strengths Runs on hardware from dozens of manufacturers at every price point; deep customization (launchers, widgets, system-level tweaks); open-source AOSP base lets vendors build heavily customized experiences
Considerations Update timelines vary widely by manufacturer/carrier since each vendor must adapt and push its own updates — a major fragmentation concern; the more open distribution model creates greater exposure to malicious sideloaded apps

Fragmentation — A Real-World Android Support Issue

Because manufacturers customize Android and control the update rollout for their own devices, two phones running "Android" can be on very different security patch levels even when released the same year. A technician troubleshooting an Android security issue always needs to check the specific device model and manufacturer, not just "which version of Android" — the manufacturer's own update policy determines what's actually possible to patch.

SECTION 3Various Filesystem Types

A filesystem is the method an OS uses to organize, name, store, and retrieve data on a storage device. Each OS family has a native filesystem it's optimized for, and knowing which filesystem pairs with which OS — and what each filesystem's limitations are — is heavily tested on 1.1.

FilesystemFull NameNative OSKey Characteristics
NTFSNew Technology File SystemWindowsJournaling; file/folder permissions (ACLs); encryption (EFS); compression; supports very large files and volumes; required for the Windows OS partition
ReFSResilient File SystemWindows Server / Windows Pro for WorkstationsNewer Microsoft filesystem built for resiliency and large-scale storage; automatic data integrity checking/repair; used for storage pools and large data volumes rather than as a general boot filesystem
FAT3232-bit File Allocation TableLegacy Windows / universal removable mediaMaximum individual file size 4 GiB; maximum volume size 2 TiB; no permissions or journaling; the most universally compatible filesystem across Windows, macOS, and Linux for small removable drives
ext4Fourth Extended FilesystemLinuxJournaling filesystem; the default on most Linux distributions; supports large files/volumes; not natively readable by Windows or macOS without third-party drivers
XFSExtended FilesystemLinux (Red Hat/enterprise)High-performance journaling filesystem tuned for large files and parallel I/O; common default on Red Hat Enterprise Linux and for large storage arrays/servers
APFSApple File SystemmacOS / iOS / iPadOSOptimized for flash/SSD storage; native encryption; space-sharing between volumes on the same physical container; snapshots for backups; replaced HFS+ as Apple's default
exFATExtensible File Allocation TableCross-platform removable mediaDesigned to replace FAT32 on large removable drives; no 4 GiB file size limit; readable/writable natively by Windows, macOS, and modern Linux — the go-to choice for cross-platform USB/external drives holding large files
Journaling A technique where the filesystem logs pending changes before committing them, so that if the system crashes mid-write, the filesystem can replay or roll back the journal on next boot rather than becoming corrupted. NTFS, ext4, XFS, and APFS are all journaling filesystems; FAT32 is not, which is why FAT32 volumes are more prone to corruption after an unclean shutdown.
Why FAT32/exFAT persist Despite being older or simpler than NTFS/ext4/APFS, FAT32 and exFAT remain important because they are the only filesystems natively readable and writable across Windows, macOS, and Linux without installing extra drivers. This cross-platform compatibility is exactly why USB flash drives and SD cards ship formatted as FAT32 (smaller/older media) or exFAT (larger drives and files).
Reading a foreign filesystem Windows cannot natively read ext4 or XFS (Linux) or write to APFS (macOS) without third-party software. macOS can read NTFS by default but cannot write to it without third-party tools or reformatting. This is a frequent real-world support scenario: a drive formatted on one OS often needs a driver, a reformat, or a cross-platform filesystem (exFAT) to be usable on another.

Exam Angle — Filesystem Selection

Windows OS/boot drive → NTFS (required). Linux OS/boot drive → ext4 (most common) or XFS (enterprise/Red Hat). macOS internal drive → APFS. Cross-platform external drive, files under 4 GB → FAT32 for maximum compatibility with older devices. Cross-platform external drive, large files (video, disk images) → exFAT, since it removes the FAT32 file-size ceiling while remaining readable everywhere.

SECTION 4Vendor Life-Cycle Limitations

Every operating system version has a defined support life cycle set by its vendor. Understanding these life-cycle stages — and the risk of running past them — is essential, because an OS's age directly determines whether it can still receive security fixes.

End-of-Life (EOL) The point at which a vendor permanently stops providing security patches, bug fixes, and technical support for an OS version. Once an OS reaches EOL, any newly discovered vulnerability in it will never be patched — the system is permanently exposed. Continuing to run EOL software in a business environment is a compliance and security liability, not just an inconvenience.
Update limitations Constraints on which updates a given device or OS version can actually receive — for example, hardware too old to meet a new OS version's minimum requirements, a mobile device whose manufacturer has stopped shipping monthly security patches, or a Windows feature update version that has itself passed its own separate support date even though the parent OS is still supported. Update limitations can leave a device vulnerable well before the OS's official EOL date.

Life Cycle Across OS Families

  • Windows — Each release/feature update has its own mainstream and extended support dates set by Microsoft; server versions are typically supported longer than desktop consumer versions
  • macOS — Apple typically supports a given macOS version with security updates for about three years from release, then drops it for the newest hardware
  • Linux distros — Support windows vary widely by distribution; enterprise distros (RHEL, Ubuntu LTS) offer multi-year support windows, while some community releases support only months
  • Mobile OSes — iOS/iPadOS support windows are tied to hardware generation and set directly by Apple; Android support windows are set independently by each device manufacturer, often shorter and less predictable

Consequences of Running EOL Software

  • No security patches — any newly discovered vulnerability remains permanently exploitable
  • Compliance failure — many regulatory/compliance frameworks explicitly prohibit EOL software in scope
  • Loss of vendor support — no technical support, no bug fixes, no driver updates for new peripherals
  • Compatibility drift — new software and hardware increasingly refuse to support or even install on EOL platforms

Real-World Consequence — EOL Is Not Theoretical

Ransomware outbreaks like WannaCry in 2017 spread most severely through organizations still running Windows XP, which had already reached EOL years earlier. Microsoft had patched the underlying vulnerability for all currently supported Windows versions, but EOL systems never received that fix and had no defense. The lesson tested on the exam: EOL is a security decision with real consequences, not just a policy checkbox.

SECTION 5Compatibility Concerns Between Operating Systems

Supporting a mixed environment — Windows machines alongside Macs, Linux servers, and a fleet of iOS and Android phones — means anticipating where these systems don't naturally interoperate. Objective 1.1 expects a technician to recognize the common friction points before they become support tickets.

  • File format and application compatibility — a file created in an application on one OS may not open correctly (or at all) in a different OS's version of that application, or in an application native to a different OS entirely
  • Filesystem compatibility — an external drive formatted as NTFS or ext4 on one OS may be unreadable, or read-only, on another OS without added drivers or a reformat (see Section 3)
  • Driver and peripheral support — a printer, scanner, or specialty peripheral may only ship drivers for certain OSes, leaving other platforms unable to use the device fully or at all
  • Application availability — some commercial software is published for only one or two OS platforms (e.g., many enterprise line-of-business applications are Windows-only), forcing organizations to maintain a specific OS just to run one application
  • Authentication and directory service integration — joining a Linux or macOS machine to a Windows Active Directory domain requires extra configuration (or third-party tools) that isn't necessary for Windows clients, which join natively
  • Mobile-to-desktop handoff — features like Apple's Continuity/Handoff only work within the Apple ecosystem; an Android phone and a Windows PC require third-party or manufacturer-specific apps to achieve similar file/clipboard sharing
  • 32-bit vs. 64-bit and legacy software — older 16-bit or 32-bit-only applications may not run at all on a modern 64-bit OS without a compatibility layer or virtual machine

Practical Example — Mixed-OS File Sharing

A small office with a mix of Windows PCs and MacBooks wants to share a single external hard drive for large video files. Formatting the drive NTFS means the Macs can read but not write to it by default. Formatting it APFS means the Windows PCs can't read it at all without third-party software. The practical fix, and the one the exam wants you to recognize, is to format the drive exFAT — it is natively readable and writable by both operating systems and has no 4 GiB file-size ceiling, making it the correct answer for cross-platform file sharing of large files.

OS Selection Guide

  • General business/home desktop — Windows
  • Server, developer workstation, IoT — Linux
  • Creative/professional production work — macOS
  • Education or low-maintenance cloud fleet — Chrome OS
  • Apple phone — iOS · Apple tablet — iPadOS
  • Multi-vendor, customizable, any price point — Android

Filesystem-to-OS Pairing

  • Windows OS partition — NTFS (required)
  • Windows Server large storage pools — ReFS
  • Linux OS partition (general) — ext4
  • Linux OS partition (enterprise/RHEL) — XFS
  • macOS/iOS/iPadOS internal storage — APFS
  • Cross-platform removable media — FAT32 (small files) / exFAT (large files)

Life-Cycle Red Flags

  • OS past its EOL date — no future patches, ever; flag for immediate upgrade/replacement
  • Device can't meet new OS hardware requirements — an update limitation, not a choice
  • Android phone with no OEM update in a year+ — check manufacturer's specific patch policy
  • Windows feature update itself past support — separate from whether Windows overall is supported

Compatibility Troubleshooting

  • Drive unreadable on another OS — check filesystem; consider reformatting to exFAT
  • App won't run on new OS — check 32-bit/64-bit and legacy compatibility layer options
  • Peripheral not working on non-Windows OS — check vendor's cross-platform driver support
  • Mac/Linux won't join AD domain natively — expect extra configuration or third-party tooling

Final Exam Reminders

Windows = NTFS, Linux = ext4/XFS, macOS = APFS — memorize these three native pairings first; every other filesystem question builds on top of them.

FAT32's defining limit is 4 GiB per file — this single fact explains why it can't hold most modern install media or large video files, and why exFAT exists.

exFAT is the correct answer for cross-platform large-file sharing on removable/external drives — native read/write on Windows, macOS, and modern Linux, with no FAT32 file-size ceiling.

iOS is for iPhone; iPadOS is the iPad-specific fork with added multitasking and accessory support — don't confuse the two on device-specific scenario questions.

Android's open licensing allows sideloading; iOS/iPadOS do not (without jailbreaking) — this is the core distribution-model difference tested between the two mobile platforms.

End-of-Life (EOL) means no security patches will ever be released again for that OS version, regardless of how severe a newly discovered vulnerability is. This is distinct from an update limitation, where a device is simply blocked from receiving updates it might otherwise be eligible for.

Chrome OS is Linux-kernel-based but is not "Linux" for exam purposes — it's tested as its own distinct category focused on cloud/education/fleet deployments.

Compatibility concerns are about friction points, not permanent impossibilities — filesystem mismatches, driver gaps, and app availability gaps almost always have a workaround (reformatting, third-party drivers, compatibility layers, or virtualization), and the exam wants you to identify the right workaround for the scenario.
