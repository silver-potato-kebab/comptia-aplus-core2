OVERVIEWIntroduction

Objective 2.2 is the most hands-on security objective on the Core 2 exam. Where 2.1 asked you to summarize what security controls are, 2.2 asks you to configure them in real Windows environments. Every topic here maps to specific settings menus, control panel applets, command-line tools, or management consoles that a technician uses daily.

The objective covers Windows built-in security tools (Defender Antivirus, Firewall, BitLocker, EFS), account management (local vs. Microsoft accounts, user types, UAC), login options (Windows Hello, PIN, biometric), file system security (NTFS permissions, share permissions, inheritance), and Active Directory administration for domain environments. Scenarios on the exam will describe a specific security problem and ask which setting to configure or which tool to use.

Where to Find These Settings

Most settings in this objective live in three places: Windows Security app (Defender, Firewall, Device Security) — accessible from the system tray shield icon or Settings → Privacy & Security → Windows Security. Control Panel — still hosts User Accounts, BitLocker, Credential Manager, and more. Computer Management (compmgmt.msc) — contains Local Users and Groups, Disk Management, Event Viewer, and other MMC snap-ins. Active Directory management is performed from Domain Controller tools (ADUC — Active Directory Users and Computers).

SECTION 1Windows Defender Antivirus

Windows Defender Antivirus is Microsoft's built-in endpoint protection platform, included at no additional cost with all editions of Windows 10 and Windows 11. It provides real-time protection against viruses, malware, ransomware, spyware, and other threats. In managed enterprise environments, Defender integrates with Microsoft Defender for Endpoint for centralized management and advanced threat detection.

Windows Security → Virus & threat protection
Defender Antivirus — Configuration Windows Security App
Activate / Deactivate
Windows Security → Virus & threat protection → Manage settings → Real-time protection toggle. Real-time protection is on by default and monitors files as they are accessed. Turning it off leaves the machine unprotected against new threats. Windows automatically re-enables real-time protection after a short period if it is turned off manually — this is a safety mechanism.

Defender automatically deactivates real-time scanning when a third-party antivirus product is installed and registered with Windows Security Center, deferring to that product. If the third-party product is removed or expires, Defender reactivates automatically. Never run two competing real-time antivirus engines simultaneously — they will conflict and degrade system performance.
Update Definitions
Virus & threat protection → Virus & threat protection updates → Check for updates. Defender's detection capability depends on its definition files (also called signatures) — a database of known malware characteristics that Defender uses to identify threats. Definitions are typically updated multiple times per day via Windows Update.

Why definitions must be current: Defender can only detect threats it has a signature for. New malware released after a definition update will not be detected until a new signature is published and downloaded. A machine with definitions that are days or weeks old is significantly less protected than one with current definitions. In environments with restricted internet access, WSUS (Windows Server Update Services) or SCCM can distribute definition updates internally.
Scan Types
Quick scan — scans locations where malware most commonly hides: startup items, running processes, system folders. Fast (minutes). Full scan — scans every file on every drive. Thorough but slow (hours on large drives). Custom scan — scan a specific folder or drive. Microsoft Defender Offline scan — reboots the machine and scans before Windows loads, catching rootkits and boot-sector malware that hide from standard OS-level scans.
Exclusions
Virus & threat protection settings → Add or remove exclusions. Files, folders, file types, or processes can be excluded from scanning. Used when Defender generates a false positive on a legitimate business application. Exclusions reduce protection — apply them narrowly and document them. A common attack technique is to place malware in an excluded folder.
Quarantine & History
Protection history shows all past detections and actions taken. Quarantined threats have been isolated — their files are moved to a protected location and prevented from executing. A quarantined threat is not removed; it can be restored if incorrectly flagged. Allowed threats are items the user has explicitly allowed despite Defender's objection — review this list during incident response.

Exam Focus — Defender and Third-Party AV

When a third-party antivirus is installed and active, Defender's real-time protection automatically deactivates. If the third-party AV expires or is uninstalled, Defender reactivates. A machine with no active real-time protection (third-party expired and Defender somehow disabled) shows a red alert in Windows Security. The fix is to either renew the third-party AV or re-enable Defender's real-time protection.

SECTION 2Windows Defender Firewall

The Windows Defender Firewall is a host-based, stateful packet filtering firewall that controls inbound and outbound network traffic to and from the local machine. Unlike a network perimeter firewall that protects the entire network, the Windows Firewall protects the individual endpoint — making it critical for laptops used outside the corporate network (hotels, coffee shops, airports) where no perimeter protection exists.

Windows Security → Firewall & network protection   |   Control Panel → Windows Defender Firewall   |   wf.msc (Advanced)

Network Profiles

Windows Firewall maintains three separate network profiles, each with independent rule sets. When a network connection is established, Windows assigns it to one of these profiles, and the appropriate rule set is applied automatically.

Firewall Network Profiles wf.msc
Domain Profile
Applied when the computer is connected to a network where it can authenticate to a domain controller. Typically the most permissive profile — corporate IT manages the rules via Group Policy and the domain environment is considered relatively trusted. Used on the office LAN.
Private Profile
Applied to networks the user has designated as private — typically a home network or a trusted small office network. More permissive than public, allows local network discovery, file and printer sharing. The user explicitly designates a network as Private when connecting.
Public Profile
Applied to all other networks by default — hotel Wi-Fi, airport hotspots, coffee shop networks. The most restrictive profile. Disables network discovery and file sharing. Drops unsolicited inbound connections. This is the correct profile for any untrusted network. If a user sets a public Wi-Fi to "Private," they expose their machine to other devices on that public network.

Activate and Deactivate

The Firewall can be turned on or off per profile independently. Windows Security → Firewall & network protection → select a network type → toggle Microsoft Defender Firewall. Turning off the Firewall for any profile leaves the machine unprotected from unsolicited inbound connections on that network type. The Firewall should virtually never be turned off as a troubleshooting step — instead, identify the specific application or port causing the issue and create a targeted rule.

Firewall Off Is Not a Troubleshooting Solution

When a user reports that an application "doesn't work," disabling the firewall entirely to test connectivity is a poor practice that leaves the machine exposed. The correct approach is to identify the port or application and create a specific allow rule. If disabling the Firewall does fix the issue, that confirms the Firewall is blocking something — the next step is to identify and allow the specific traffic, then re-enable the Firewall.

Port Security

Port-based rules in the Windows Firewall control which TCP and UDP ports are allowed to receive inbound connections or make outbound connections. The Windows Defender Firewall with Advanced Security (wf.msc) provides the full rule management interface.

Port and Rule Management wf.msc → Inbound/Outbound Rules
Inbound rules
Control traffic arriving at this machine. By default, Windows Firewall blocks all unsolicited inbound connections. Creating an inbound rule for port 3389 (TCP) allows Remote Desktop connections to this machine. Inbound rules are the primary security concern — they control what can reach this machine from the network.
Outbound rules
Control traffic leaving this machine. By default, all outbound connections are allowed. Outbound rules are used in higher-security scenarios to restrict which applications or destinations this machine can communicate with — for example, blocking a non-approved application from reaching the internet.
Creating a port rule
wf.msc → Inbound Rules → New Rule → Port → TCP or UDP → Specific local ports → enter port number(s) → Allow the connection → select profiles → name the rule. Multiple ports can be listed comma-separated (80, 443) or as a range (8080-8090). Always restrict the rule to the minimum necessary profiles (e.g., Domain only, not Public).
Common ports to know
TCP 80 = HTTP, TCP 443 = HTTPS, TCP 3389 = RDP, TCP 22 = SSH, TCP/UDP 53 = DNS, UDP 67/68 = DHCP, TCP 25 = SMTP, TCP 143 = IMAP, TCP 110 = POP3, TCP 445 = SMB file sharing, TCP 3306 = MySQL, TCP 1433 = MSSQL.
Rule precedence
Block rules take precedence over Allow rules. If a block rule and an allow rule both match the same traffic, the block rule wins. Connection security rules (IPsec) are evaluated before standard inbound/outbound rules.

Application Security

Application-based rules allow or block specific programs from communicating through the Firewall, regardless of port. When an application attempts to listen for inbound connections for the first time, Windows displays a pop-up asking whether to allow it on Private and/or Public networks. This creates an application-based allow rule in the Firewall.

Application Rules wf.msc or Control Panel Firewall
Allow an app through
Control Panel → Windows Defender Firewall → Allow an app or feature through Windows Defender Firewall. This simpler interface lists all apps with checkboxes for Private and Public profiles. Checking both boxes creates inbound allow rules for that application on both profiles. This is the appropriate interface for non-technical users managing app exceptions.
Application rule in wf.msc
wf.msc → New Rule → Program → browse to executable path. More granular — can specify direction (inbound/outbound), action (allow/block), profiles, scope (restrict to specific remote IP addresses), and protocol. Best for IT-managed rules. Example: allow only the corporate VPN client to make outbound connections to a specific server IP on specific ports.
Application control vs. port control
Application rules are generally more secure than port rules because they restrict which specific program can use a port. A port rule for TCP 8080 allows anything to connect on that port. An application rule for a specific executable allows only that program. Where possible, create application rules rather than broad port rules.

SECTION 3Users and Groups

Local vs. Microsoft Account

Local Account Stored in the local Security Account Manager (SAM) database on the machine. Credentials exist only on this device. No cloud sync, no Microsoft services integration, no cross-device settings. When the machine is not domain-joined, local accounts are the only option for sign-in without internet access. Created during Windows setup by choosing "Offline account" (increasingly hidden in Windows 11 Home, which pushes Microsoft account signup).
Microsoft Account An email-based account (any @outlook.com, @hotmail.com, @live.com, or any email linked to a Microsoft account) that authenticates against Microsoft's cloud identity service. Credentials sync across devices; settings, themes, browser favorites, and OneDrive sync automatically. Purchasing from the Microsoft Store requires a Microsoft account. On a domain-joined machine, Microsoft accounts are not used for domain authentication — the domain account is used instead.
Key Differences Microsoft accounts enable BitLocker Device Encryption recovery key backup to OneDrive (on Home editions), cross-device settings sync, and seamless integration with Microsoft 365. Local accounts provide more privacy (no data transmitted to Microsoft) and work without internet access. In enterprise environments, domain accounts managed by Active Directory replace both for primary authentication.

Account Types

Administrator
✓Full system control — install software, change system settings, manage all users
✓Modify security settings, install drivers
✓Access all files on the system regardless of NTFS permissions
✓Create and manage other user accounts
—Should not be used for daily tasks — privilege escalation risk

The built-in Administrator account is disabled by default. Members of the Administrators group have equivalent rights. UAC prompts for consent/credentials when elevation is required.

Standard Account
✓Run applications, use the internet, print documents
✓Change own password and personal settings
✓Access own files; read files explicitly shared with them
✗Cannot install software to Program Files or modify system settings
✗Cannot change security settings or manage other users

Recommended for all day-to-day use — even for IT staff. Limits damage from malware and user error. UAC prompts for admin credentials when elevation is needed.

Guest User
~Minimal temporary access — run applications, browse internet
✗Cannot install software or change system settings
✗Cannot access other users' files
✗Profile is discarded at logoff — no persistence
✗Disabled by default in Windows 10/11 — and should remain disabled

Security best practice: keep the Guest account disabled. An enabled Guest account creates an unauthenticated entry point. Use a Standard account for temporary users instead.

Power User
~Legacy group — had elevated privileges in Windows XP/Vista era
~In Windows 10/11, Power Users group has no special privileges above Standard Users
—Retained for backward compatibility only
—Not a security boundary in modern Windows

The Power Users group exists for legacy application compatibility. Do not use it as a middle ground between Standard and Administrator — it provides no meaningful additional privileges in modern Windows.

Exam Focus — Account Types

Know three things: (1) Standard accounts are the correct choice for everyday use — even for IT staff. (2) The Guest account is disabled by default and should remain disabled. (3) The Power Users group is a legacy artifact with no special privileges in modern Windows — it does not represent a useful middle tier between Standard and Administrator.

SECTION 4Login OS Options

Windows 10 and 11 support multiple authentication methods for signing in to the OS. These are configured in Settings → Accounts → Sign-in options. Different methods offer different trade-offs between security strength, convenience, and hardware requirements.

Settings → Accounts → Sign-in options

Username & Password

The traditional method. A text-based password is entered at the login screen. Supports local accounts, Microsoft accounts, and domain accounts. Password complexity requirements are set via Group Policy or account settings. Weakest in terms of phishing and credential theft — the password can be stolen, shared, or guessed.

PIN

A numeric (or alphanumeric) code specific to this device. Unlike a password, the PIN is device-bound — it only works on the machine it was set on. Even if a PIN is stolen, it cannot be used to log in from another device or access the Microsoft account online. Backed by the TPM chip for hardware-protected storage. Simpler to type, especially on touchscreens. Windows Hello PIN is not stored in the cloud.

Fingerprint

Uses an enrolled fingerprint via a compatible fingerprint scanner. Part of the Windows Hello framework. Fast, convenient, and hardware-backed by the TPM. Requires compatible fingerprint hardware. The fingerprint template is stored locally on the device (never leaves the device) and is processed by Windows Hello infrastructure, not transmitted to Microsoft.

Facial Recognition

Uses an infrared camera to perform 3D facial recognition. Part of Windows Hello. Requires compatible IR camera hardware (e.g., Intel RealSense, Surface cameras). Uses infrared and 3D depth sensing to prevent spoofing with a 2D photograph. Among the most convenient login methods — the user simply looks at the camera. Template stored locally, never uploaded.

Windows Hello

Microsoft's framework for passwordless authentication on Windows. Encompasses PIN, fingerprint, and facial recognition. Credentials are stored in the TPM and never leave the device. FIDO2-compliant. When configured with a Microsoft account or Azure AD, Windows Hello acts as a strong second factor that replaces passwords entirely for local and cloud resource access.

SSO / Passwordless

In domain and Azure AD environments, a successful Windows login (especially with Windows Hello) establishes an SSO session that grants access to connected resources without additional prompts. Passwordless authentication using Windows Hello for Business replaces the password entirely with asymmetric cryptography, achieving phishing-resistant authentication with no password to steal.

Windows Hello PIN Is Not a Simple Password

A common misconception: a Windows Hello PIN feels like a simple 4-digit code and therefore seems less secure than a long password. In fact, a Windows Hello PIN is more secure for local login because it is device-bound and hardware-backed by the TPM. A stolen password works anywhere on any device; a stolen PIN only works on the specific physical machine with the specific TPM it was configured on — and requires physical access to that machine. The TPM also enforces lockout after failed attempts, preventing brute-force attacks.

SECTION 5NTFS vs. Share Permissions

Windows uses two distinct permission systems that interact when a resource is accessed over the network. Understanding how they work individually and together is critical for both security configuration and troubleshooting access problems.

NTFS Permissions

NTFS permissions are applied to files and folders stored on NTFS-formatted volumes and control access at the file system level. They apply both locally (when a user is logged in directly) and remotely (when accessing over the network). NTFS permissions are the primary and most granular access control mechanism for files in Windows.

Share Permissions

Share permissions control access to a folder that has been shared over the network via Windows file sharing (SMB). They apply only to network access — when a user accesses the share over the network via a UNC path (\\server\share). Share permissions do not apply to local access. They are configured via: right-click folder → Properties → Sharing tab → Advanced Sharing → Permissions.

Share Permission Levels Folder → Sharing → Advanced Sharing → Permissions
Full Control
Read, Write, and the ability to change permissions on the share itself. Equivalent to full control over the shared resource via the network. Rarely assigned to non-administrator users.
Change
Read and write access — users can read, create, modify, and delete files in the share. Cannot change share permissions. This is the typical permission for users who need to work with files in a shared folder.
Read
View files and subfolders, read file contents, run executable files. Cannot make any changes. Default permission when a folder is shared — the "Everyone" group gets Read by default on new shares.

The Combined Effect — Most Restrictive Wins

When a user accesses a shared folder over the network, both NTFS permissions and Share permissions are evaluated. The effective access is the most restrictive (intersection) of the two permission sets. This is the most important rule for troubleshooting network file access.

Combined Permission Examples Most Restrictive Wins
Example 1
Share permission: Full Control / NTFS permission: Read → Effective network access = Read. NTFS is more restrictive, so it wins.
Example 2
Share permission: Read / NTFS permission: Full Control → Effective network access = Read. Share is more restrictive, so it wins.
Example 3
Share permission: Change / NTFS permission: Modify → Effective network access = Change/Modify (these are roughly equivalent — Read+Write+Delete, not Full Control).
Best Practice
Set Share permissions to Everyone: Full Control and manage all actual access control through NTFS permissions only. This simplifies administration — you only manage one permission system rather than two. The broad share permission will never be the limiting factor because NTFS is more granular and more restrictive where it needs to be.

File and Folder Attributes

File and folder attributes are metadata flags that affect how Windows handles a file or folder. They are distinct from permissions — attributes do not control who can access a file, but rather how the file behaves. Attributes are visible and configurable via File Explorer (Properties dialog) and the attrib command.

Read-only (R) The file can be read but not modified or deleted through normal means. Setting a document as read-only prevents accidental editing. Note: NTFS permissions are a stronger enforcement mechanism than the read-only attribute — an admin with Modify permission can override the read-only attribute.
Hidden (H) The file does not appear in File Explorer or dir output by default. Not a security control — any user with access to the folder can reveal hidden files via View → Show hidden items (File Explorer) or dir /a (command line). Hides files from casual view, not from determined access.
System (S) Marks the file as a critical operating system file. System files are hidden and protected from modification by default. Removing the system attribute from a critical OS file could allow it to be accidentally deleted.
Archive (A) Indicates the file has been modified since the last backup. Backup software checks the archive attribute to determine which files have changed and need to be backed up. After a backup, backup software clears the archive bit. When the file is modified again, Windows sets the archive bit again.

Inheritance

NTFS permission inheritance is the mechanism by which permissions set on a parent folder automatically flow down to all child files and subfolders within it. This simplifies administration — instead of setting permissions on every individual file, set them once on the parent folder and they propagate automatically.

Permission Inheritance Propagates Down
How it works
When you grant a user Read access to C:\Reports, all files and subfolders within Reports automatically inherit that Read permission. New files created inside Reports also inherit the permissions automatically. Inherited permissions appear greyed out in the permissions dialog — they cannot be modified directly on the child object.
Disabling inheritance
Right-click folder → Properties → Security tab → Advanced → Disable inheritance. You are then prompted to either convert inherited permissions to explicit permissions (copy the current inherited permissions as explicit, then you can modify them) or remove all inherited permissions (start with a blank permission list). Disabling inheritance is required when a subfolder needs different access than its parent.
Explicit vs. Inherited
Explicit permissions are set directly on an object and take precedence over inherited permissions. An explicit Deny always wins over an inherited Allow. An explicit Allow can override an inherited Deny. When troubleshooting unexpected access, always check whether a permission is inherited (from a parent) or explicit (set directly on the object).
Copying vs. Moving files
When a file is copied to a new location, it inherits the permissions of the destination folder. When a file is moved within the same volume, it retains its original permissions. When moved to a different volume, it inherits the destination's permissions (same as a copy). This is a frequently tested behavior.

Exam Focus — Copy vs. Move Permissions

Copy anywhere = inherits destination permissions. Move on same volume = keeps original permissions. Move to different volume = inherits destination permissions (because a cross-volume move is technically a copy + delete). This distinction is tested in scenarios about file access changing unexpectedly after moving files.

SECTION 6Run as Administrator vs. Standard User

Windows implements privilege separation — the concept that standard users run with limited rights, and elevated operations require explicit administrator-level privileges. Two mechanisms implement this separation: Run as administrator and User Account Control (UAC).

Run as Administrator

Right-clicking an executable and selecting Run as administrator launches the program with a full administrator token. This is necessary for programs that modify system settings, install software, write to protected directories (C:\Windows, C:\Program Files), or modify the Registry at the HKLM level.

Standard user launching When a standard user runs an application requiring elevation, Windows prompts for administrator credentials (the username and password of an admin account on this machine). This is the over-the-shoulder (OTS) credential prompt — an admin provides their credentials while sitting with the user, without giving the user the password.
Admin user launching When an administrator user runs an application requiring elevation, UAC prompts for consent — a simple Yes/No dialog confirming intent to elevate. The admin does not re-enter their password (unless UAC is set to the highest level). This prompt exists to prevent silent, automatic privilege escalation by malware.
Command line elevation Right-click Command Prompt or PowerShell → Run as administrator to launch an elevated shell. All commands run in that session execute with admin privileges. The title bar shows "Administrator:" prefix. Many diagnostic and repair commands (sfc, chkdsk /f, net user /add) require an elevated prompt.

User Account Control (UAC)

User Account Control (UAC) is a Windows security feature that limits the privileges of running applications, even when the logged-in user is an Administrator. When an application attempts to perform an operation that requires elevated privileges, UAC intercepts the request and prompts for explicit authorization — preventing programs from silently acquiring administrator rights without user knowledge or consent.

Why UAC Exists

Before UAC (Windows XP era), most users ran as Administrator all the time. Any malware that ran under that user context automatically had full administrator rights — no prompts, no barriers. UAC was introduced in Vista to break this model: even administrator users run with a split token (a limited token for daily tasks and an elevated token that must be explicitly requested). This means malware that runs under a standard admin session still starts with limited rights and must trigger a UAC prompt to escalate — giving the user a chance to notice.

UAC Notification Levels (High → Low)
Always notify
Most secure. Prompts every time any program (including Windows itself) attempts to make changes to system settings. Secure desktop dims the screen and prevents other interactions until the prompt is addressed. Recommended for high-security environments.
Notify (changes to apps)
Default setting. Prompts when apps attempt to make changes, but not when the user makes Windows setting changes. Uses secure desktop. Balances security with usability. The standard configuration for most environments.
Notify (no secure desktop)
Same as default but without the secure desktop (screen does not dim). The UAC prompt can be interacted with by other running programs — a security concern. Not recommended in general use.
Never notify
Least secure. Effectively disables UAC. No prompts for any elevation. Administrator users always run with full privileges. Equivalent to Windows XP behavior. Not recommended for any production environment. Only acceptable in tightly controlled scenarios with other compensating controls.
Control Panel → User Accounts → Change User Account Control settings   |   secpol.msc → Local Policies → Security Options (UAC policies)

SECTION 7Encryption — BitLocker, BitLocker-To-Go, and EFS

Windows provides three distinct encryption technologies, each serving a different scope and purpose. Understanding the difference between them, their hardware requirements, and their edition requirements is essential for this objective.

BitLocker Drive Encryption

BitLocker encrypts entire volumes (partitions) using AES encryption (128-bit or 256-bit). It protects data at rest — if a drive is removed from the machine and connected to another computer, the data is unreadable without the recovery key. The encryption is transparent to the user when the machine is running normally.

Control Panel → System and Security → BitLocker Drive Encryption   |   Manage-bde command-line tool
BitLocker Configuration Pro / Enterprise Only
Edition requirement
BitLocker is available only on Windows 10/11 Pro, Pro for Workstations, and Enterprise. Home editions have "Device Encryption" — a simplified, automatically enabled subset of BitLocker with fewer management options and no management interface. Device Encryption requires a Microsoft account for recovery key backup. Full BitLocker is not available on Home.
TPM requirement
BitLocker's default configuration requires a TPM 1.2 or later to store the encryption key. The TPM seals the key to the system's hardware state — if critical hardware changes, the TPM refuses to release the key and BitLocker enters recovery mode. BitLocker can be configured to run without a TPM using a startup key on a USB drive (requires Group Policy change: Require additional authentication at startup) but this reduces convenience and is non-standard.
Authentication modes
TPM only (transparent — no user interaction at boot). TPM + PIN (requires PIN entry before Windows loads — strong, recommended for laptops). TPM + USB key (requires USB drive inserted at boot). USB key only (no TPM; requires USB drive). Password (data-only volumes). TPM + PIN is the recommended mode for maximum security on laptop systems.
Recovery key
A 48-digit numerical recovery key is generated when BitLocker is enabled. This key can unlock the drive if the normal unlock method fails (lost PIN, hardware change, TPM malfunction). Store the recovery key securely — options include: save to Microsoft account (Home Device Encryption), save to Active Directory/Entra ID (enterprise — automatically stored when domain-joined), save to a file (USB, network location), or print. If the recovery key is lost and normal access fails, data is permanently inaccessible.
Enabling BitLocker
Control Panel → BitLocker Drive Encryption → Turn on BitLocker for the desired volume. The wizard walks through TPM check, recovery key storage, encryption scope (used space only vs. full drive — used space only is faster for new drives; full drive is better for drives with existing data that may contain recoverable deleted data), and encryption mode (XTS-AES for fixed drives, AES-CBC for removable drives for compatibility).

Exam Focus — BitLocker Recovery

BitLocker recovery mode triggers when: the PIN is entered incorrectly too many times, a hardware component changes (new motherboard, new TPM), the drive is moved to a different computer, or BIOS/UEFI settings change (Secure Boot toggled, boot order changed). The only way out is to enter the 48-digit recovery key. This is why recovery key management is critical — always ensure the key is stored in a retrievable location before enabling BitLocker.

BitLocker-To-Go

BitLocker-To-Go extends BitLocker encryption to removable storage devices — USB flash drives, external hard drives, and SD cards. It protects data on portable media that is easily lost or stolen.

BitLocker-To-Go Pro / Enterprise Only (to encrypt)
Encrypting
Connect the removable drive → Control Panel → BitLocker Drive Encryption → Turn on BitLocker for the removable drive. Authentication uses a password or smart card (no TPM for removable media). The drive is encrypted with AES and is unreadable without the password or recovery key.
Reading on other machines
Any Windows machine can read a BitLocker-To-Go encrypted drive — even Windows Home. When connected, Windows prompts for the password. The user enters the password and the drive mounts transparently. The ability to encrypt a drive requires Pro or Enterprise; the ability to read it does not.
Group Policy enforcement
In enterprise environments, Group Policy can enforce that removable drives must be encrypted with BitLocker-To-Go before files can be written to them (Deny write access to removable drives not protected by BitLocker). This prevents sensitive data from being written to unencrypted USB drives — a DLP-style control enforced at the OS level.

Encrypting File System (EFS)

The Encrypting File System (EFS) is an NTFS feature that encrypts individual files and folders using certificate-based encryption tied to a specific user account. Unlike BitLocker (which encrypts an entire volume), EFS encrypts selectively at the file/folder level and is transparent only to the user whose certificate was used to encrypt the files.

EFS — Encrypting File System Pro / Enterprise Only
How it works
When a user encrypts a file with EFS: a File Encryption Key (FEK) is generated and used to encrypt the file content with AES. The FEK is then encrypted with the user's public key from their EFS certificate and stored in the file's header. To open the file, the user's private key decrypts the FEK, which then decrypts the file. The process is entirely transparent to the encrypting user — they see no prompts when opening EFS-encrypted files. Other users see "Access Denied" when trying to open the file, even administrators (unless they have the recovery agent certificate).
Enabling EFS
Right-click a file or folder → Properties → General tab → Advanced → check "Encrypt contents to secure data" → OK → Apply. Windows prompts to encrypt the file only or the file and its parent folder (encrypting the folder is recommended so future files placed there are automatically encrypted). Encrypted files appear in green text in File Explorer by default.
EFS certificate management
EFS certificates are stored in the user's certificate store (certmgr.msc → Personal → Certificates). If the user's profile is deleted or the EFS certificate is lost, the encrypted files are permanently inaccessible — even to administrators — unless a Data Recovery Agent (DRA) certificate has been configured via Group Policy. Always back up EFS certificates before deleting user profiles or reformatting machines.
EFS vs. BitLocker
EFS: per-file/folder, user-specific, survives across sessions (encrypted even when logged in on same machine as different user), requires no additional hardware, manageable without admin rights. BitLocker: entire volume, transparent to all users of the volume, requires TPM for full protection, protects against physical theft of the drive. They can be used simultaneously — BitLocker encrypts the volume and EFS provides additional per-user file encryption within it.

EFS Gotcha — Moving Encrypted Files

If a user copies an EFS-encrypted file to a FAT32 or exFAT volume (USB drive, for example), the file is automatically decrypted because those file systems do not support EFS. This is a data leakage risk — a user can unknowingly expose encrypted files by copying them to an unencrypted USB drive. BitLocker-To-Go on the USB drive would prevent the data from being readable if the drive is lost, but the file itself would no longer be EFS-encrypted on the USB volume.

SECTION 8Active Directory

Active Directory (AD) is Microsoft's directory service that provides centralized identity management, authentication, and policy enforcement for domain-joined Windows machines. In a domain environment, a technician's day-to-day AD tasks are performed using Active Directory Users and Computers (ADUC) — the primary management console for managing users, computers, groups, and organizational units.

Active Directory Users and Computers (dsa.msc) — run on Domain Controller or from RSAT tools on a workstation

RSAT — Remote Server Administration Tools

Active Directory management tools (including ADUC) are not installed on standard Windows workstations. Administrators install RSAT (Remote Server Administration Tools) — available as an optional feature in Settings → Apps → Optional features — to manage AD from their workstation without being physically present at a Domain Controller. RSAT includes ADUC, Group Policy Management Console (GPMC), and other management tools.

Joining a Domain

A Windows PC must be explicitly joined to an Active Directory domain before it can use domain accounts, receive Group Policy, and access domain resources. Domain join requires administrator credentials (either local admin or domain admin, depending on environment policy) and network connectivity to a Domain Controller.

Joining a Domain — Step by Step
01
Verify prerequisites: The machine must have a static IP or reliable DHCP. DNS must be configured to point to the domain's DNS server (which is typically the Domain Controller). If DNS is wrong, domain join will fail with a "domain controller not found" error.
02
Navigate to System Properties: Settings → System → About → Join a domain (Windows 10/11). Alternatively: Control Panel → System → Change settings → Computer Name tab → Change.
03
Enter the domain name (e.g., corp.contoso.com). Windows contacts the domain's DNS server to locate a Domain Controller via SRV records.
04
Authenticate with domain credentials. A domain administrator account (or an account with the "Add workstations to domain" right) must provide credentials. By default, each standard domain user can join up to 10 machines.
05
Restart the machine. Domain join completes after a reboot. After reboot, users can log in with domain credentials and the machine appears in the default "Computers" container in ADUC.
06
Move the computer account from the default Computers container to the appropriate Organizational Unit (OU) so that the correct Group Policy Objects are applied to it.

Organizational Units (OUs) and Moving Objects

An Organizational Unit (OU) is a container within Active Directory used to organize objects (users, computers, groups) hierarchically. OUs reflect the organization's structure — by department (Finance, Engineering, HR), by location (NewYork, London), or by function (Servers, Workstations, Laptops). Group Policy Objects are linked to OUs, so an object's OU placement determines which policies it receives.

Managing Objects in ADUC ADUC (dsa.msc)
Moving objects between OUs
Right-click a user, computer, or group in ADUC → Move → select the destination OU. The object immediately receives the Group Policy of its new OU at the next policy refresh (or after gpupdate /force). Moving a laptop computer from the "Standard Workstations" OU to the "Executive Laptops" OU instantly changes which Group Policies apply to that machine — for example, more restrictive policies or BitLocker enforcement.
Creating OUs
Right-click the domain or parent OU in ADUC → New → Organizational Unit. Enable "Protect container from accidental deletion" — this adds a Deny delete ACE on the OU that prevents accidental removal of an OU with objects in it (a catastrophic error that deletes all objects in the OU). Requires unchecking in Advanced Features → Properties → Object tab to delete a protected OU.
Finding objects
ADUC → right-click domain or OU → Find (Ctrl+F in newer versions). Search by name, username, email, SID, or other attributes. Faster than manually navigating the OU tree in large environments with thousands of objects.

Assigning Login Scripts

A logon script is a batch file (.bat), VBScript (.vbs), or PowerShell script (.ps1) that runs automatically when a user logs in. It can map network drives, connect to printers, set environment variables, or perform any automated task. Login scripts are assigned per-user in their AD account properties.

Logon Script Assignment ADUC → User → Profile tab
Assigning via ADUC
ADUC → find the user → double-click → Profile tab → Logon script field. Enter the script filename (e.g., login.bat). The script must be stored in the NETLOGON share on the domain controller (\\domain\NETLOGON, which maps to %SystemRoot%\SYSVOL\sysvol\domain\scripts). Windows automatically looks for the script in NETLOGON, so only the filename is needed — not the full path.
Group Policy scripts
A more flexible alternative: Group Policy → User Configuration → Windows Settings → Scripts → Logon. Scripts assigned here apply to all users in the linked OU, not individual users. Supports PowerShell scripts. Preferred for new deployments over per-user logon scripts in ADUC.

Assigning Home Folders

A home folder is a personal network share assigned to each user where they store their documents. Centralizing user documents on a file server ensures they are backed up with server backup routines and accessible from any domain-joined machine the user logs into.

Home Folder Configuration ADUC → User → Profile tab
Assigning in ADUC
ADUC → User → Profile tab → Home folder section → select Connect → choose a drive letter (commonly H:) → enter the UNC path: \\fileserver\users\%username%. The %username% variable automatically substitutes the user's login name, creating a unique path for each user. When saved, ADUC creates the folder on the server automatically and sets the correct NTFS permissions (the user has Full Control of their folder).
Benefits
User files are stored on the server rather than the local machine. Roaming users log into any workstation and their H: drive is always available. IT can back up all user data from the central file server. Departing user data is preserved on the server even after the workstation is reimaged. Disaster recovery of user data is simplified.

Applying Group Policy

Group Policy is the primary mechanism for applying security settings and configuration to domain-joined computers and users at scale. A Group Policy Object (GPO) is a collection of settings that is linked to a container in Active Directory (domain, site, or OU). All objects in that container receive the GPO's settings.

Group Policy Application Group Policy Management Console (gpmc.msc)
LSDOU processing order
GPOs are applied in this order: Local policy → Site → Domain → OU (and nested OUs, from parent to child). Later-applied policies override earlier ones for conflicting settings. This means OU-level GPOs generally win over domain-level GPOs for the same setting. Remember: LSDOU — "Last applied wins" for non-conflicting settings.
Linking GPOs
gpmc.msc → right-click an OU → Link an Existing GPO (or Create a GPO and link it here). Linking connects the GPO to that container. A single GPO can be linked to multiple OUs. Multiple GPOs can be linked to a single OU — processed by link order (lower number = processed last = wins for conflicts).
Enforced & Block Inheritance
Enforced (formerly "No Override"): the GPO's settings cannot be overridden by lower-level GPOs. Block Inheritance: set on an OU to prevent higher-level GPOs from applying to it (except Enforced GPOs, which bypass Block Inheritance). Use sparingly — complex inheritance configurations are difficult to troubleshoot.
Loopback processing
Normally, Computer Configuration GPOs apply to the computer and User Configuration GPOs apply to the user (from the user's OU). Loopback processing reverses or merges this — it applies the User Configuration settings from the computer's OU to the user, regardless of which OU the user account lives in. Used for kiosk machines, terminal servers, and lab computers where the machine's purpose defines the user experience regardless of who logs in.

Security Groups

Security groups in Active Directory are containers that collect user accounts (and other security principals) to manage permissions efficiently. Instead of assigning permissions directly to individual users, permissions are assigned to groups, and users are made members of the appropriate groups.

Security Group Types and Scopes ADUC → New → Group
Global groups
Contain members from the same domain. Used to organize users by job function or department. Can be granted access to resources in any domain in the forest. Example: "G_Finance_Analysts" in the CORP domain contains all finance analysts in CORP.
Domain Local groups
Can contain members from any domain. Used to assign permissions to resources in the local domain. Best practice: assign permissions to Domain Local groups, then add Global groups to the Domain Local group. Example: "DL_FileShare_FinanceDocs_Read" grants read access to the finance docs share; the G_Finance_Analysts global group is added as a member.
Universal groups
Can contain members from any domain in the forest and can be granted access to resources in any domain. Used in multi-domain forests to aggregate access across domains. Universal group membership is stored in the Global Catalog — changes to universal groups trigger Global Catalog replication across all DCs in the forest, so they should be used judiciously.
A-G-DL-P best practice
The recommended group nesting strategy: Accounts → Global groups → Domain Local groups → Permissions. Users go in Global groups by department; Global groups go into Domain Local groups that define access to specific resources; Domain Local groups are assigned permissions on files, folders, and printers. This structure simplifies access changes — moving a user to a different global group changes all their resource access automatically.

Folder Redirection

Folder Redirection is a Group Policy feature that transparently redirects Windows special folders (Documents, Desktop, Downloads, AppData, etc.) from the user's local profile to a network location. The user's documents appear to be local but are physically stored on a file server.

Configuring Folder Redirection GPMC → User Configuration → Windows Settings → Folder Redirection
Configuration path
Group Policy Management Console → edit a GPO → User Configuration → Policies → Windows Settings → Folder Redirection. Right-click a folder (e.g., Documents) → Properties → Setting: Basic (same location for everyone) or Advanced (different locations by security group membership). Target: \\fileserver\homeshares\%username%\Documents.
Benefits
Roaming: users access their documents from any machine. Backup: IT backs up the file server, not individual workstations. Disaster recovery: workstation failure or theft does not result in data loss — documents are on the server. Performance: eliminates the need for full roaming profiles (which copy the entire profile at login/logoff, causing slow logons for large profiles).
Offline Files integration
Folder Redirection typically works with Offline Files (Client-Side Caching) — a feature that caches the redirected folder contents locally so users can work offline (disconnected from the network). Changes sync to the server when reconnected. Configured in the same Folder Redirection GPO settings or separately via Group Policy → Offline Files.
Removing redirection
If Folder Redirection is removed from a GPO, the "Policy Removal" setting determines what happens: Redirect the folder back to local (copies files back to the local profile) or Leave the folder in the new location (server). The redirect-back option is safer — it ensures the user's documents follow them.

High-Probability Exam Scenarios

Scenario 1: User cannot connect to a network application after Firewall was enabled → Create an inbound allow rule in wf.msc for the application or its port.
Scenario 2: Third-party AV subscription expires; machine shows Defender is off → Renew AV or re-enable Defender real-time protection in Windows Security.
Scenario 3: Standard user needs to install software → They cannot; admin must either perform the install or use Run as administrator with admin credentials (over-the-shoulder).
Scenario 4: User copies a file from an NTFS folder with Full Control (share) to another with Read (NTFS) — effective access = Read.
Scenario 5: Laptop is stolen; data must be protected → BitLocker (if Pro edition). Recovery key storage is critical before enabling.
Scenario 6: User leaves company; their EFS-encrypted files must be accessible → The DRA (Data Recovery Agent) certificate is required; or export the user's EFS certificate before deleting the profile.
Scenario 7: A new computer is not receiving the correct GPOs → Verify the computer account is in the correct OU; run gpupdate /force; check gpresult /r.
Scenario 8: User's Documents folder should be stored on the server for backup → Configure Folder Redirection via Group Policy.
Scenario 9: UAC prompt keeps appearing when running an application → The application requires elevation; add it to an elevated shortcut or investigate whether it was designed to run as standard user.
Scenario 10: Windows Hello PIN doesn't work after hardware replacement → TPM change triggers Windows Hello re-enrollment; user must set up their PIN again.
