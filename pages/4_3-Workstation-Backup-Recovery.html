OVERVIEWIntroduction to Backup and Recovery

A backup is a copy of data kept separately from the original, so that if the original is lost, corrupted, encrypted by ransomware, or destroyed, the data can still be recovered. Every other security control covered elsewhere in the A+ objectives — antivirus, firewalls, hardening, user education — is about preventing bad things from happening. Backup and recovery is the control that assumes prevention will eventually fail anyway, and makes sure that failure doesn't mean permanent data loss.

Objective 4.3 covers four connected pieces of this discipline. Backup types defines the different methods of capturing data (full, incremental, differential, synthetic full), each trading off backup speed, storage space, and restore complexity differently. Recovery covers where restored data actually gets written back to. Backup testing addresses the uncomfortable truth that a backup nobody has verified is not a backup — it's a hope. And backup rotation schemes covers how organizations manage many backups over time without either running out of storage or accidentally deleting the one backup they needed.

Core Concept — A Backup Strategy Is a Set of Trade-Offs

There is no single "best" backup type or schedule — every choice in this objective trades something against something else. Full backups are simple to restore but slow and storage-heavy to create. Incremental backups are fast to create but slower and more complex to restore. Objective 4.3 tests whether you understand these trade-offs well enough to pick the right approach for a described scenario, not just whether you can recite definitions.

SECTION 1Backup Types

Each backup type differs in exactly which data gets copied during a given backup run, which in turn determines how long the backup takes, how much storage it consumes, and how complicated recovery is afterward.

Full Backup

Full BackupCopies everything, every time
What it captures A complete copy of all selected data, every single time the backup runs — regardless of what has or hasn't changed since the last backup
Backup time/storage Slowest to create and consumes the most storage of any backup type, since every run duplicates the entire data set again
Restore complexity Simplest possible restore — only the single most recent full backup is needed to fully recover the data

Incremental Backup

Incremental BackupCopies only what changed since the last backup (of any type)
What it captures Only the data that has changed since the most recent backup of any type — full or incremental — meaning each incremental backup only ever needs to look back to the one immediately before it
Backup time/storage Fastest to create and smallest in storage footprint of the traditional types, since each run only captures recent changes
Restore complexity Most complex restore — requires the last full backup plus every single incremental backup made since, applied in the correct order, since each one only contains changes relative to the last

Differential Backup

Differential BackupCopies everything changed since the last FULL backup only
What it captures All data that has changed since the last full backup — not since the last differential — so each differential backup grows larger the further it sits from the most recent full backup
Backup time/storage A middle ground: larger and slower than incremental (since it re-captures all changes since the full, not just since the last backup), but smaller and faster than another full backup
Restore complexity Middle ground — requires only the last full backup plus the single most recent differential backup, regardless of how many differentials have run since the last full

Synthetic Full Backup

Synthetic Full BackupAssembled from existing backups without touching the source
What it captures Effectively nothing new from the source system — a synthetic full is constructed by combining a previous full backup with subsequent incremental backups at the backup storage level, producing a backup that looks and restores exactly like a true full backup
Backup time/storage Avoids the production-system load and network transfer time of running a real full backup again, since the assembly happens on the backup storage itself rather than by re-reading the live source data
Restore complexity Same simplicity as a true full backup restore — a single, complete backup file to restore from — while gaining the speed/efficiency benefits of incremental backups on the front end

Exam Angle — The Restore-Complexity Trade-Off

This is the single most commonly tested distinction in Section 1: incremental backups are the fastest to create but the slowest/most complex to restore, because recovery means replaying the full backup plus every incremental since, in order. Differential backups split the difference — slower to create than incremental since they re-capture all changes since the full each time, but faster to restore since only the full plus the single latest differential are needed. If a scenario emphasizes fast nightly backups with a tolerance for a longer restore process, that's incremental; if it emphasizes fast, simple restores with some tolerance for larger backup windows, that's differential or full.

SECTION 2Recovery

Once a backup exists, recovery is the act of actually restoring that data. The exam distinguishes two destinations a restore can target.

In-Place/Overwrite Recovery

  • What happens — restored data is written directly back to its original location, overwriting whatever currently exists there
  • Common use case — recovering after data corruption or accidental deletion, where the goal is simply to return the original location to its last-known-good state
  • Risk — destroys whatever is currently in that location, so it should only be used once you're confident the current data is not worth keeping

Alternative Location Recovery

  • What happens — restored data is written to a different location than the original (a different folder, drive, or even a separate machine), leaving the original location untouched
  • Common use case — verifying a backup's integrity, recovering a single file without disturbing the current state of everything else, or investigating an incident where the original location itself may be compromised
  • Benefit — allows side-by-side comparison between the restored data and whatever currently exists, and avoids destroying evidence during an active investigation

Choosing Between the Two — A Ransomware Example

If a workstation has been hit by ransomware, restoring in-place immediately would overwrite the encrypted files — which might still be useful for a forensic investigation or in case a future decryption tool becomes available. Restoring to an alternative location first (or to a separate clean machine) lets a technician recover the user's data without destroying that evidence, and only move the restored copy into place once the original system has been fully wiped and rebuilt.

SECTION 3Backup Testing

A backup that has never been tested is only a theoretical backup. Backup testing means periodically attempting an actual restore from a backup — not just confirming the backup job completed without errors — to verify that the data is genuinely recoverable and usable when it's actually needed.

Frequency How often backup testing is performed is itself a deliberate decision, balancing the assurance a fresh test provides against the time and resources testing consumes. Critical systems typically warrant more frequent test restores than low-priority ones, and testing frequency is often documented as part of an organization's broader backup policy alongside the backup schedule itself.

The Failure Mode Backup Testing Exists to Prevent

It is entirely possible for a backup job to report "success" every night for months while actually producing corrupted, incomplete, or unusable backup files — a bad drive, misconfigured software, or a silently failing agent can all cause this. The organization only discovers the problem the moment it actually needs to restore something, which is the worst possible time to learn a backup doesn't work. Regularly scheduled test restores are the only way to catch this before a real emergency does.

SECTION 4Backup Rotation Schemes

Keeping every backup ever made forever is neither practical nor necessary — storage costs money, and most organizations only need a defined window of recovery points. Backup rotation schemes are the strategies for managing which backups get kept, for how long, and where, so that storage stays manageable while still preserving enough recovery points to be useful.

Onsite vs. Offsite

Onsite Backup

  • Location — stored at the same physical location as the original data (e.g., a local NAS or backup server in the same building)
  • Advantage — fastest to access and restore from, since there's no transfer time over a WAN link
  • Weakness — vulnerable to any event that affects the entire site — fire, flood, theft, a building-wide power event — which could destroy the original data and the onsite backup simultaneously

Offsite Backup

  • Location — stored at a different physical location, or in the cloud, away from the original data
  • Advantage — survives a site-wide disaster that destroys the original location entirely
  • Weakness — typically slower to restore from due to data transfer time, and may involve ongoing storage/transfer costs

Grandfather-Father-Son (GFS)

The Grandfather-Father-Son (GFS) rotation scheme organizes backups into three tiers based on age and retention length, giving an organization a mix of recent short-term recovery points and older long-term archives without keeping every single backup ever made.

Son
Daily

The most frequent tier — typically a daily backup, kept for a short retention period (e.g., one to two weeks) before being overwritten or discarded

Father
Weekly

One backup retained per week, kept for a longer period than the daily "son" backups (e.g., a month), representing a slightly longer-term recovery point

Grandfather
Monthly

One backup retained per month (often the full backup), kept for the longest period of the three tiers — sometimes a year or more — serving as the long-term archive

Why GFS Matters — Balancing Recency and Depth

GFS solves a real tension: recent daily backups matter most for everyday accidental-deletion recovery, but a serious data-corruption or ransomware event might not be discovered for weeks — by which point every recent daily backup could already be compromised too. Retaining older weekly and monthly tiers gives an organization a fallback recovery point from further in the past, precisely for the scenario where the problem isn't caught right away.

3-2-1 Backup Rule

The 3-2-1 backup rule is a widely used guideline for how many copies of data to keep, on what kind of media, and in how many locations, to minimize the chance that any single event wipes out every copy at once.

3
Copies
Keep at least three total copies of the data — the original plus two backups
2
Media Types
Store those copies on at least two different types of storage media, so a flaw affecting one media type doesn't destroy every copy
1
Offsite Copy
Keep at least one copy offsite, away from the original, to survive a site-wide disaster

3-2-1 in Practice

A typical real-world 3-2-1 setup: the original data on a workstation's internal drive (copy one), a nightly backup to a local external drive or NAS using different media (copy two), and a cloud backup or a rotated drive stored at a different physical location (copy three, satisfying both the second media type and the offsite requirement). The rule is deliberately simple to remember precisely so it gets followed consistently rather than skipped for being too complicated.

REFERENCEQuick Reference Cards

Backup Type Decision Guide

  • Simplicity of restore matters most — full backup
  • Backup window/storage is tight, restore speed is secondary — incremental
  • Want a balance of both — differential
  • Want full-backup simplicity without re-reading the whole source — synthetic full

Recovery Destination Decision Guide

  • Confident current data is worthless/corrupted — in-place/overwrite
  • Need to preserve evidence or compare before committing — alternative location
  • Investigating a possible security incident — always alternative location first

Backup Testing Reminders

  • "Backup job succeeded" ≠ "backup is restorable" — test actual restores
  • Test frequency should match system criticality — more critical, more frequent
  • The worst time to discover a bad backup — during a real emergency

Rotation Scheme Cheat Sheet

  • GFS tiers, shortest to longest retention — Son (daily) → Father (weekly) → Grandfather (monthly)
  • 3-2-1 rule — 3 copies, 2 media types, 1 offsite
  • Fastest restore location — onsite
  • Disaster-survival location — offsite

Final Exam Reminders

Incremental backups reference the last backup of any type; differential backups always reference the last full backup — this single distinction is the most frequently tested detail in Section 1, and it's also exactly why incremental restores need every incremental in sequence while differential restores only need the latest one.

A synthetic full backup is built from existing backup data, not by re-reading the live source system — it gives you full-backup-style restore simplicity while keeping the lighter backup-window footprint of incrementals.

Alternative location recovery is the safer default whenever evidence preservation or verification matters — ransomware, suspected compromise, or simply double-checking a backup's integrity before committing to overwrite production data.

A backup that has never been test-restored should not be trusted — "the backup job completed successfully" is not the same claim as "the data is recoverable," and the exam expects you to recognize backup testing as a distinct, necessary step.

Onsite backups are fast but share fate with the original in a site-wide disaster; offsite backups survive that disaster but restore more slowly — most real strategies use both for exactly this reason, which is also why the 3-2-1 rule explicitly requires at least one offsite copy.

GFS gives you daily, weekly, and monthly recovery points simultaneously — remember the retention order (son = shortest/daily, father = medium/weekly, grandfather = longest/monthly) rather than just the names.

The 3-2-1 rule is about copies, media types, and location — not about backup type (full/incremental/etc.) — don't conflate 3-2-1 with the Section 1 backup types; they answer different questions and can be combined freely.
