OVERVIEWIntroduction

Objective 1.10 steps back from any single operating system (covered individually in 1.7–1.9) to address a universal pre-installation discipline: before installing any application, on any platform, a technician needs to verify the target system actually meets that application's requirements, choose an appropriate distribution method, and think through the broader impact that installing new software might have — on the device itself, the network, business operations, and ongoing operational workflow.

This objective rewards a methodical, "look before you leap" mindset. A scenario describing a failed or problematic installation is very often really testing whether you'd have caught the issue beforehand by checking the right requirement, or whether you considered a consequence of the installation that wasn't obvious at first glance.

PART 1System Requirements for Applications

Every application publishes (or implies) a set of minimum and/or recommended system requirements. Verifying these against the target system before attempting installation is the most basic, most frequently skipped step in real-world application deployment — and a frequent source of exam scenarios describing installation failures or poor post-install performance.

System Requirements Checklist

0132-bit vs. 64-bitSome applications require a 64-bit operating system specifically (objective 3.5's x86/x64 concepts) and will not install — or will install but fail to run correctly — on a 32-bit OS. A 64-bit OS can generally run most 32-bit applications, but the reverse is not true.
02Dedicated vs. integrated graphicsGraphics-intensive applications (CAD software, video editing, 3D rendering, many modern games) often require or strongly recommend a dedicated GPU (objective 3.5's expansion card concepts) rather than relying on a CPU's built-in integrated graphics, which share system resources and generally offer far less graphics performance.
03VRAM requirementsVideo RAM — dedicated memory built into a graphics card, used to store textures, frame buffers, and other graphics data. Graphics-intensive applications often specify a minimum VRAM amount, distinct from a system's regular system RAM (objective 3.3); insufficient VRAM can cause poor performance, visual artifacts, or an application's failure to launch at all.
04RAM requirementsThe minimum (and often separately listed recommended) system memory needed for acceptable performance, directly tied to objective 3.3's RAM concepts — insufficient RAM commonly causes sluggish performance, excessive use of slower disk-based virtual memory/paging, or outright failure to run memory-intensive applications.
05CPU requirementsMinimum processor speed, core count, architecture, or even specific supported CPU instruction sets (objective 3.5's CPU architecture/core configuration concepts) that an application needs to run acceptably, or at all.
06External hardware tokensSome specialized or licensed software (particularly certain professional, scientific, or security-sensitive applications) requires a physical hardware token — sometimes called a dongle — plugged into the system (commonly via USB) to unlock, license, or authenticate use of the software; without the token physically present, the application won't run regardless of how correctly everything else is configured.
07Storage requirementsThe disk space needed for installation itself, plus often additional working/temporary space needed during actual use (objective 3.4's storage concepts) — insufficient free storage is one of the most common, easily-overlooked causes of installation failure.
08Application-to-OS compatibilityWhether the application is actually built/certified to run on the target operating system and version at all (Windows vs. macOS vs. Linux, and often specific version ranges within each) — an application built exclusively for one OS family generally cannot simply be installed on another without compatibility layers, emulation, or a separate OS-specific version.

Exam Angle

A scenario describing a graphics-intensive application running poorly or refusing to launch despite "meeting the RAM and CPU requirements" should prompt checking VRAM and dedicated vs. integrated graphics specifically — these are easy to overlook since they're distinct from regular system RAM and general CPU specs, but are frequently the actual limiting factor for graphics-heavy software. Similarly, a scenario describing licensed software that "won't run" despite a clean install should prompt checking for a required hardware token.

PART 2Distribution Methods

Once requirements are confirmed, an application can be delivered to the target system through several different distribution methods, each suited to different scales and scenarios.

Physical Media vs. Mountable ISO File

MethodDescriptionTypical Use Today
Physical mediaA physical disc (CD, DVD, Blu-ray, objective 3.4) containing the installer, inserted into an optical driveLargely legacy; certain older software, specific business/institutional distribution requirements, or systems lacking other installation options
Mountable ISO fileA single file (.iso) that's an exact digital image of an optical disc's contents, "mounted" by the OS to behave as if a physical disc were inserted, without requiring any physical media or optical drive at allCommon today for OS installation media and software still distributed in a disc-image format, especially useful on modern laptops that often lack a built-in optical drive entirely

Downloadable Package

Software downloaded directly over the internet — an installer executable (Windows), a .dmg/.pkg (macOS, objective 1.8), a package installed via a package manager (Linux, objective 1.9), or an app obtained through a platform's app store. This is by far the most common modern distribution method for individual installations, requiring only an internet connection and no physical media at all.

Image Deployment

Image deployment installs a pre-configured, complete system image — potentially including the OS, standard applications, and baseline settings all bundled together — onto multiple machines at once, rather than installing applications individually one at a time on each system. This is the standard approach for organizations needing to provision many identical or near-identical machines efficiently (a school computer lab, a corporate fleet of standardized workstations), dramatically reducing the time and manual effort compared to performing individual installations on every single device.

Choosing a Distribution Method By Scale

Think of these methods along a spectrum of scale: a downloadable package suits installing software on one (or a handful of) individual machines; physical media/ISO suits situations without reliable internet access or specific legacy/compliance requirements; image deployment suits provisioning many machines at once with a consistent, standardized configuration. A scenario describing setting up dozens or hundreds of identical new computers for an organization points toward image deployment as the efficient answer, not individually downloading and installing software on each one.

PART 3Impact Considerations for New Applications

Beyond simply confirming an application can be installed, a thoughtful technician considers the broader consequences of actually installing it — across four distinct dimensions of potential impact.

DEVICE

How the new application affects the specific device it's installed on — consuming storage space and system resources (RAM, CPU, battery life on a laptop), potentially conflicting with existing installed software, or affecting overall system stability and performance.

NETWORK

How the application affects network resources — bandwidth consumption (especially for large initial downloads, ongoing sync, or cloud-connected features), the need to open specific firewall ports or exceptions (objective 1.7's firewall concepts) for the application to function, or additional network traffic load if deployed across many machines simultaneously.

OPERATION

How installing the application affects ongoing day-to-day workflows and operations — whether installation requires a system restart that interrupts active work, whether existing processes/workflows need to be retrained or adjusted around the new software, and whether installation should be scheduled during a maintenance window to minimize disruption.

BUSINESS

Broader organizational considerations — licensing costs and compliance, whether the application fits existing IT governance/security policy, support and maintenance burden going forward, and whether the software introduces any new compliance, data-handling, or vendor-risk considerations for the organization as a whole.

Exam Angle

A scenario asking "what should be considered before deploying this application across the organization" is testing whether you think beyond the single machine in front of you — does it need new firewall rules (network)? Will it require retraining staff or interrupt current work (operation)? Does it introduce new licensing costs or policy concerns (business)? Will it strain the hardware it's running on (device)? Strong answers to these scenarios typically touch more than one of these four categories rather than focusing narrowly on just the installation mechanics.

Tying It All Together

These three parts of the objective form a natural sequence a technician would actually follow in practice: first confirm the application's system requirements are met (Part 1), then choose the appropriate distribution method for the situation and scale (Part 2), and finally think through the broader impact the installation will have beyond just "does it install successfully" (Part 3). Treating this as a deliberate, ordered process — rather than three disconnected bullet lists — reflects the real-world workflow the exam is ultimately testing.

REFERENCE1.10 Quick Reference

Easy-to-Miss Requirements

  • Graphics app runs poorly despite "enough RAM" → Check VRAM/dedicated GPU
  • Licensed software won't launch → Check for required hardware token
  • Install fails partway through → Check storage space

Distribution Method By Scenario

  • One machine, internet available → Downloadable package
  • No internet, legacy/compliance need → Physical media/ISO
  • Many identical machines at once → Image deployment

Impact Considerations — Four Angles

  • Device → Resources, storage, stability
  • Network → Bandwidth, firewall rules
  • Operation → Downtime, workflow, training
  • Business → Licensing, compliance, support cost

The Three-Step Process

  • 1. Verify system requirements
  • 2. Choose the right distribution method
  • 3. Consider broader impact before deploying

Final Exam Reminders

64-bit OS generally runs 32-bit apps; a 32-bit OS cannot run apps requiring 64-bit.

VRAM is dedicated graphics memory, separate from regular system RAM — don't conflate the two when troubleshooting graphics-heavy software.

Hardware tokens = some licensed software simply won't run without the physical token present, regardless of correct software configuration.

ISO files = the modern, driveless equivalent of physical installation media.

Image deployment = the efficient choice for provisioning many machines identically at once, instead of individual installs.

Four impact categories = Device, Network, Operation, Business — a thorough pre-deployment answer typically considers more than one.
