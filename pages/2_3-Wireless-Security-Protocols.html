OVERVIEWIntroduction

Wireless networks present a unique security challenge: unlike wired networks where an attacker must physically connect a cable, wireless signals propagate through walls and into public spaces, making them inherently accessible to anyone within range. The security mechanisms that protect wireless networks — and the authentication systems that control who can access both wireless and wired network resources — are the subject of this objective.

Objective 2.3 tests two distinct but related topics: wireless encryption protocols (the mechanisms that protect data in transit over Wi-Fi), and centralized authentication systems (the server-based systems that verify user identity for network access). Understanding how they evolved, why older protocols are broken, and which components belong to each system is what the "compare and contrast" verb demands.

How This Objective Is Tested

Expect scenario questions identifying which protocol is most secure, which authentication system is appropriate for a given environment, and the key technical differentiators between RADIUS and TACACS+. The evolution from WEP to WPA to WPA2 to WPA3 — and specifically why each step was necessary — is the most important narrative to understand. Know: TKIP = broken/legacy, AES = current standard, WPA3 = latest, RADIUS = network access control, TACACS+ = device administration control, Kerberos = domain ticket-based auth.

SECTION 1The Evolution of Wireless Security Protocols

Wi-Fi security protocols have gone through four generations, each introduced to address fundamental cryptographic flaws discovered in the previous generation. WEP — The Broken Foundation

Wired Equivalent Privacy (WEP) was the first Wi-Fi security standard, ratified in 1997 as part of the original IEEE 802.11 specification. Its name expressed its design goal — to provide wireless networks with security equivalent to that of a wired network. It failed catastrophically at this goal.

WEP used the RC4 stream cipher with a static 40-bit (later 104-bit) encryption key shared among all clients. The fatal flaw was in how it generated its initialization vectors (IVs) — the random values used to vary each packet's encryption. WEP's 24-bit IVs were too short, meaning they repeated frequently on busy networks. By collecting enough packets with repeated IVs, an attacker could perform statistical analysis to recover the shared encryption key. Tools like Aircrack-ng can crack WEP in minutes using captured traffic from a moderately busy network.

WEP on the Exam

WEP is mentioned here as context for understanding why the subsequent protocols exist. The exam does not test WEP configuration. What you must know: WEP is broken and must never be used. Any scenario mentioning WEP as a security option requires choosing a different protocol. WEP cannot be "fixed" by using a longer key or rotating passwords — the cryptographic flaw is fundamental to its design.

SECTION 2WPA2 — Wi-Fi Protected Access 2

Wi-Fi Protected Access 2 (WPA2), standardized as IEEE 802.11i in 2004, replaced both WEP and the interim WPA standard. WPA2 was the dominant enterprise and consumer wireless security standard for over a decade and remains widely deployed. Its most significant advancement was replacing the broken RC4/TKIP encryption used by WEP and WPA with the substantially stronger AES-based CCMP encryption.

WPA2

Core encryption
CCMP (Counter Mode with Cipher Block Chaining Message Authentication Code Protocol) — the encryption and integrity protection mechanism used by WPA2. Built on AES (Advanced Encryption Standard) with 128-bit keys in Counter Mode (CTR) for confidentiality, plus CBC-MAC for message integrity. CCMP addresses every weakness of TKIP and WEP — proper IV management, strong message integrity, and a cryptographically sound cipher.
Personal mode (WPA2-PSK)
Pre-Shared Key (PSK) mode — a single shared passphrase (8–63 ASCII characters) is configured on the access point and all clients. The passphrase is used to derive the Pairwise Master Key (PMK), which seeds the 4-way handshake to establish session keys. No authentication server required. Used in homes and small offices. Weaknesses: all clients share the same key (if it's exposed, the entire network is compromised); vulnerable to offline dictionary attacks against captured 4-way handshake packets.
Enterprise mode (WPA2-802.1X)
802.1X authentication — each user authenticates individually with unique credentials (username/password or certificate) via a RADIUS server. No shared key — compromise of one user's credentials does not expose other users' traffic. Uses EAP (Extensible Authentication Protocol) as the framework. Standard for corporate wireless networks. Requires RADIUS server infrastructure. Also called WPA2-Enterprise.
Known weaknesses
KRACK (Key Reinstallation Attack, 2017) — a vulnerability in the WPA2 4-way handshake that allows an attacker to decrypt traffic under certain conditions. Mitigated by OS and firmware patches. PMKID attack — allows offline cracking of WPA2-PSK without needing a captured 4-way handshake. The weakness of WPA2-Personal against dictionary attacks on weak passphrases remains the primary practical concern.
Backward compatibility
WPA2 access points can optionally support WPA/WPA2 mixed mode — allowing older WPA-only devices to connect using TKIP while newer devices use AES/CCMP. Mixed mode is a security downgrade; disable WPA if the network does not have legacy clients that require it.

SECTION 3WPA3 — Wi-Fi Protected Access 3

Wi-Fi Protected Access 3 (WPA3) was introduced by the Wi-Fi Alliance in 2018 and has been mandatory for Wi-Fi Certified devices since 2020. WPA3 addresses the remaining weaknesses of WPA2 — particularly the offline dictionary attack vulnerability in Personal mode and the absence of forward secrecy — while introducing new features for open networks and simplifying device onboarding.

WPA3

SAE — Personal mode
Simultaneous Authentication of Equals (SAE) — replaces the WPA2-PSK pre-shared key handshake with a more secure key exchange based on the Dragonfly handshake (an implementation of the PAKE — Password Authenticated Key Exchange protocol). The key improvement: even if an attacker captures the authentication exchange, they cannot perform an offline dictionary attack. Each authentication attempt requires active interaction with the access point — limiting brute-force attacks to real-time attempts, not offline cracking.
Forward secrecy
WPA3 provides forward secrecy (also called perfect forward secrecy) — each session uses unique encryption keys derived freshly for that session. Even if the network password is later compromised, previously captured traffic cannot be retroactively decrypted. WPA2-PSK lacked this property — if you captured traffic and later obtained the password, you could decrypt all previously captured sessions.
WPA3-Enterprise
Uses 192-bit security mode with AES-256/GCMP-256 encryption and SHA-384 for integrity. Designed to meet requirements of government, defense, and financial sector environments requiring CNSA (Commercial National Security Algorithm) suite compliance. Optional in standard enterprise deployments — WPA3-Enterprise can also operate with the standard 128-bit security level.
OWE — Open networks
Opportunistic Wireless Encryption (OWE) — a WPA3 feature for open (no-password) networks like guest Wi-Fi and public hotspots. OWE establishes an encrypted connection for each client without requiring any password, protecting traffic from passive eavesdropping by other clients on the same network. In WPA2, open networks transmitted all data in plaintext — anyone nearby with a packet capture tool could read all traffic. OWE eliminates this.
Wi-Fi Easy Connect (DPP)
Device Provisioning Protocol (DPP) — simplifies connecting IoT devices that lack screens or keyboards (smart light bulbs, thermostats, cameras) to WPA3 networks. A QR code or NFC tap on the device's packaging or housing is scanned or tapped with a smartphone acting as a configurator to securely provision the device's network credentials.
Transition mode
WPA3-capable access points can operate in WPA2/WPA3 transition mode, allowing WPA2-only devices to still connect while WPA3 clients use the stronger protocol. This backward compatibility is important during the transition period as older devices are replaced.

Exam Focus — WPA2 vs. WPA3 Key Differences

The exam tests specific technical differences, not just "WPA3 is newer." Know these three: (1) SAE vs. PSK — WPA3-Personal uses SAE (immune to offline dictionary attacks); WPA2-Personal uses PSK (vulnerable). (2) Forward secrecy — WPA3 has it, WPA2 does not. (3) Open network encryption — WPA3 supports OWE for encrypted open networks; WPA2 open networks are plaintext. In a scenario asking which to choose, WPA3 is always preferred when hardware supports it.

SECTION 4TKIP — Temporal Key Integrity Protocol

Temporal Key Integrity Protocol (TKIP) was an interim security measure introduced with the original WPA standard in 2003 as a software-based fix for WEP's cryptographic failures. Because WEP was so fundamentally broken, the industry needed an immediate fix that could be deployed as a firmware update to existing hardware — without waiting for the complete redesign that became WPA2/AES.

How TKIP improved on WEP
TKIP addressed WEP's specific weaknesses through three mechanisms: (1) Per-packet key mixing — instead of using the same key for every packet (WEP's fatal flaw), TKIP derives a unique 128-bit key for each packet by mixing the base key with the transmitter's MAC address and a sequence number. (2) Message Integrity Check (MIC) — called "Michael," a 64-bit message integrity code that detects packet tampering (WEP's CRC-32 could be easily manipulated). (3) Extended IV — 48-bit IVs instead of WEP's 24-bit IVs, dramatically reducing IV collision frequency.
Why TKIP is deprecated
TKIP retained RC4 as its underlying cipher — the same stream cipher used by the broken WEP protocol. While the per-packet key mixing addressed WEP's specific IV reuse attack, RC4 itself has deeper cryptographic weaknesses. In 2008 and 2009, researchers demonstrated practical attacks against TKIP. In 2012, the IEEE 802.11 standard formally deprecated TKIP, and in 2013 the Wi-Fi Alliance began requiring WPA2/AES certification. TKIP support was removed from the 802.11 standard in 2020.
Current recommendation
Disable TKIP entirely. If a network is running in WPA/TKIP or WPA2/TKIP (mixed mode), it should be configured to use WPA2/AES (CCMP) only. TKIP should only be enabled if there are legacy devices that absolutely require it and cannot be replaced — and even then, the risk should be formally accepted and the timeline for replacement documented.

SECTION 5AES — Advanced Encryption Standard

Advanced Encryption Standard (AES) is the symmetric block cipher that replaced DES (Data Encryption Standard) as the U.S. government's official encryption standard in 2001, following a public competition organized by NIST. AES is not a wireless protocol — it is a cipher that underlies multiple protocols and encryption systems, including WPA2's CCMP and WPA3's GCMP.

AES

Industry Standard Cipher
Type
Symmetric Block Cipher
Block Size

Key Sizes
128, 192, or 256 bits
AES-128
Used in WPA2/CCMP. 128-bit key — 10 rounds of transformations. Provides approximately 2128 possible keys. Considered computationally infeasible to brute-force with any foreseeable technology. Approved for SECRET-level classified U.S. government information.
AES-192
192-bit key — 12 rounds. Used in some higher-security configurations. Approved for TOP SECRET-level when combined with appropriate key management.
AES-256
256-bit key — 14 rounds. Used in WPA3-Enterprise (192-bit security suite). Maximum security level. The preferred choice when the additional computation cost is acceptable. Used in TLS 1.3, BitLocker, and many modern security protocols. Approved for TOP SECRET-level U.S. classified information.
AES in CCMP (WPA2)
WPA2 uses AES in Counter Mode (CTR) for encryption combined with CBC-MAC for integrity verification — together forming CCMP. CTR mode converts the block cipher into a stream cipher by encrypting a counter value and XORing the result with the plaintext — allowing parallelization and efficient encryption of variable-length data.
AES in GCMP (WPA3)
WPA3-Enterprise uses AES in Galois/Counter Mode (GCM), forming GCMP. GCM provides both encryption and authentication in a single pass and is more efficient than CCMP. WPA3-Enterprise's 192-bit mode uses GCMP-256 (AES-256 in GCM mode).
AES vs. RC4 (TKIP)
RC4 is a stream cipher — it generates a pseudorandom keystream that is XORed with the plaintext. It is fast in software but has been shown to have statistical biases and is vulnerable to key recovery attacks. AES is a block cipher with a far more complex and mathematically sound structure. For Wi-Fi, the transition from RC4/TKIP to AES/CCMP was the most significant security improvement in WPA2.

SECTION 6Authentication — RADIUS

Remote Authentication Dial-in User Service (RADIUS) is a client-server networking protocol that provides centralized Authentication, Authorization, and Accounting (AAA) services for network access. Originally designed for dial-in modem access, RADIUS has become the industry-standard protocol for authenticating users connecting to networks via Wi-Fi (WPA2/WPA3 Enterprise), VPN, 802.1X wired network access, and other network access scenarios.

RADIUS
Remote Authentication Dial-in User Service · RFC 2865/2866 · UDP 1812 (auth) / 1813 (accounting)
Network Access AAA
Role in the network
RADIUS sits between the Network Access Server (NAS) — the device users connect to (a wireless access point, VPN concentrator, or switch) — and the identity backend (Active Directory, LDAP directory, or a local user database). When a user attempts to connect, the NAS forwards their credentials to the RADIUS server, which authenticates them and returns an allow/deny decision along with authorization attributes (VLAN assignment, IP address pool, session time limit).
Three A's of AAA
Authentication — verifies the user's identity (who are you?). Authorization — determines what the authenticated user is permitted to do or access (what are you allowed to do?). For example, assigning a user to a specific VLAN based on their department. Accounting — records what the user did — connection time, bytes transferred, which resources were accessed (what did you do?). Accounting is critical for billing (ISPs) and security auditing.
Transport protocol
UDP — RADIUS uses UDP ports 1812 (authentication) and 1813 (accounting). The legacy ports 1645 and 1646 are also used by some older implementations. UDP is connectionless — RADIUS handles its own retransmission logic. The use of UDP rather than TCP means RADIUS does not have the TCP connection overhead, which is valuable when handling many simultaneous authentication requests.
Encryption scope
RADIUS encrypts only the password in the authentication request using MD5 (a weak hash, but the password is obscured). All other RADIUS attributes — username, NAS IP, session attributes — are transmitted in cleartext. This is a known weakness. RadSec (RADIUS over TLS) addresses this by encapsulating all RADIUS traffic in TLS. In high-security environments, RADIUS communications should traverse a dedicated management network or be protected with IPsec.
RADIUS in WPA2/WPA3 Enterprise
In enterprise wireless: the wireless access point is the RADIUS client (also called the NAS). When a user connects, the AP forwards the user's EAP credentials to the RADIUS server. The RADIUS server validates the credentials against Active Directory (or another directory) and returns Access-Accept (with attributes like VLAN assignment) or Access-Reject. The AP then either completes the connection or denies it. The user never communicates directly with the RADIUS server.
Common RADIUS servers
Microsoft NPS (Network Policy Server) — the built-in RADIUS server in Windows Server, integrates with Active Directory, free with Windows Server licensing. FreeRADIUS — open-source, widely deployed in Linux environments. Cisco ISE (Identity Services Engine) — enterprise-grade with advanced features (posture assessment, device profiling, guest access). Aruba ClearPass — another enterprise AAA platform.

WPA2-Enterprise — 802.1X / RADIUS Authentication Sequence

AP (Authenticator) → EAP-Request/Identity — AP requests client's identity
Client → EAP-Response/Identity — client sends username to AP

SECTION 7Authentication — TACACS+

Terminal Access Controller Access-Control System Plus (TACACS+) is a Cisco-developed AAA protocol designed primarily for device administration authentication — controlling who can log into and administer network devices such as routers, switches, firewalls, and other infrastructure equipment. Despite sharing AAA functions with RADIUS, TACACS+ differs significantly in its design, transport, and scope of use.

TACACS+
Terminal Access Controller Access-Control System Plus · Cisco proprietary · TCP port 49
Device Administration AAA
Primary use case
Network device administration — controlling who can SSH or console into a Cisco router, switch, or firewall and what commands they can execute. When a network engineer logs into a router CLI, TACACS+ authenticates the login, authorizes each command they attempt to run (command authorization), and logs every command for audit purposes (command accounting). This granular command-level control is TACACS+'s defining differentiator from RADIUS.
Transport protocol
TCP port 49 — unlike RADIUS's UDP, TACACS+ uses TCP for all communications. TCP provides reliable, connection-oriented delivery with built-in error detection and retransmission. This makes TACACS+ more reliable for interactive device administration sessions where a lost packet cannot simply be retried by the application layer.
Encryption scope
TACACS+ encrypts the entire payload of every packet — not just the password as RADIUS does. The encryption uses a shared secret key (a pre-shared key configured between the network device and the TACACS+ server) and MD5 hashing to generate the encryption key. Full payload encryption means that usernames, authorization attributes, and command logs are all protected in transit.
Separated AAA
TACACS+ implements fully separated Authentication, Authorization, and Accounting services — each function can use a different database, a different policy, or a different server. This modularity enables flexible configurations: authenticate against Active Directory, authorize commands against a local policy file, and log accounting to a separate syslog server. RADIUS combines authentication and authorization in a single request/response, making this separation impossible.
Command authorization
TACACS+ can be configured to permit or deny specific CLI commands per user or per group. A junior network technician might be authorized to run show commands (read-only) but not configure terminal (configuration changes). A senior engineer has full command access. This granularity allows strict separation of duties in network operations. RADIUS has no equivalent command-level authorization capability.
Cisco proprietary
TACACS+ was developed by Cisco and, while the protocol has been published, it is not an open standard. Primary implementations are Cisco ISE (Identity Services Engine) and the open-source tac_plus daemon. RADIUS is an IETF open standard (RFC 2865) with broad multi-vendor support. In non-Cisco environments, RADIUS is more commonly used even for device administration.

Exam Focus — RADIUS vs. TACACS+ Decision

The exam tests this distinction repeatedly. The key decision rule: RADIUS = network access authentication (who can connect to the Wi-Fi, VPN, or 802.1X wired port). TACACS+ = device administration authentication (who can log into and configure a router or switch). The three technical differentiators: (1) TACACS+ uses TCP, RADIUS uses UDP. (2) TACACS+ encrypts the entire payload, RADIUS encrypts only the password. (3) TACACS+ supports per-command authorization, RADIUS does not.

SECTION 8Authentication — Kerberos

Kerberos is a network authentication protocol developed at MIT that uses ticket-based authentication to allow nodes to prove their identity to one another over a non-secure network without transmitting passwords. It is the default authentication protocol for Windows Active Directory domains and is used by Linux and macOS in domain environments as well. Named after the three-headed dog guarding the underworld in Greek mythology — reflecting its three main components.

Kerberos
Kerberos v5 · RFC 4120 · Default Windows Active Directory authentication · UDP/TCP port 88
Domain Authentication
Core concept: tickets
Kerberos uses tickets — encrypted tokens issued by a trusted authority (the Key Distribution Center, KDC) that prove a user's identity to services without the user repeatedly transmitting their password. Once a user authenticates and obtains tickets, they can access multiple services during the day by presenting their ticket — the password is never sent again after the initial authentication. This is the mechanism enabling Single Sign-On in Active Directory environments.
Key Distribution Center (KDC)
The KDC is the trusted third party that issues tickets. In a Windows domain, the Domain Controller runs the KDC. The KDC has two components: the Authentication Service (AS) — handles initial user authentication and issues the TGT; and the Ticket Granting Service (TGS) — issues Service Tickets upon presentation of a valid TGT.
Ticket Granting Ticket (TGT)
The TGT is the "master ticket" obtained after the initial authentication against the KDC/AS. It proves to the TGS that the user has already been authenticated. The TGT is encrypted with the KDC's secret key — only the KDC can decrypt it. The user cannot read or modify their TGT. TGTs have a limited lifetime (default 10 hours in Windows AD, renewable for up to 7 days).
Service Ticket (ST)
A Service Ticket (ST) (also called a Service Granting Ticket, SGT) grants access to a specific service. When the user wants to access a file server, they present their TGT to the TGS and request a Service Ticket for that file server. The TGS issues a Service Ticket encrypted with the file server's secret key. The user presents this Service Ticket to the file server — the file server decrypts it (proving it came from the KDC) and grants access. The file server's password is never involved in the user interaction.
Mutual authentication
Kerberos provides mutual authentication — not only does the server verify the client's identity, but the client also verifies the server's identity. This prevents impersonation attacks where a rogue server tricks a client into authenticating to it. The service ticket mechanism ensures that only a server with the correct private key (shared with the KDC) can be authenticated.
Time sensitivity
Kerberos requires that all participating systems have synchronized clocks within a maximum skew (default 5 minutes in Windows AD). If a client's clock is more than 5 minutes off the KDC's clock, Kerberos authentication fails with a "clock skew too great" error. This is a replay attack defense — expired tickets are rejected based on timestamps. NTP (Network Time Protocol) is used to synchronize clocks across the domain.
Transport and port
Kerberos uses UDP port 88 by default for KDC requests. TCP port 88 is used when the response is too large for UDP (typically when certificates or large PAC data is included in the TGT). Kerberos traffic should be restricted to the internal network and not exposed externally.

Kerberos Authentication Flow

Kerberos Authentication — Accessing a File Server
Client → KDC/AS → AS-REQ — client requests authentication, sends username + pre-authentication data (timestamp encrypted with password-derived key)
KDC/AS → Client → AS-REP — KDC issues TGT (encrypted with KDC key) + session key (encrypted with client's key)
Client → KDC/TGS → TGS-REQ — client presents TGT + authenticator + name of target service (file server)
KDC/TGS → Client → TGS-REP — TGS issues Service Ticket (encrypted with file server's key) + new session key
Client → File Server → AP-REQ — client presents Service Ticket to file server + authenticator encrypted with session key
File Server → Client → AP-REP — file server confirms identity to client (mutual authentication); access granted

Kerberos in the Real World

Every time a user logs into a Windows domain computer and accesses a file share, printer, or application server without being prompted for a password — that seamless access is Kerberos working invisibly. The user authenticated once at login (obtained their TGT), and Kerberos handles all subsequent resource access transparently using Service Tickets. This ticket-based SSO is why domain users rarely need to re-enter their password during the workday, even as they access dozens of different servers and services.

SECTION 9Multifactor Authentication in Network Access

The multifactor authentication (MFA) listed in this objective specifically addresses MFA as it applies to network authentication — how the AAA systems (RADIUS, TACACS+, Kerberos) can be configured to require more than one authentication factor before granting access.

MFA with RADIUS RADIUS can enforce MFA for network access by integrating with an MFA provider. For example, Microsoft NPS with the Azure MFA extension requires both a password and an Authenticator app approval before allowing Wi-Fi or VPN connections. The RADIUS server forwards the authentication challenge to the MFA provider; the user approves on their phone; the RADIUS server then issues the Access-Accept. EAP methods such as EAP-TLS (certificate-based) inherently provide strong MFA — the user possesses a certificate (something they have) and the private key is protected by the machine's TPM or a PIN.
MFA with TACACS+ TACACS+ can be configured to require a second factor for device administration login. When a network engineer SSHs into a router managed by TACACS+, they may be required to enter their password and then approve an MFA push notification on their phone before receiving CLI access. This prevents unauthorized device changes even if an engineer's credentials are compromised.
MFA with Kerberos Kerberos pre-authentication can be strengthened with smart cards — the user inserts their smart card and enters a PIN to authenticate to the KDC. The smart card holds a certificate, making this MFA: something you have (smart card) + something you know (PIN). Windows Hello for Business also integrates with Kerberos — the biometric or PIN authenticates to Windows Hello, which then performs Kerberos authentication on the user's behalf using a certificate stored in the TPM.
EAP methods and factors EAP-TLS — certificate-based; the client presents a digital certificate (something you have); the certificate's private key is protected by TPM or PIN, making it inherently two-factor. PEAP-MSCHAPv2 — tunneled password authentication; single factor by itself but can be combined with additional factors. EAP-TTLS — similar to PEAP, supports various inner authentication methods. EAP-TLS is the most secure EAP method and the recommended choice for enterprise WPA2/WPA3 deployments.

RADIUS transportUDP ports 1812 (auth) / 1813 (accounting); encrypts password only
RADIUS use caseNetwork access authentication — Wi-Fi, VPN, 802.1X wired
TACACS+ transportTCP port 49; encrypts entire payload
TACACS+ use caseDevice administration — SSH/console to routers and switches; per-command authz
RADIUS vs. TACACS+UDP vs. TCP; password-only vs. full encryption; combined vs. separated AAA
Kerberos portUDP/TCP 88; Windows AD default authentication protocol
TGTTicket Granting Ticket — issued at login; used to get Service Tickets; proves prior auth
Service TicketGrants access to a specific service; encrypted with the target service's key
Kerberos time syncClocks must be within 5 minutes of KDC; NTP required; drift = auth failure
KDCKey Distribution Center — runs on Domain Controller; AS + TGS components
EAP-TLSCertificate-based EAP — most secure EAP method; inherent MFA (cert + PIN/TPM)
Forward secrecyWPA3 only — past traffic cannot be decrypted even if password is later compromised

High-Probability Exam Scenarios

Scenario 1: A company is using WEP on their wireless network. What should they upgrade to? → WPA2 (minimum) or WPA3. WEP is broken and must be replaced immediately.
Scenario 2: Users need to connect to Wi-Fi with their individual domain credentials rather than a shared password → WPA2/WPA3 Enterprise with 802.1X and a RADIUS server (Microsoft NPS).
Scenario 3: A network admin needs to log into a Cisco router — what authentication protocol controls this? → TACACS+ (device administration).
Scenario 4: Which AAA protocol uses TCP and encrypts the entire payload? → TACACS+. Which uses UDP and encrypts only the password? → RADIUS.
Scenario 5: A user cannot access domain resources after their workstation clock drifted → Kerberos time skew error; synchronize clock with NTP/domain controller.
Scenario 6: Which wireless security mode prevents offline dictionary attacks against the network password? → WPA3-Personal (SAE/Dragonfly).
Scenario 7: A technician sees a TKIP option in a router's security settings. Should they select it? → No — TKIP is deprecated; select AES (CCMP) only.
Scenario 8: What allows a domain user to access a file server without re-entering their password after logging in? → Kerberos ticket-based SSO (TGT → Service Ticket).
